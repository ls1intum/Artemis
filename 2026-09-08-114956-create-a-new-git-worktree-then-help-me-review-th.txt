  Short answer

  Your instinct is right. The container hardening in this PR is good and worth
  keeping. The transport is the wrong shape for the problem, and running it on
  build agents buys nothing that the PR's own recommended deployment
  (run-build-jobs=false on a dedicated host) does not already give you more
  directly.

  Why the middleware is the wrong transport

  The traffic is a stateful, session-affine request/response protocol, with
  large binary payloads and operations lasting minutes. Pub/sub gives you none
  of those four properties, and the code has to rebuild every one of them by
  hand:

  - correlation IDs plus an in-flight dedup map plus a 10,000-entry
    completed-response cache (claimRequest / rememberCompletedResponse)
  - at-least-once retry with exponential backoff and jitter, republishing the
    same request every 5s up to 60s for the whole budget
  - per-request deadlineEpochMillis, rechecked at four separate points inside
    handleCreate
  - a separate blob side-channel (hyperion-sandbox-payloads) with its own
    15-minute TTL, because the topic cannot carry the bytes
  - decline classification by substring matching on English error text
    (CAPACITY_REFUSAL_MARKER, DRAINING_REFUSAL_MARKER, OVERLOAD_REFUSAL_MARKER
    in isFailoverDecline)

  Each of those is a symptom of the envelope, not of the problem. A direct HTTP
  or gRPC call between core and the sandbox host deletes the entire layer:
  connection lifetime gives you liveness, streaming gives you copy-in/out
  without a cluster blob, a status code gives you a typed decline, and mTLS
  gives you the authentication the topic does not have.

  Concrete costs today:

  1. Broadcast fan-out for point-to-point RPC. Every EXEC reaches every hosting
     agent and is deserialized on its event thread before being discarded by the
     targetAgentShortName filter. Every response reaches every core node the
     same way. An agentic loop is chatty (tens to hundreds of tool calls per
     attempt, up to 11 attempts), and the retry loop multiplies it: one
     20-minute Maven verification republishes roughly 25 times, fleet-wide. This
     lands on the same Hazelcast event threads that carry the build-job queue,
     results, feature toggles, and broker status.
  2. 32 MB entries in the distributed map. MAX_PAYLOAD_BYTES = 32 * 1024 * 1024,
     staged in hyperion-sandbox-payloads. On Hazelcast that entry is
     partitioned across data members, which are your core nodes. Large entries
     inflate partition size and make migration on member join/leave lurch, so a
     workspace copy can degrade the cluster serving students. A plain socket
     between two processes costs neither heap nor cluster state.
  3. Structural worker starvation. The relay pool is maxGenerationSandboxSlots +
     1 threads on a SynchronousQueue with AbortPolicy. A long EXEC holds a
     worker for its full duration, so with 2 slots you get 3 threads and two
     running builds leave exactly one for every DESTROY, RESET, COPY_* and admin
     LIST in the fleet. Anything else is refused as "overloaded" and has to be
     retried.
  4. Duplicated, eventually consistent capacity. The semaphore is on the agent,
     the advertised free-slot count travels through BuildAgentInformation, and
     core picks optimistically then discovers the truth by trying candidates in
     order. That decline-and-retry loop only exists because there is no
     synchronous placement call.
  5. Asymmetric reconnect. InteractiveSandboxRelayHandler registers a
     connection-state listener and re-registers its request listener after a
     reconnect. RemoteInteractiveSandboxClient.registerResponseListener() runs
     once in @PostConstruct and never re-subscribes. If that topic proxy is
     invalidated, in-flight generations on that core wait out their full budget
     in silence.
  6. It breaks the distributed-data abstraction you just built. The PR states
     generation requires Hazelcast data-member topology, because
     GenerationJobService needs getDataNodeIds() for admission and quorum. So
     one of the three supported backends cannot run the feature at all. That is
     a regression against the whole point of DistributedDataProvider.

  Security

  Genuinely good, and worth keeping in any design: cap_drop ALL,
  no-new-privileges, read-only rootfs, bounded tmpfs, PID/CPU/memory limits with
  memorySwap == memory enforced, creation from the resolved immutable sha256:
  image ID rather than a tag, withInit(true), no host bind mounts, no Artemis
  credentials, operator-owned network with host and container: rejected and the
  bridge driver verified, and tar validation on both copy directions with hard
  byte caps.

  Where the relay widens the surface instead of narrowing it:

  - The request topic is an unauthenticated cluster-wide command channel.
    Anything that can publish to hyperion-sandbox-requests can ask a hosting
    agent to EXEC an arbitrary argv or COPY_OUT an arbitrary path. There is no
    requester authentication and no check that the publisher is a core node.
    Build agents are the least trusted machines in the deployment (they run
    student code), and this hands them the ability to inject commands into
    generation containers and to read other sessions' copy-in bytes out of the
    shared map. Today the cluster is one trust domain, so this is not an
    exploit. It does make that boundary load-bearing for a new capability.
  - timeoutSeconds is taken verbatim from the caller. SandboxSessionSpecDTO says
    resource limits come from the agent, and that holds for CPU/memory/PIDs,
    but handleExec does Duration.ofSeconds(request.timeoutSeconds()) with no
    clamp. Over an unauthenticated topic that is an unbounded container-hold
    primitive. One line to fix, but it shows what happens when a boundary
    becomes a wire protocol.
  - Blast radius on exam-critical hosts, mitigated only by documentation. Also
    ensureDockerImageAvailable takes the same ReentrantLock in
    BuildAgentDockerService that student image pulls take, so a cold generation
    pull blocks student build pulls on that agent.

  That last point is the crux. If the recommended deployment is a dedicated host
  with run-build-jobs=false, then the relay has bought a distributed command
  channel to reach a machine you then dedicate anyway.

  The dedicated generation node

  I'd separate two decisions, and I think the answer to both is yes:

  Transport should be direct. Keep the middleware for discovery and capacity
  advertisement, which is what BuildAgentInformation already does well. Take it
  off the per-operation data path.

  The container should be local to the process running the agent loop. The loop
  is: call the model, run a command, read output, decide. Every hop between
  "decide" and "run" is overhead. There is no queueing benefit (admission is
  fail-fast 503, there is no queue), no fairness benefit, and no scaling benefit
  at max-concurrent-jobs-per-core-node = 2. InteractiveSandbox is already an
  interface with a working local implementation; the relay is the ~1,400 lines
  wrapped around it.

  On the counter-arguments as I read them:

  - Core nodes should not hold a Docker socket. Right, which is why it should be
    a new node role rather than the existing core: a generation profile with
    the socket, no student traffic, no VCS serving, no exam duty. Then "which
    machines run untrusted generated code" is a topology fact instead of a
    property an operator must remember to zero out on every agent.
  - Provider credentials must stay on core. They can, and co-location makes that
    more true: model call and credential live in one process.
  - Generation needs the LocalCI parsers and the persistence path. This is the
    real constraint, and it argues exactly for your proposal (a core-family node
    that also has Docker), not for shipping operations to a build agent.
  - You lose horizontal scaling. You add generation nodes the way you add build
    agents. Placement becomes "which generation node has a free slot", and the
    session then stays there for its whole life, which the relay has to enforce
    with affinity logic anyway.
  - Holding a container for 45 minutes while waiting on the model is wasteful.
    True, and equally true on a build agent. Co-location does not make it worse,
    it puts it on the node whose slot limit already governs it.

  Two things I'd keep regardless of transport: separating the sandbox slot from
  the exercise coordination slot, and releasing the container before repository
  persistence. Both are good calls and independent of this decision.

  Separately, the sharpest reliability edge I found is not in the sandbox layer
  at all: the external-mutation guard now sits on the ordinary staff push and
  code-editor save path, fails fast with 409 on any concurrent staff edit of the
  same exercise, applies a strict cluster-topology check to every push, and
  leaves a slot that is never auto-reclaimed if the node dies mid-push. Say the
  word and I'll write that up.

⏺ Here's a concrete access design, grounded in what the generation code actually
  calls. I traced the cross-module imports of
  hyperion/service/exercisegeneration/** and the two services that own the I/O
  (GenerationWorkspaceService, GenerationPersistenceService).

  Node role

  A new profile, say generation, that composes as core + localci + localvc + 
  scheduling + generation, with buildagent absent and Docker present. That is
  the same profile set HyperionExerciseGenerationEnabled already demands, so the
  condition does not change.

  There is one wrinkle worth deciding up front: localvc is currently an
  all-or-nothing profile. It gives you GitService (which is what generation
  needs), but it also activates JGitServletConfiguration,
  ArtemisGitServletService, SshConfiguration (the SSH daemon),
  GitPublickeyAuthenticatorService, LocalVCServletService, VcsAccessLogService
  and LocalVCPersonalAccessTokenManagementService. A generation node needs
  repository access, not a repository server. So either split the profile
  (localvc-core for the git plumbing, localvc-serve for the servlet plus SSH
  listener) or leave the listeners bound off on generation nodes. I'd split it:
  it is a small change and it makes the "no student or staff git traffic reaches
  this host" property structural rather than a firewall rule.

  1. Database

  Read-write, full schema, same credentials as a core node. There is no useful
  reduction here. The generation flow writes through the ordinary services:

  Two things I would constrain:

  - Do not let a generation node own Liquibase. Set
    spring.liquibase.enabled=false on this role. Migration should stay with the
    core nodes so a generation node joining or restarting never races a schema
    change.
  - Size its pool separately and small. Concurrency is
    max-concurrent-jobs-per-core-node = 2, and the DB work is bursty (seed at
    start, save at the end) with 45 minutes of near-idle model waiting in
    between. A generation node holding a core-sized HikariCP pool against the
    same database is wasted capacity, and worse, it is a way for generation
    nodes to eat connections that students need. Give it its own small
    spring.datasource.hikari.maximum-pool-size.

  The @Scheduled reaper (GenerationJobService.clearStaleJobs, stale-job-scan-ms)
  means the scheduling profile has to be active, so also confirm this node does
  not pick up the other scheduled jobs that assume a single owner (retention,
  cleanup, notifications). That is worth an explicit audit, not an assumption.

  2. Filesystem

  Read-write on the LocalVC bare repository tree. This is the load-bearing one
  and it is easy to miss. GitService.getGitUri() returns
  vcsRepositoryUri.getLocalRepositoryPath(localVCBasePath).toUri(), so every
  clone, ls-remote, and push in the generation flow is a file:// operation
  against artemis.version-control.local-vcs-repo-path. On our production and
  staging setup that path is the NFS export. So a generation node needs the same
  NFS mount as core, read-write, and it inherits the boot-order hazard we
  already hit (my note on the staging1 NFS boot race: a hard mount that is not
  yet available hangs startup at SshConfiguration forever).

  If you want to avoid the NFS dependency, the alternative is to make generation
  reach repositories over the git protocol (HTTP or SSH against a LocalVC node)
  instead of the filesystem. That is a bigger change and it puts staff-level
  credentials on the generation node, so I would keep the mount and accept it.

  Node-local scratch, not the shared clone path. Generation already does the
  right thing here: checkoutWorkingTree and the persistence checkouts both use
  TempFileUtilService temporary roots (temporaryRoot.resolve("repository")) and
  delete them afterwards, rather than artemis.repo-clone-path. So the node needs
  a decent local scratch volume sized for a few concurrent full checkouts of
  template plus solution plus tests, and it does not need the shared clone
  directory. Worth making that explicit in the deployment so nobody points
  artemis.repo-clone-path at a shared volume on this role.

  The Docker socket. Local, root-equivalent on that host, which is exactly why
  this must not be a machine that also serves students.

  Classpath template resources.
  ResourceLoaderService.getFileResources(Path.of("templates")...) reads the Java
  reference project and build-script templates, so nothing external.

  3. Docker and egress

  Unchanged from the PR, and this part is good: containers created from the
  resolved immutable sha256: image ID, cap_drop ALL, no-new-privileges,
  read-only rootfs, bounded tmpfs on the four writable roots, CPU/memory/PID
  limits with memorySwap == memory enforced, init for reaping, no host bind
  mounts, no Artemis credentials inside.

  The network policy stays operator-owned (generation-sandbox-network, none by
  default, bridge driver verified, host and container: rejected). What changes
  for the better with a dedicated node: the container network and the host
  network are now the same blast radius question, and you can answer it once per
  host instead of per build agent. Firewall the generation host so its
  containers cannot reach the database, the Hazelcast or Redis ports, the
  LocalVC node, the NFS export, or the cloud metadata endpoint. Right now that
  isolation is documentation plus an operator remembering to set
  max-generation-sandbox-slots=0 on exam agents.

  Also move the image pull off the shared lock. Today ensureDockerImageAvailable
  takes the same ReentrantLock in BuildAgentDockerService that student build
  image pulls take, so a cold generation pull stalls student pulls. On a
  dedicated node that lock has no student traffic to block, but the code should
  not be reaching into BuildAgentDockerService at all.

  4. Incoming REST

  Split the seven endpoints by what they actually need:

  Endpoint: POST .../generate-exercise
  Needs Docker + local Git: yes (runs the loop)
  Can be served anywhere:

  Endpoint: POST .../generate-exercise/revert
  Needs Docker + local Git: yes (Git write + DB)
  Can be served anywhere:
  ────────────────────────────────────────
  Endpoint: GET .../status
  Needs Docker + local Git:
  Can be served anywhere: yes, reads GenerationJobReplayStore from the
  distributed map
  ────────────────────────────────────────
  Endpoint: GET .../artifacts
  Needs Docker + local Git:
  Can be served anywhere: yes, same store
  ────────────────────────────────────────
  Endpoint: DELETE .../jobs/{jobId}
  Needs Docker + local Git:
  Can be served anywhere: yes, writes the cancellation map plus interruptCluster
  ────────────────────────────────────────
  Endpoint: GET .../supported-languages, /effort-profiles
  Needs Docker + local Git:
  Can be served anywhere: yes, static config
  ────────────────────────────────────────
  Endpoint: POST courses/{id}/.../metadata-suggestion
  Needs Docker + local Git:
  Can be served anywhere: yes, but needs the provider credential

  So only two of seven are node-bound. I see two ways to route, and I prefer the
  second:

  (a) Load-balancer path routing. Send
  /api/hyperion/programming-exercises/*/generate-exercise and .../revert to the
  generation pool, everything else to core. Simple, no new plumbing, but it
  hard-codes a feature into the nginx config and it will be got wrong at least
  once.

  (b) Keep the whole REST surface on every core node, and hand off the job. The
  admitting core node does what it already does (authorize, validate
  eligibility, resolve the effort profile, reserve the budget, mint the job id,
  claim the exercise slot, return 202), then publishes one start message. A
  generation node picks it up, claims ownership, starts heartbeating, and runs
  the loop entirely in-process. Progress and status flow back the way they
  already do, through the replay store and the STOMP broker.

  I prefer (b) because it uses the middleware for the thing it is actually good
  at, a single job handoff, rather than a chatty per-tool-call data path. It is
  one message per job instead of the hundreds the current relay sends, the LB
  stays dumb, and as a side effect it removes the "no spillover from a busy core
  to an idle one" limitation that max-concurrent-jobs-per-core-node currently
  imposes. It is also the same shape as the existing build job queue, so the
  reliability story is one your team already operates. If you go further and
  make it a real queue rather than a fail-fast handoff, instructors would wait
  instead of getting a 503 exerciseGenerationCapacityExceeded, which is probably
  the better product behaviour anyway.

  One decision (b) forces: metadata-suggestion is a plain model call with no
  Docker. If you want the provider credential to exist only on generation nodes,
  that endpoint has to be routed there too, or the credential has to live on
  core as well. Pick one deliberately.

  5. Outbound

  - STOMP broker relay. Progress goes to
    /user/topic/hyperion/exercise-generation/jobs/{jobId} and the state topic
    /topic/hyperion/exercise-generation/exercises/{id}/state. Because that goes
    through the external broker, the instructor's browser can stay connected to
    any core node while the job runs elsewhere. The generation node needs
    outbound access to the broker and nothing more; it does not need to
    terminate client websockets.
  - AI provider. Outbound HTTPS, credential on this node.
  - OTel collector. If artemis.telemetry.gen-ai.capture-content=true, this node
    ships prompt and completion content, so treat its egress to the collector as
    a sensitive path.

  6. Distributed middleware, and a trap to avoid

  The node still needs the distributed provider for the job slot map,
  cancellation map, replay store, budget windows, and the exercise coordination
  lock. What it should no longer need is hyperion-sandbox-requests,
  hyperion-sandbox-responses, and hyperion-sandbox-payloads. Deleting that last
  one is the single biggest win: no more 32 MB entries partitioned across the
  nodes that serve students.

  The trap: it is tempting to make generation nodes Hazelcast lite members so
  they host no partitions and their restarts cause no rebalancing. That is the
  right instinct, but the current code would break on it.
  HazelcastDistributedDataProviderService.getDataNodeIds() filters lite members
  out, and GenerationJobReaper.ownerMemberIsPresent(job) checks
  getDataNodeIds().contains(job.ownerNodeId()). A lite-member owner would never
  appear in that set, so shouldClearAsStale would be true from the first sweep
  and every generation job would be treated as owner-absent immediately.

  The fix is to separate two questions the current API conflates:

  - Is the owner still in the cluster? Full member set, lite members included.
    This is a liveness check.
  - Is the store topology what we configured? Data members only. This is the
    quorum check behind verifyExpectedDataMemberTopology and
    verifyMajorityDataMemberTopology.

  Worth doing regardless of the lite-member decision, because right now a
  generation node that is a data member also counts toward
  expected-data-member-count, which means adding generation capacity changes the
  quorum arithmetic for admission and for wedged-slot recovery. That coupling
  is not something you want.

  7. What the node must not have

  - No buildagent profile, so it never takes a student or exam build job.
  - No exposed git servlet or SSH daemon (see the profile split above).
  - No client websocket termination and no place in the normal /api/** LB pool,
    if you go with routing option (a).
  - No Liquibase ownership.
  - No shared writable Docker or Maven cache with any other host, which the PR
    already says.
  - Container egress firewalled off the database, the distributed-store ports,
    LocalVC, NFS, and metadata endpoints.

  The worst-case argument

  This is the reason I'd push for it even at some engineering cost. Compare what
  a compromised generation host gets you:

  With the PR as written (or with my earlier dedicated-core-node sketch): a
  root-equivalent Docker socket, an NFS mount holding every repository of every
  course, a read-write connection to the whole database including users and exam
  data, and membership in the distributed store where the build-job queue and
  feature toggles live.

  With your split: the ability to return a bad candidate for the one exercise it
  was handed, plus whatever egress its containers were granted. It has no
  repository access, no database, no cluster membership. Nothing else on the
  machine is worth stealing.

  That is a genuine security argument, not a tidiness argument.

  The job contract

  Input (core to worker). All of this is data core already computes:

  - mode (GENERATE / ADAPT), the brief, selected feedback thread text
  - effective settings: max turns, token budget, deadline, model id, effort
    profile contents
  - exercise facts, not the entity: programming language, project type,
    sequential-test-runs flag, package name, short name, title, problem
    statement, task list
  - seed content: Map<String, String> per repository (template, solution,
    tests), plus the head hash of each as an opaque echo token
  - build config: image reference, build script or phases, result paths
  - SCA configuration (this is the StaticCodeAnalysisCategoryRepository read,
    moved into the payload)
  - existing test case names and weights if adapting (the other Optional
    repository read, same treatment)

  Output (worker to core):

  - produced Map<String, String> per repository, plus the problem statement
  - raw verification artifacts: the surefire XML and SCA report contents for
    both lanes, and build logs
  - the worker's own verdict and review findings, clearly labelled as advisory
  - usage accounting: tokens by class, model and request ids, tool call counts,
    attempts, accounting state
  - the head hashes it was seeded with, echoed back
  - terminal outcome and reason

  Nothing in either direction is an entity, so the worker does not need JPA at
  all.

  Lifecycle

  Core keeps everything durable. Worker exposes a small job API:

  - POST /generation-jobs returns 202 with a worker-local id
  - GET /generation-jobs/{id}/events streams progress (SSE), so core can
    reattach after its own restart
  - GET /generation-jobs/{id}/result
  - DELETE /generation-jobs/{id} cancels
  - GET /capacity for placement

  Core relays events to STOMP, which keeps websocket authorization where
  AuthorizationCheckService lives. Core owns the job slot, the heartbeat, the
  budget reservation, and cancellation, because core is the one with the
  database.

  The crash semantics get much better as a side effect. The worker holds nothing
  durable, so a worker crash means "job lost, retry" with no partial writes, no
  wedged slot, and no admin recovery endpoint. That removes a whole class of
  problems, including the lite-member versus quorum trap I flagged earlier,
  since the worker is no longer a cluster member at all.

  Placement also collapses: core dispatched the jobs, so core knows the load. No
  permit semaphore, no advertised slot count in BuildAgentInformation, no
  optimistic placement with decline-and-retry, and no routing decisions made by
  substring-matching English error messages.

  Three things this forces you to decide

  1. Core must re-verify, not trust the verdict. This is the one place the split
  adds a requirement rather than removing one. The PR's safety story is
  "Artemis rebuilds clean lanes and parses with the production parsers". If the
  worker executes the build and reads the report and reports the outcome, then a
  bug or compromise in the worker can hand core a false "verified" and core
  will persist it.

  Minimum fix: the worker returns raw report content, core re-parses it with
  TestResultXmlParser and ReportParser and derives the verdict itself. Cheap,
  and it reduces the worker's forgery surface from "assert success" to
  "fabricate plausible surefire XML".

  Stronger, and I think worth considering: core already triggers a LocalCI
  synchronization build after saving (triggerRestrictedBuild). Make that build's
  outcome gate the SUCCESS label rather than being informational. Then you get
  the best of both models: the sandbox handles the fast iterative authoring loop
  with no CI scheduling per attempt, which was the whole point of the PR, and
  real LocalCI provides the final independent acceptance check exactly once. A
  mismatch becomes NEEDS_REVIEW or PARTIAL instead of silent success.

  2. Where the provider credential lives. Your design puts it on the worker,
  which contradicts the PR's "provider credentials stay on core". I think worker
  is right for the generation loop, but note the consequences:
  metadata-suggestion is a pure model call with no Docker, and the existing

  3. Packaging. Same WAR with a new profile is the pragmatic answer, and it
  keeps the parsers and classpath templates available with no new artifact. The
  cost is making the app start with no datasource: you need the JPA and
  Liquibase autoconfiguration excluded on that profile and you'll likely find

  cost and worth budgeting for honestly rather than discovering it late.

⏺ Before the plan, one consequence of your reframing that I think reshapes
  everything downstream.

  The playground framing removes most of the hard machinery

  In the PR as written, the system decides to save. That single fact is what
  forces: a non-cancellable transition, ownership fencing around Git and DB
  writes, the wedged-slot map with no TTL, the admin exact-token recovery
  endpoints, the PARTIAL reconciliation state, the seven-day undo baseline, and
  the shutdown drain timeout. All of it exists to answer "what if the writer
  dies mid-write".

  In a playground, the instructor decides to apply. The write becomes a short,
  user-initiated REST call on a core node that can go through the ordinary
  exercise-update path with its existing guards. That deletes the whole
  category. And because the worker never writes anything durable, a dead worker
  is always safe to reclaim: worst case the session is lost and the instructor
  restarts it.

  So I would make instructor-triggered apply the v1 semantics and treat
  "auto-apply when verified" as a later, optional mode. It is a better product
  and it is a dramatically smaller system.

  A second consequence: with apply under human control, the verification and
  critic packages from the current PR (ExerciseIntegrityGate,
  DifferentialVerificationService, StageCheckService, SpecFidelityCriticService,
  SpecificationReviewCritic, StructuralOracleSeedingService, about 5,100
  production lines plus large tests) stop being a save gate and become advisory
  quality signals. They can be deferred entirely and added later without
  blocking the playground. That is roughly a third of the current server code
  removed from the critical path.

  Why the middleware is now the right transport

  I argued against it earlier for the per-tool-call relay. Your design changes
  the arithmetic. Message volume per session:

  ┌───────────┬──────────────────────┬──────────────────────────────────────┐
  │           │      Current PR      │             This design              │
  ├───────────┼──────────────────────┼──────────────────────────────────────┤
  │ Per tool  │ 2 broadcast messages │ 0                                    │
  │ call      │                      │                                      │
  ├───────────┼──────────────────────┼──────────────────────────────────────┤
  │ Large     │ 32 MB blobs in a     │                                      │
  │ payloads  │ distributed map, per │ a few hundred KB per checkpoint      │
  │           │  copy                │                                      │
  ├───────────┼──────────────────────┼──────────────────────────────────────┤
  │ Per       │ hundreds to low      │ 1 dispatch, ~30 to 80 events, 3 to   │
  │ session   │ thousands            │ 10 checkpoints, a handful of inbox   │
  │           │                      │ messages, plus heartbeats            │
  └───────────┴──────────────────────┴──────────────────────────────────────┘

  At that volume the middleware is a fine control plane, and you avoid adding a
  network listener, TLS, service discovery, and firewall rules to a new node
  type. The relay was wrong because it was a data path. A checkpoint channel is
  a control path.

  The node contract

  Call it an authoring worker, not a core node. The name matters, because "core"
  invites the next person to give it a datasource.

  ┌──────────────────────────────────┬──────────────────────────────────────┐
  │              Access              │                Yes/No                │
  ├──────────────────────────────────┼──────────────────────────────────────┤

  ├──────────────────────────────────┼──────────────────────────────────────┤
  │ Distributed store (Hazelcast or  │ yes, five channels, nothing else     │
  │ Redis)                           │                                      │
  ├──────────────────────────────────┼──────────────────────────────────────┤

  ├──────────────────────────────────┼──────────────────────────────────────┤

  ├──────────────────────────────────┼──────────────────────────────────────┤

  │                                  │ verification only                    │

  Everything it needs about the exercise arrives in the session request.
  Everything it produces leaves as events and checkpoints.

  One detail that keeps localci off the worker entirely:
  BuildScriptProviderService and BuildPhasesTemplateService are both template
  and config driven with no repository dependency. So core renders the build 
  script and ships it as a string. The worker just executes it.

  The five channels

  Channel: hyperion-session-queue
  Kind: queue
  Direction: core → worker
  Contents: session request. Any worker with a free slot takes one. Natural load

  balancing, no capacity advertisement, no placement RPC, and it fixes the "no
  spillover from a busy core to an idle one" limitation
  ────────────────────────────────────────
  Channel: hyperion-session-owners
  Kind: map
  Direction: worker → all
  Contents: {workerNodeId, startedAt, lastHeartbeat, state}. Core's reaper
  reclaims a stale or departed owner, which is safe here
  ────────────────────────────────────────
  Channel: hyperion-session-events
  Kind: queue
  Direction: worker → core
  Contents: stage transitions, tool activity, usage deltas, "checkpoint N
  available", terminal outcome. A queue rather than a topic so exactly one core
   republishes to STOMP
  ────────────────────────────────────────
  Channel: hyperion-session-inbox
  Kind: expiring map per session
  Direction: core → worker
  Contents: instructor feedback, request-checkpoint, pause, cancel. Worker
  drains
  at turn boundaries; cancel is polled more eagerly
  ────────────────────────────────────────
  Channel: hyperion-session-artifacts
  Kind: expiring map
  Direction: worker → core
  Contents: checkpoint payloads. Hard size cap, bounded retained count, core
  removes after ingestion

  Keep events and artifacts separate: events are small and frequent, artifacts
  are large and rare.

  Because both directions are now cluster-internal messages rather than
  commands, core should validate that an incoming event or checkpoint belongs to
  a session it dispatched and whose owner token matches. Cheap, and it closes
  the "any cluster member can inject" gap I flagged in the relay.

  Container and warm caches

  One container per session, long-lived, holding the working state:

  - /workspace/{template,solution,tests} materialized from the seed text maps.
    BinaryContent already establishes that the pipeline is UTF-8 text maps, so
    this is the shape the code already uses.
  - git init plus an initial commit inside each. This buys three things: the
    agent gets real git diff and git status tools, checkpoints get a natural
    diff representation, and a checkpoint can ship as a diff since the last one
    instead of a full snapshot, which cuts payload size substantially.
  - The build script runs in the same container against the same working tree,
    so the inner loop needs no roundtrip at all.

  On warm caches, the naive implementation is a shared writable host volume for
  ~/.m2/repository, and I would push back on that specifically. Model-authored
  code executes in these containers. A shared writable Maven cache is a
  poisoning path from session A into session B, and it is exactly the "shared
  writable host caches" the current PR already forbids for good reason.

  The clean version: bake the warm cache into the pinned sandbox image, then
  mount an anonymous Docker volume at the cache path per session. Docker seeds a
  fresh anonymous volume from the image content when the image directory is
  non-empty, so you get a warm, writable, per-session cache that is discarded
  with the container, and it works alongside --read-only rootfs (which masks a
  plain --tmpfs mount, so that variant would hide the baked cache). Cache
  freshness then becomes an image-release concern, which is where the
  artemis-maven-docker work already lives.

  Checkpoints, apply, and final verification

  - Worker reaches a checkpoint (explicitly, or when the instructor asks) and
    publishes the payload: text maps or diffs per repository, plus raw build
    reports and logs.
  - Core ingests, stores it in the session replay store, and republishes an
    event to STOMP. The instructor browses it read-only in the code editor.
  - Instructor clicks apply. Core writes through the ordinary exercise update
    and repository commit path.
  - Core then triggers the normal LocalCI build on the real build agents, and
    gates the reported outcome on that build: the solution must pass and the
    template must fail the intended tests. If the build disagrees with what the
    container reported, say so and mark it needs review.

  That last step is what makes the worker's verdict non-load-bearing. Core
  should also re-parse the raw reports itself with the production parsers rather
  than trusting a parsed verdict, so the worker's forgery surface shrinks from
  "assert success" to "fabricate plausible surefire XML".

  Idle sessions

  An interactive session holds a container through minutes of instructor
  thinking time. Two things to decide up front: an idle policy (warn event,
  auto-checkpoint, then release with the checkpoint preserved on core) and the
  sizing basis. Capacity should be sized on concurrent open sessions, not
  concurrent active compute, and utilization will be low by design. Better to
  say that out loud than discover it.

  Solving autonomous save without the wedged-slot machinery

  In the experiment PR the writer is the long-lived process holding the model
  session, so "what if the writer dies mid-write" needs fencing, a
  non-cancellable transition, and admin recovery.

  Here the worker never writes. It requests an apply, and core authorizes and
  performs it. That turns the problem into "what if a core node dies during a
  short apply", which is solvable by making apply declarative and idempotent
  rather than by fencing:

  - The checkpoint fully declares the target state, so apply means "make these
    three repositories equal this content, given these expected heads".
  - applyId is derived deterministically from (sessionId, checkpointId), so a
    retry is recognized as the same operation.
  - Core records apply progress before touching Git, and each push carries the
    checkpoint's expectedHeadCommit as a lease.
  - Re-running the same applyId converges: repositories already matching are
    no-ops, a failed lease is a hard CONFLICT that stops the whole apply.

  A core node that dies mid-apply is recovered by any core re-running the same
  applyId. No wedged slot, no admin token endpoint, no drain timeout.

  That single decision is what lets the agent decide to save while keeping the
  worker write-free, and it is also what makes the interactive mode a policy
  swap rather than a second architecture.

  Failure: Worker JVM dies
  Detected by: core reaper via stale heartbeat
  Result: session reclaimed, container reaped locally, last checkpoint
  preserved,
  nothing written
  ────────────────────────────────────────
  Failure: Container dies
  Detected by: worker
  Result: session fails, event published, no write
  ────────────────────────────────────────
  Failure: Worker cannot reach the cluster
  Detected by: core reaper
  Result: same as worker death
  ────────────────────────────────────────
  Failure: Core dies before apply
  Detected by: reaper
  Result: session reclaimed, checkpoint intact
  ────────────────────────────────────────
  Failure: Core dies during apply
  Detected by: next applyId retry
  Result: converges; repos already matching are no-ops
  ────────────────────────────────────────
  Failure: Lease fails on a repository
  Detected by: CheckpointApplyService
  Result: CONFLICT, nothing further attempted, instructor told which repo moved
  ────────────────────────────────────────
  Failure: Final LocalCI build disagrees with the container
  Detected by: recordFinalVerification
  Result: outcome downgraded to needs-review with the discrepancy stated
  ────────────────────────────────────────
  Failure: Budget or deadline exhausted
  Detected by: worker
  Result: terminal event; last candidate remains applicable by an instructor
  ────────────────────────────────────────
  Failure: Instructor idle in interactive mode
  Detected by: worker idle policy
  Result: auto-checkpoint, then release the container; checkpoint survives on

  Three design points that came out of drawing it, and which I'd want you to
  push back on if you disagree:

  The worker asks, core writes. The agent's toolset ends in requestApply(),
  which emits an event. It has no write method at all. That is what makes
  autonomous save affordable: in PR #13156 the process holding the model session
  is also the process writing Git and the database, which is why it needs a
  non-cancellable transition, a wedged-slot map with no TTL, two admin recovery
  endpoints, a PARTIAL state, and a drain budget. Moving the write to core
  deletes that whole category.

  Apply is declarative and keyed by applyId = hash(sessionId, checkpointId). The
  checkpoint declares the full target content, so re-running the same apply
  converges and matching repositories are no-ops. A core node dying mid-apply is
  recovered by any core re-running the same id, not by an operator with a
  token.

  AWAITING_INSTRUCTOR is in the enum from day one. The autonomous policy never
  enters it. That is the entire cost of keeping the playground open as a future:
  a second CandidatePolicy implementation plus UI, no new states and no
  protocol change. The command channel that carries INSTRUCTOR_FEEDBACK also
  carries APPLY_RESULT, which autonomous mode needs anyway, so it gets built in
  PR 1 regardless.

  no existing code. Three open decisions are listed at the bottom of the page;
  the checkpoint representation question (full snapshot versus diff) is the one
  that has to be settled before PR 1, because it shapes RepositoryContentDTO.

  application-buildagent.yml runs Artemis in production today with no
  datasource. My earlier call that the no-datasource boot was the plan's one

  What the build-agent profile already solves

  It disables Liquibase, blanks the datasource, turns off
  spring.data.jpa.repositories, and excludes:

  HibernateJpaAutoConfiguration, DataSourceAutoConfiguration,
  DataJpaRepositoriesAutoConfiguration,
  DataSourceTransactionManagerAutoConfiguration,
  JdbcTemplateAutoConfiguration, JdbcClientAutoConfiguration

  The worker copies that block verbatim. Four things genuinely differ.

  Difference 1: no servlet container at all

  Build agents keep a web server on port 8080 for actuator. The worker should
  not, and there is a security reason rather than just a tidiness one:
  SecurityConfiguration is @Profile(PROFILE_CORE), so a non-core node has no
  SecurityFilterChain. Any controller that reached the worker's port would be
  unauthenticated.

  So set spring.main.web-application-type: none. That makes "no incoming REST"
  structural: no Tomcat, no DispatcherServlet, no listening socket. Everything
  @ConditionalOnWebApplication backs off by itself.

  What you give up is the HTTP health probe. The worker's liveness is already
  visible in the cluster through its hyperion-session-owners heartbeat, so an
  admin view can show it, and process supervision covers the rest. If you decide
  you need an HTTP probe, the fallback is a servlet app with server.address: 
  127.0.0.1 plus a dedicated management.server.port, but then the unsecured-port
  problem is yours to handle.

  This is the remaining unknown. Nothing in the repo sets web-application-type
  today, so it is untried. It is what the PR 1 spike should test.

  Difference 2: Hyperion on, and Spring AI without a DataSource

  Build agents force artemis.hyperion.enabled: false. The worker needs it true,
  which loads SpringAIConfiguration (condition: isAtlasEnabled || 
  isHyperionEnabled).

  The good news: AgentLoopRunner injects Collection<ChatModel>, not ChatClient
  and not ChatMemory. The model bean comes from spring-ai-starter-model-openai
  autoconfiguration, which needs no database.

  The trap: SpringAIConfiguration declares

  @Bean @Lazy
  public ChatMemoryRepository chatMemoryRepository(DataSource dataSource) { ...
  }

  Its javadoc claims "only created if no other ChatMemoryRepository bean
  exists", but there is no @ConditionalOnMissingBean on it. Today it survives on
  the worker only because it is @Lazy and nothing asks for it. That is a latent
  trip-wire, so guard it properly (see the code changes below).

  spring.ai.model.chat: openai is already set in application-artemis.yml, so the
  worker inherits a working model config and only needs the endpoint, key and
  model name pointed at the approved provider.

  Difference 3: Hazelcast client, not data member

  HazelcastConfiguration.shouldRunAsHazelcastClient() is:

  return activeProfiles.contains(PROFILE_BUILDAGENT)
          && !activeProfiles.contains(PROFILE_CORE)
          && !activeProfiles.contains(PROFILE_TEST_BUILDAGENT);

  A node with only a worker profile matches none of that, so it would join as a
  full data member. That is wrong in three ways: it would host partitions
  (checkpoint payloads land on it), it would count in getDataNodeIds() and so
  shift the expected-data-member-count arithmetic that Hyperion admission and
  quorum recovery depend on, and every worker restart would trigger cluster-wide
  partition rebalancing.

  The worker must run as a Hazelcast client, like build agents. That is a
  one-line condition change, and it has to be in PR 1.

  Difference 4: ResourceLoaderService is core-only

  It is @Profile(PROFILE_CORE), and the generation flow uses it to load the Java
  reference-project fixture and build-script templates.

  Rather than widening the profile, core should ship the reference fixture in 
  the seed, the same way it already renders the build script. Then template
  resolution stays in exactly one place and the worker needs no template
  knowledge at all. That means one more field on WorkspaceSeedDTO, which is a
  change to make now while the record is still on paper.
