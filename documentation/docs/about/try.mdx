The fastest way to judge Artemis is to use it. The setup below includes the
[integrated code lifecycle](/instructor/integrations/integrated-code-lifecycle), so it covers
**programming exercises**: Artemis hosts the git repositories itself and runs the tests in Docker
containers on a build agent. That is the part of Artemis worth looking at first.

## Run it locally with Docker

You need [Docker](https://docs.docker.com/get-started/get-docker/) with the Compose plugin, and about
6 GB of memory available to it (in Docker Desktop: **Settings → Resources**). Published images cover
both `amd64` and `arm64`, so Apple Silicon pulls a prebuilt image rather than building one.

```bash
git clone https://github.com/ls1intum/Artemis.git
cd Artemis
# Select the native exercise build images for the Docker engine.
export ARTEMIS_TRIAL_ARCH=$(docker version --format '{{.Server.Arch}}')
# Native Linux only: give the build agent access to the host's Docker socket.
export ARTEMIS_DOCKER_GROUP_ID=$(stat -c %g /var/run/docker.sock)
docker compose --env-file .env -f deployment/docker/artemis-dev-local-vc-local-ci-postgres.yml pull
docker compose --env-file .env -f deployment/docker/artemis-dev-local-vc-local-ci-postgres.yml up
```

Then open **http://localhost:8080** and sign in as `artemis_admin` / `artemis_admin`.

The architecture setting selects the build agent’s exercise images and is required for native
ARM64 builds, including Apple Silicon. On Docker Desktop, skip the `ARTEMIS_DOCKER_GROUP_ID` line.
In PowerShell, set `$env:ARTEMIS_TRIAL_ARCH = docker version --format '{{.Server.Arch}}'` before
running Compose.

<Callout variant={CalloutVariant.warning}>
    Run Compose **from the repository root** and keep `--env-file .env`. The Compose files read image
    versions from the `.env` file in the repository root, and Compose looks for that file next to the
    first `-f` file, which is `deployment/docker/`, not the root. Without it the images resolve to blanks and the
    project either fails to start or fails to pull.
</Callout>

To stop, press `Ctrl+C`. To remove the containers and the database volume as well:

```bash
docker compose --env-file .env -f deployment/docker/artemis-dev-local-vc-local-ci-postgres.yml down -v
```

## Verify automatic grading

The local trial supports password sign-in for the test administrator. With the trial running, open a second terminal at the repository root and run the check with Node.js 26. If your rehearsal requires an administrator passkey, use the browser procedure in the [production hardening checklist](/admin/production-setup/hardening-checklist#data).

```bash
node supporting_scripts/trial/verify-grading.mjs
```

The check creates a test course, imports the small C exercise bundled with Artemis, and opens a
student participation. It commits the supplied solution through the online editor API. A successful
run prints `PASS` with the exercise, participation, Git commit and result IDs, a score of 100%, and
the count of passing tests. Each build has up to ten minutes to report its result. If the check
stops at a build stage, open **Server Administration → Build Agents** and the build queue to
inspect the job and the image pull.

The course and its Git repositories stay available for inspection. To check a disposable restored
copy, use the same account and the exercise ID printed by the first run.

```bash
node supporting_scripts/trial/verify-grading.mjs --exercise-id 123
```

Replace `123` with your ID. The check confirms that the previous grade’s commit exists in the restored
repository, submits a new commit to that participation, and waits for its grade. Both commands
use the local listener on port 8080. Set `ARTEMIS_TRIAL_PORT` for another local port. Set `ARTEMIS_TRIAL_USERNAME` and `ARTEMIS_TRIAL_PASSWORD` if the copy uses
different local administrator credentials.

Release CI runs the same check on a fresh trial Compose stack with the published release tag. To
check a specific published image locally, set `ARTEMIS_TRIAL_IMAGE` to its full image reference
before running the Compose commands above.

## What you can do with it

The first start creates the database schema, so give it a moment. Once Artemis reports itself started,
you have a complete instance:

- **Programming exercises.** Create one and Artemis provisions the template, solution, and test
  repositories on its own git server. Students participate, push commits, and the build agent runs the
  tests in a container and reports feedback. The online code editor, manual code review, and
  submission policies are all part of this setup.
- **Every other exercise type.** Quiz, text, modeling, and file upload, with manual assessment against
  structured grading criteria.
- **Exams.** Including exercise variants per student and instructor test runs.
- **Courses, lectures, competencies, learning paths, communication channels, and FAQs.**

The setup starts one build agent with four concurrent build slots, which is enough to feel how the
feedback loop behaves. Production deployments scale this out horizontally.

<Callout variant={CalloutVariant.info}>
    The build agent pulls a language-specific Docker image the first time an exercise of that language
    is built, so the very first build takes noticeably longer than the ones after it, and it needs
    working network access to the image registry. If a build does not appear, look at **Server
    Administration → Build Agents** and the build queue: the agent has to be listed and reachable, and
    it needs access to the Docker socket that the Compose file mounts for it.
</Callout>

## What it deliberately leaves out

- **AI features.** Iris, Athena, and Hyperion are optional integrations and need a configured model
  provider. See [Artemis Intelligence](/admin/artemis-intelligence).
- **External authentication.** The trial uses internal accounts. LDAP, SAML2, and OIDC are configured
  per deployment.
- **Mail.** Notification emails need an SMTP server; [Mailpit](/developer/mailpit-setup) is the local
  option.

<Callout variant={CalloutVariant.danger}>
    This is a trial setup, not a deployment. It runs the development profile with the credentials
    published in this repository, and it gives the container access to your Docker socket so the build
    agent can start containers. Never expose it to a network you do not control. For a real deployment,
    follow the [administrator guide](/admin/intro); the production profile refuses to start until you
    replace those credentials with your own.
</Callout>

## Simpler variant, without programming exercises

If you do not need programming exercises, or you would rather not mount the Docker socket, this one is
smaller and needs no group configuration:

```bash
docker compose --env-file .env -f deployment/docker/artemis-dev-postgres.yml up
```

## Ask for a hosted trial

If you would rather not run anything, or your institution is too small to operate its own instance,
the Artemis team at TUM can host one for you. This is intended for schools and for institutions
evaluating Artemis before committing to their own infrastructure.

Write to [artemis@xcit.tum.de](mailto:artemis@xcit.tum.de).

## Deploy it properly

When the trial has answered your questions:

- [Administrator guide](/admin/intro) for production setup, security, scaling, and operations.
- [Integrated code lifecycle setup](/admin/production-setup/integrated-code-lifecycle-setup) for
  running programming exercises in production, including separate build agents.
- [Artemis Ansible Collection](https://github.com/ls1intum/artemis-ansible-collection) automates a
  production deployment and is the recommended path.
- [Docker Compose setups](/developer/docker-compose) documents every Compose file in the repository.
- [Trust and transparency](./trust) answers the security, privacy, accessibility, and AI questions that
  come up in an institutional review.

If you want to change Artemis rather than only run it, start with the

with hot reload.
