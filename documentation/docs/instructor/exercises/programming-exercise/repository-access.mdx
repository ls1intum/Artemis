Who may read or write which repository depends on three things: the kind of repository, the role of the user, and where you are in the exercise timeline. The tables below spell out every combination, and the last section covers how to see who actually accessed a repository.


If you are a student looking for repository access information, see the [student documentation on integrated code lifecycle setup](/student/tools-reference/integrated-code-lifecycle).

The following sections explain repository types and access rights for different user roles.

## Repository Types

| Repository Type               | Description                                                                                                  |
|-------------------------------|--------------------------------------------------------------------------------------------------------------|
| Base                          | Repositories set up during exercise creation (template, solution, tests, auxiliary repositories)             |
| Student Assignment            | Student's assignment repository copied from template. Includes team assignments                              |
| Teaching Assistant Assignment | Assignment repository created by a Teaching Assistant for themselves                                         |
| Instructor Assignment         | Assignment repository created by editor/instructor. Not available for exam exercises                         |
| Student Practice              | Student's practice repository (from template or assignment). Created after due date. Not available for exams |
| Teaching Assistant Practice   | Practice repository created by Teaching Assistant. Not available for exams                                   |
| Instructor Practice           | Practice repository created by editor/instructor. Not available for exams                                    |
| Instructor Exam Test Run      | Test run repository for exam testing before release. Should be deleted before exam                           |

## User Roles

| Role               | Description       |
|--------------------|-------------------|
| Student            | Course student    |
| Teaching Assistant | Course tutor      |
| Editor             | Course editor     |
| Instructor         | Course instructor |

<Callout variant={CalloutVariant.info}>

  Editors and instructors have the same access rights in the table below.

</Callout>

## Time Periods

- **Before start**: Before exercise/exam start date
- **Working time**: After start date, before due/end date
- **After due**: After due/end date

<Callout variant={CalloutVariant.info}>

  For Instructor Exam Test Run, "Before start" is the test run start date and "After due" is the test run end date (both before exam start).

</Callout>

**Read access (R)** includes `git fetch`, `git clone`, `git pull`.
**Write access (W)** corresponds to `git push`.

## Who Accessed a Repository

Artemis records every fetch and push to a repository, which is useful when you need to establish what a participant actually did — for example when investigating a suspected exam irregularity or a disputed submission time.

Open the repository from **Course Management** and click **Open Access Log**. Each entry shows:

| Column | Meaning |
|--------|---------|
| User Id | The internal id of the account that accessed the repository |
| Author | The name and email of the Artemis account, not the author on the Git commit. For an access by a build agent it names the agent and job instead |
| Action Type | Clone, pull (a fetch of an existing clone), or push for an operation that transferred data. A rejected attempt is shown as a failed clone or push |
| Access Type | How the user authenticated, for example over HTTPS with a token, or over SSH with a key |
| Commit Hash | For a push, the commit that was pushed. For a clone or pull, the newest commit of the repository when the data was sent. For a failed push, the commit the repository still has. For a failed clone or pull, empty |
| Timestamp | When the access happened |

Every clone, pull, and push is recorded as exactly one entry, whether it runs over HTTPS or over SSH, and an entry is never changed afterwards. It is written when the operation is over, so it holds everything known by then:

- A fetch that transferred data is a **clone** if the client had nothing yet and a **pull** otherwise.
- A push is a **push** with the pushed commit if the repository accepted it. If the server refused it, for example because it went to a branch that is not allowed, it is a **failed push** with the commit the repository still has. An accepted push keeps its commit even if Artemis then creates no submission from it, as for a push to another branch. The log shows what reached the repository, not what was graded.
- An attempt that was rejected is a **failed clone** or **failed push**: credentials that do not hold, an account that is not active, a participant who may not access the repository, or the use of an offline IDE where it is not allowed. It names the account that was tried and the repository.

Some git commands move no data and are not operations of their own, so they leave no entry: a fetch that is up to date, a push with nothing new, listing the references of a repository, and the first request of every operation, which carries no credentials because git waits to be asked for them. The log is therefore a record of what was transferred, and of attempts that were rejected. It is not a record of every request to the server: an attempt can only be attributed to an account and repository if both can be identified, so a wrong user name, a rejection by the rate limit, and an SSH key that is not accepted, which happens before the repository is named, leave no entry.

An HTTPS build-agent clone authenticated with a build-job token records one **pull** entry, identifying the agent and job.

The log shows the newest accesses first. Click a column heading to sort by user, author, action, access type, or timestamp. Use the search field above the table to find entries by user, author, action, access type, commit hash, or date. Search dates in `YYYY-MM-DD` format using your local calendar date.

Use the pagination controls below the table to change pages or the number of entries per page. The column headings and pagination remain visible while the entries scroll. On narrow screens, scroll the table horizontally to reach the remaining columns.
