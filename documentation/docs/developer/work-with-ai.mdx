Artemis [agent skills](https://github.com/ls1intum/Artemis/tree/develop/skills) provide
repository-specific procedures for testing, CI, migrations and development.

## Shared instructions and task-specific skills

[`AGENTS.md`](https://github.com/ls1intum/Artemis/blob/develop/AGENTS.md) contains shared rules
and links to skills. [Codex](https://developers.openai.com/codex/guides/agents-md) reads it directly.
`CLAUDE.md` contains only `@AGENTS.md`, so Claude Code loads the same rules through its
[documented import](https://code.claude.com/docs/en/memory#share-one-file-with-other-coding-tools).
Do not copy the rules into `CLAUDE.md` or import the skills there.

[Claude Code can also read `AGENTS.md` directly](https://code.claude.com/docs/en/memory#agents-md),
but versions before 2.1.281 could silently skip it when telemetry was disabled or the session
used Bedrock. The import keeps the shared rules available in those sessions without requiring
telemetry. In Claude Code, use `/memory` or `/context` to check which instruction file loaded.

Skill discovery exposes names and descriptions; the agent reads a selected `SKILL.md` and its
references as needed. Ordinary Markdown links do not install skills or import their contents.
They let an agent read the checked-in procedures without installation. Do not `@`-import
skills into an instruction file: imports load at startup rather than on demand. See the
[Agent Skills specification](https://agentskills.io/specification) and
[Codex skill documentation](https://developers.openai.com/codex/skills) for discovery behavior.

## Installing

### Skills CLI

```bash
npx skills add ls1intum/Artemis
```

Select your agent in the [skills CLI](https://github.com/vercel-labs/skills#supported-agents).
Installation locations and invocation syntax depend on the agent.

### Claude Code

For Claude Code, prefer the namespaced plugin over the Skills CLI:

```text
/plugin marketplace add ls1intum/Artemis --scope local
/plugin install artemis@artemis --scope local
```

The local scope enables the plugin only in this checkout, without shared settings changes.
The plugin distributes skills, not repository memory files. Installing it in another repository
does not load Artemis's `AGENTS.md`.

The skills then appear as `/artemis:e2e-pr-check`, `/artemis:ci-triage`, and so on. Claude can also
select them automatically from their descriptions; selection is not guaranteed.

Use one installation method per agent to avoid duplicate skill entries. Plugin names such as
`/artemis:ci-triage` distinguish these skills from personal skills with the same short name.

### Working on the skills themselves

```bash
claude --plugin-dir .
```

Run from the repository root to load this checkout rather than an installed copy. For Codex:

```bash
npx skills add . --agent codex --skill '*' --copy --yes
```

This installs every skill from the working tree. Repeat after editing them to refresh the
installed copies. Local skill files and `skills-lock.json` are ignored by Git; edit `skills/`,
not `.agents/skills/`. Use `npx skills list --agent codex` to check discovery.

## Checking skill behavior

Use a fresh agent session after changing shared instructions. In Claude Code, inspect `/memory`
or `/context` to confirm that `CLAUDE.md` loaded and imported `AGENTS.md`. In Codex, ask which repository instructions and skills are
available. When testing edits to a skill, confirm the agent reads this checkout rather than an
older installed copy; `claude --plugin-dir .` loads the working plugin directly.

Compare representative tasks before and after an instruction change with the same model,
settings and repository state. Include both matching tasks and tasks that should not use a skill:

| Request                                         | Expected behavior                                                                                          |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Fix a typo in documentation                     | No server, client or E2E procedure is needed                                                               |
| Migrate an Angular component to signal inputs   | Use `client-conventions`; load migration examples when needed                                              |
| Add a Vitest regression test                    | Use `write-tests` and its client reference, not the server reference                                       |
| Explain why a CI check never started            | Use `ci-triage`, not a speculative code fix                                                                |
| Add a NOT NULL database constraint              | Use `liquibase-migration` and check data and rollback requirements                                         |
| Run affected E2E tests with uncommitted changes | Use `e2e-pr-check`; disclose the resolver's committed-diff limitation without making an unsolicited commit |

Record which files were loaded, whether the task succeeded, the checks run and unnecessary work.
Skill selection is model-dependent: a valid file or a successful path check does not prove useful
routing or better outcomes. Skill instructions do not grant permission to commit, deploy or alter services.

## Contributing a skill

A skill is a directory under `skills/` with a `SKILL.md` and optional `reference/` files:

```text
skills/
  my-skill/
    SKILL.md
    reference/background.md
```

```markdown
---
name: my-skill
description: What it does and when to use it, key use case first.
---

# Title

The procedure.
```

Use a short description of the task that should trigger the skill, not a contents list or promise
of success.

1. **Cite repository paths for non-obvious facts.**
   [`supporting_scripts/check_skill_references.py`](https://github.com/ls1intum/Artemis/blob/develop/supporting_scripts/check_skill_references.py)
   runs in the `Agent Skills` CI job. It checks recognized path-shaped tokens in inline code
   and fenced blocks, not every Markdown link or the truth of the surrounding claim. Review
   linked files and command behavior separately.
2. **Route the new skill.** The same check requires a link from `AGENTS.md` and from the
   [skill table](#the-skills) above, so agents reach the skill without installing anything.
   It also rejects frontmatter that agents cannot index: the `name` must match the directory
   and the `description` must be present.
3. **Keep the body focused.** Put substantial conditional detail in linked `reference/` files.
4. **Explain non-obvious constraints.** Include the reason when it prevents a plausible but incorrect alternative.
5. **Do not duplicate `AGENTS.md` or other skills.** Keep shared constraints in the entry point,
   procedures in the matching skill, and conditional detail in linked references. Preserve
   non-obvious Artemis constraints rather than deleting them to meet a line-count target.

Validate the files and run the [behavioral checks](#checking-skill-behavior):

```bash
python3 supporting_scripts/check_skill_references.py
python3 supporting_scripts/check_skill_references.py --self-test
claude plugin validate .
claude plugin validate .claude-plugin/plugin.json
```

When publishing skill changes, bump `version` in `.claude-plugin/plugin.json` in the same pull
request. Claude Code uses that version to identify updates; unchanged versions can leave users
on cached instructions. After merging, plugin users can run `/plugin marketplace update artemis`
and `/plugin update artemis@artemis --scope local`, then restart Claude Code. See [plugin version management](https://code.claude.com/docs/en/plugins-reference#version-management).

Update the skill when its cited code or convention changes.
