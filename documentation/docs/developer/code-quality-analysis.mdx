Artemis enforces code quality in CI and publishes its code quality ratings through SonarQube Cloud.

**The enforcing checks are the ones in this repository.** A pull request cannot merge until
`ci-quality.yml` and `ci-test.yml` are green, and between them they run Spotless, Checkstyle,
Modernizer, the ArchUnit architecture rules, the dependency-family guard, ESLint with the custom
rules in `config/eslint/rules/`, Prettier, Stylelint, the TypeScript compiler, the Playwright lint and type-check,
the large-class and complex-bean ceilings in `supporting_scripts/analyze_java_files.py`, the
over-fetch detector in `supporting_scripts/find_slow_queries.py`, and the per-module coverage floors
in `gradle/jacoco.gradle`. This is where a quality problem actually stops you.

The [SonarQube Cloud](#sonarqube-cloud) new-code quality gate is also required for relevant ready pull requests.

## Codacy

Artemis has disabled Codacy status checks and cloud analysis. The repository dashboard shows the
last available analysis. [Codacy dashboard](https://app.codacy.com/gh/ls1intum/Artemis/dashboard?branch=develop)

If Codacy is re-enabled, it will read the retained `.codacy.yaml`. The file defines repository-wide
`exclude_paths` for every engine and adds narrower exclusions for individual engines. Tools are
enabled in Codacy Cloud, so a newly enabled engine inherits the repository-wide exclusions.

## SonarQube Cloud

SonarQube Cloud analyzes the deployed application, with the server and client in one project. Its
**new-code quality gate is a required pre-merge check** for relevant ready pull requests. Scanner,
upload, timeout and quality-gate failures fail **All required CI Passed**. Its ratings appear as
badges in the root `README.md`.

The analysis runs from `.github/workflows/ci-sonar.yml`, called from `ci.yml` after the test jobs, importing the
JaCoCo and LCOV reports they already uploaded, so no test suite is re-run. All configuration lives in
`gradle/sonar.gradle`. The [workflow reference](https://github.com/ls1intum/Artemis/blob/develop/.github/workflows/README.md#the-code-quality-analyses)
describes the policy, including fork pull requests and recovery.

### Getting a grade on demand

A full CI run takes a long time because of the end-to-end tail. To get a grade without waiting,
dispatch the workflow directly from the **Actions** tab, or from the command line by naming the ref
you want analysed:

```bash
gh workflow run ci-sonar.yml --ref develop
```

The dispatch takes two optional inputs: `analyze_default_branch` analyzes the repository's default branch with the
selected workflow revision (recovery mode), and `pull_request_number` scans reviewed code that was promoted to an
internal `chore/sonar/pr-<number>` branch, where `0` analyzes the selected ref. A dispatched run has no `test` job
whose coverage artifacts it could import, so unless it can reuse verified coverage of the same revision it reports
no coverage. The ratings and issue counts still come back. For coverage, use the analysis of a complete CI run.

### Running it locally

Analysis uploads to SonarQube Cloud and therefore needs a token. Nothing wires `sonar` into `check`
or `build`, so an ordinary local build never contacts the service.

```bash
export SONAR_TOKEN="paste-your-token-here"
./gradlew compileJava sonar -x webapp
```

To inspect the configuration without contacting the service at all, dump the computed properties:

```bash
./gradlew compileJava sonar -Dsonar.scanner.internal.dumpToFile=/tmp/sonar-props.txt -x webapp
grep -E '^sonar\.(sources|exclusions|java\.binaries)' /tmp/sonar-props.txt
```

Keep `compileJava` in that command even though it dumps rather than analyzes. Without it the run
reproduces the degraded configuration described below instead of the real one, and
`sonar.java.binaries` — one of the properties the `grep` asks about — is simply absent.

### Two things to know before changing it

**Sonar scans the roots listed in `sonar.sources`.** The exclusions in `gradle/sonar.gradle` omit
exercise templates, test code and specs, Storybook stories, `supporting_scripts`, and the local
OIDC test provider. The historical Codacy analysis used similar exclusions and also covered
supported repository tooling outside the Sonar source roots.

**`compileJava` is required, not an optimization.** Sonar's Java analyzer needs bytecode. The Gradle
plugin derives `sonar.java.binaries` from the main source set's output directory, but only if that
directory already exists — with no prior compile the property is omitted and the Java half of the
analysis degrades without reporting an error. This is why the CI job and the commands above compile
first. `-x webapp` skips the Angular production build, because Sonar analyzes the TypeScript sources
rather than the bundled output.
