`@tumaet/ui-angular` is the reusable component package for the in-house TUM UI design system.
Artemis production builds consume its compiled public entry point and stylesheet.

<Callout variant={CalloutVariant.info}>
    TUM UI is the target component system for Artemis. Bootstrap, ng-bootstrap, and PrimeNG are migration-only dependencies. Use an existing TUM UI component whenever it covers the
    requirement.
</Callout>

Use the [TUM UI component reference](/developer/tum-ui-reference) to inspect
supported states, controls, accessibility results, and APIs. This guide covers package architecture
and contribution rules.

## Ownership boundary

Package code:

- imports only its declared dependencies;
- exposes supported contracts through `src/public-api.ts`;
- uses package-owned translation keys and `--tumaet-ui-*` theme properties;
- contains no Artemis routes, services, Artemis-owned theme properties or translation keys, or
  request models.

Artemis-specific adapters live in `src/main/webapp/app/shared-ui/tum-ui-integration`. Artemis
imports package symbols from `@tumaet/ui-angular`; ESLint rejects deep imports.

The package has its own version and GitHub release notes. Repository code owners review its public contract;
npm organization maintainers approve releases.

## Adding or changing a component

Follow the [component decision order](/developer/guidelines/client-development#ui-components). A
new package API needs a reusable design-system responsibility and a concrete Artemis consumer;
keep application policy in Artemis. Document unsupported public behavior beside the API declaration.

Package components use standalone declarations, signal APIs, `ChangeDetectionStrategy.OnPush`,
native input coercion, and semantic Tailwind utilities. Prefer stable native controls and CDK
behavior over custom keyboard, focus, overlay, or selection machinery.

Tests should assert public behavior: accessible role and name, keyboard interaction, focus changes,
disabled behavior, emitted values, and forms integration. Avoid tests that restate implementation
details or static class maps.

### Stories

Colocate each top-level consumer story with its component or directive. Document supporting pieces
of a composite API, such as tab panels or sortable columns, as subcomponents of that story. Use the
package's [CSF3 format](https://storybook.js.org/docs/api/csf) with `Meta`, `StoryObj`, and
TypeScript's `satisfies` operator. Type component stories with the component or explicit story args.
Keep configuration in `packages/tum-ui/.storybook`; do not add root Storybook configuration or
import Artemis into a story.

Prefer an args-driven default story and only the additional states that expose a meaningful visual
or behavioral contract. Let Storybook render the component directly when inputs and outputs are
enough. Use an Angular template only when the public contract requires projection, a directive host,
forms, a `TemplateRef`, or compound components. Use args for initial state and Controls. Keep
interaction state in Angular bindings when a transition depends on preserving the rendered element;
updating Storybook args rerenders an inline AutoDocs story.

Stories should provide the minimum realistic context needed to understand the contract. A
presentation wrapper may arrange an example but must not repair or restyle the component. Expose
meaningful serializable controls; keep callbacks, templates, and framework objects read-only.
Source JSDoc is the canonical description for non-obvious inputs and outputs. Test compact, narrow,
dark, reduced-motion, or right-to-left conditions only when they affect the contract.

Add a `play` function for browser-only behavior such as focus, keyboard navigation, overlays, or
dismissal. Hide a tested story from the sidebar and AutoDocs only when the interaction is valuable
but its final state is not a useful reference; do not create hidden duplicates of unit tests. Query
by accessible role and name. Do not assert CSS classes, duplicate unit-test matrices, add snapshots,
or disable accessibility rules to make a story pass.

## Consuming the package

Import only from the package root:

```ts
import { TumUiButtonComponent, TumUiDialogComponent } from '@tumaet/ui-angular';
```

Storybook AutoDocs derives the component API from those declarations and their source JSDoc.
Document non-obvious public behavior beside the declaration; do not maintain separate input and
output tables.

Artemis declares the package through pnpm's `workspace:*` protocol. Application builds and Artemis
tests consume `packages/tum-ui/dist`; their root commands build the package first. Development serve
mode maps the package entry point to its source so changes participate in Angular's normal watch and
reload cycle.

### Theme contract

The [package README](https://github.com/ls1intum/Artemis/blob/develop/packages/tum-ui/README.md)
documents stylesheet loading, token semantics, dark mode, and host styling.

Artemis loads `@tumaet/ui-angular/styles.css` after application styles. Its unlayered stylesheet
overrides the package's font family, brand, application surfaces, and status roles. Its Tailwind
configuration owns application utilities. Set `data-theme="dark"` on the document element for dark
mode; the package theme also sets the matching CSS `color-scheme` for browser controls.

Treat package token names and responsive thresholds as public styling contracts. Add a token only when a host needs a supported customization
axis; do not expose Tailwind's full primitive theme.

Apply application layout classes directly to the component host with the native `class` attribute.
Do not add `styleClass`-style compatibility inputs or expose internal element classes. Add a
semantic input or theme token only when the customization is a supported component contract.

### Translation contract

Package-owned text uses `tumUi.*` keys and has English defaults. A host can implement
`TumUiTranslator` and register it once:

```ts
providers: [provideTumUiTranslator(ApplicationTranslator)];
```

The adapter's `translationChanges` signal invalidates translated views, and its `locale` signal
controls locale-sensitive formatting. Artemis registers `provideArtemisTumUiTranslator()` in
`app.config.ts`; its key mapping belongs in `app/shared-ui/tum-ui-integration`, not in the package.

## Local workflow

After installing workspace dependencies, install Chromium for browser tests. Repeat this after
upgrading Playwright:

```bash
pnpm --dir packages/tum-ui exec playwright install --with-deps --only-shell chromium
```

Run focused commands while developing:

| Command                                         | Purpose                                                                   |
| ----------------------------------------------- | ------------------------------------------------------------------------- |
| `pnpm run tum-ui:test`                          | Run package unit tests with Angular's Vitest runner                       |
| `pnpm run tum-ui:test:coverage`                 | Run package specs with the CI coverage thresholds                         |
| `pnpm run tum-ui:pack:check`                    | Build and validate an isolated artifact with publint and AreTheTypesWrong |
| `pnpm run tum-ui:source:check`                  | Build Artemis against the package source entry point                      |
| `pnpm --dir packages/tum-ui run storybook`      | Build package styles and start its isolated Storybook                     |
| `pnpm --dir packages/tum-ui run storybook:test` | Run stories and accessibility checks in Chromium                          |
| `pnpm run docs:test`                            | Build the combined documentation and test its navigation and themes       |

Before submitting a package change, run the complete validation from the repository root:

```bash
pnpm run tum-ui:validate
```

`pnpm start` and the shared IntelliJ client configuration first build `packages/tum-ui/dist` for
editor resolution, then serve package sources. Restart the client after changing the package
manifest or build configuration. Production builds consume `packages/tum-ui/dist`; package
validation writes to `packages/tum-ui/dist-pack`.

Published peer ranges start at the workspace catalog versions; `pnpm run test:rules` checks this
alignment. External consumer tests install the tarball outside the workspace with strict peer
resolution, build an Angular production application, and exercise forms, icons, dialog focus, and
theme overrides in Chromium. CI tests minimum and latest compatible peers. Server-side rendering
is not supported.

```bash
pnpm run tum-ui:pack:check
pnpm run tum-ui:test:consumer minimum
pnpm run tum-ui:test:consumer latest
```

`pack:check` writes the validated tarball and its integrity metadata to `build/tum-ui-package`.
Consumer failures retain the npm manifest, resolved lockfile, and browser diagnostics under
`build/test-results/tum-ui-consumer`; CI uploads these as artifacts.

## Publishing to npm

TUM UI uses independent versions and the **Release TUM UI** workflow (`release-tum-ui.yml`).
A manual run validates without publishing. A `tum-ui-v<version>` tag stages a release when it
matches the package version and its commit is reachable from `develop`.

The external consumer installs the tarball outside the workspace. Artemis tests integration, but
its local aliases and shared dependencies can hide missing published files or dependencies.
The workflow validates the package and both external consumer configurations before staging the
tested tarball. npm publication requires a maintainer's 2FA approval.

### One-time setup and first release

Merge the workflow into `develop` before setup; GitHub enables manual dispatch only after it
exists on the default branch.

1. Give the release maintainers access to the `@tumaet` npm organization and require 2FA.
2. Protect `develop` with required CI and code-owner review. Restrict creation of `tum-ui-v*` tags
   to release maintainers and prevent tag updates and deletion.
3. Create the GitHub environment **npm-tum-ui**, restricted to `tum-ui-v*` tags.
4. Create the first annotated `tum-ui-v<version>` tag at the reviewed commit on `develop`.
   Temporarily [disable the workflow](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows)
   while pushing this first tag: npm cannot authenticate the publisher until the package exists.
   Replace `<version>` with the version in `packages/tum-ui/package.json`.

    ```bash
    gh workflow disable release-tum-ui.yml
    git push origin tum-ui-v<version>
    gh workflow enable release-tum-ui.yml
    gh workflow run release-tum-ui.yml --ref tum-ui-v<version>
    ```

    Re-enable the workflow even if the tag push fails. The manual run validates the tagged commit
    without staging. After all jobs pass, download its `tum-ui-package` artifact and extract it.
    Compute the tarball's SHA-512:

    ```bash
    openssl dgst -sha512 -binary ./tumaet-ui-angular-<version>.tgz | openssl base64 -A
    ```

    Compare this with the value after `sha512-` in the `pnpm run tum-ui:pack:check` step log.
    Publish that tarball using interactive authentication:

    ```bash
    npm login
    npm publish ./tumaet-ui-angular-<version>.tgz --ignore-scripts --access public
    ```

    npm requires an existing package for staging. The first local publication has no CI-generated
    provenance.

5. In npm's package settings, add a GitHub trusted publisher with organization **ls1intum**,
   repository **Artemis**, workflow **release-tum-ui.yml**, and environment **npm-tum-ui**.
   Allow **stage publish** only. Select **Require two-factor authentication and disallow tokens**
   under publishing access. Do not add an npm publishing token to GitHub secrets.
6. Create GitHub release notes for the existing tag as described below.

[Trusted publishing](https://docs.npmjs.com/trusted-publishers/) generates provenance for the
public package and repository. [Staged publishing](https://docs.npmjs.com/staged-publishing/)
requires npm 11.15 or newer. Use the Node version in `.nvmrc`, including for the first local
publication. Trusted-publisher fields are case-sensitive.

### Subsequent releases

Update the version from `packages/tum-ui` with `npm version <version> --no-git-tag-version --ignore-scripts`.
Before 1.0, incompatible API, token, or peer-minimum changes increment the minor; compatible fixes and additions
increment the patch. After 1.0, breaking changes increment the major.
Document migrations instead of adding compatibility aliases.

Merge the validated change into `develop`, then push an annotated `tum-ui-v<version>` tag at that
commit. All releases target `latest`. Omit an explicit `--tag` so npm retains its built-in
[protection against staging older versions](https://docs.npmjs.com/cli/v11/commands/npm-stage/#tag-behavior).

After the workflow succeeds, inspect the staged package's version, content, and provenance commit
on npm, then approve with 2FA using the website or `npm stage approve <stage-id>`. Confirm the
published version, then create a GitHub release for its existing tag. Write TUM UI-specific notes
covering consumer-visible changes and any migration steps; repository-wide generated notes also
include unrelated Artemis changes. Use
[`gh release create tum-ui-v<version> --verify-tag --latest=false`](https://cli.github.com/manual/gh_release_create)
so release creation requires the existing tag and preserves the latest Artemis release. TUM UI
release events are excluded from Artemis's application release and Android test workflows.

Staging success does not mean the package is public. Before retrying an interrupted run, inspect
`npm stage list @tumaet/ui-angular`; the upload may already have succeeded. Published versions are
immutable. Fix a bad release with a new version, deprecate the affected version, and restore the
previous dist-tag if necessary. Do not move release tags or overwrite versions.
