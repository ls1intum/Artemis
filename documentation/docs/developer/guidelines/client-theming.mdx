Artemis supports light and dark themes. The active scheme is exposed as
`data-theme="light"` or `data-theme="dark"` on the document element so application styles, TUM AET UI,
and embedded content share one framework-neutral signal.

<Callout variant={CalloutVariant.danger}>
    Verify every visual change in light and dark mode. Do not hard-code colors in component stylesheets, templates, or TypeScript. Do not introduce Bootstrap, PrimeNG, or
    package-owned color properties as a shortcut.
</Callout>

For design intent and accessibility requirements, follow the
[AET UI/UX color guidelines](https://ls1intum.github.io/ui-ux-guidelines/docs/colors). This page
documents how Artemis implements those decisions.

## Theme architecture

The theming boundary has four layers:

1. The light and dark SCSS variable files define Artemis semantic roles and compile them to CSS
   custom properties.
2. `src/main/webapp/tailwind.css` exposes selected roles as semantic Tailwind utilities.
3. The same file maps Artemis foundations and color roles to the public `--tumaet-ui-*` contract.
   TUM AET UI components consume only that package-owned contract.
4. Bootstrap and PrimeNG receive compatible values while they remain in the application. They are
   migration consumers, not the source of Artemis design decisions.

This keeps one semantic source of truth while allowing legacy frameworks to leave independently.
Do not reference Artemis properties from package source, and do not reference `--tumaet-ui-*`
directly from application components. Change the host mapping when a package-wide theme decision
changes.

## Choosing styles

Use the first suitable option:

1. **TUM AET UI component input or variant.** Use `severity`, `variant`, `size`, and other supported
   contracts instead of overriding component internals.
2. **Semantic Tailwind utility.** Use one when Artemis owns the mapping, such as
   `text-state-danger`. PrimeUI surface scales are not Artemis design tokens.
3. **Artemis semantic CSS property.** Use an existing role in component SCSS or an irreducible
   dynamic style when a utility cannot express the requirement.
4. **New semantic role.** Add one only when the concept recurs and no existing role has the correct
   meaning. Define both light and dark values and expose it to TUM AET UI only when it is a supported
   package customization axis.

<Callout variant={CalloutVariant.warning}>
    A raw palette value describes appearance, not intent. Do not use hexadecimal values, numbered Tailwind colors, `--p-*`, or `--bs-*` in new component code. Reusing an unsuitable
    token because its current color looks right is also incorrect.
</Callout>

Common Artemis roles include:

| Intent                       | Artemis role                                                              |
| ---------------------------- | ------------------------------------------------------------------------- |
| primary action and link      | `--primary`, `--primary-dark`                                             |
| default and muted text       | `--body-color`, `--text-body-secondary`                                   |
| content and overlay surfaces | `--module-bg`, `--popover-bg`, `--hover-slightly-darker-body-bg`          |
| border                       | `--border-color`                                                          |
| state                        | `--danger`, `--success`, `--warning`, `--info`                            |
| state message                | `--artemis-alert-{danger,success,warning,info}-{color,background,border}` |

Use the `state-*` Tailwind utilities for state-colored plain markup:

```html
<small class="text-state-danger" id="title-error"> {{ 'entity.validation.required' | artemisTranslate }} </small>
```

Use TUM AET UI for a component-shaped status:

```html
<tumaet-ui-message severity="error"> {{ 'entity.validation.required' | artemisTranslate }} </tumaet-ui-message>
```

Color must never be the only signal. Pair a state color with text, an icon, or another programmatic
cue as required by
[WCAG 1.4.1](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html).

## Button intent and hierarchy

Use TUM AET UI `severity` for an action's established functional category, and `variant`, placement,
and grouping for its emphasis. Exercise management already uses a richer scheme than blue primary
and neutral secondary actions. Keep the same action recognizable in the course list, exam exercise
groups, and exercise details.

| Action category | Severity | Examples in exercise management |
| --- | --- | --- |
| Main workflow, work-area navigation, and creation | `primary` (blue) | Create Exercise, Participations, Teams, quiz Batches, Add Batch; ordinary Save actions |
| Authoring, configuration, and changes requiring attention | `warn` (yellow) | Edit, Edit in Editor, Grading, Edit Build Plan, Iris Settings, Create Variant, Edit Selected, Evaluate and Re-evaluate Quiz, Show Quiz Now |
| Analytics and assessment | `info` (cyan/teal) | Statistics, Assessment Dashboard |
| Data transfer | `secondary` (neutral gray) | Import, Export, Export Results, Download Repository, Download Example Solution |
| Preview, reference material, and positive execution or activation | `success` (green) | Quiz Preview, Quiz Solution, Example Submissions, Start Quiz, Start Batch, Activate Submission Policy |
| Destructive, interrupting, or consequential bulk operation | `danger` (red) | Delete, reset participations, discard work, End Quiz Now, Re-evaluate All, Trigger All student builds |
| Supporting utilities and overflow controls | `secondary` (neutral gray) | More actions, deselect, cancel; repository history, access log, Code |

Yellow authoring controls, cyan analysis controls, and green preview/reference controls are
established action families. The color identifies the category of the action: green Preview opens a
preview, and yellow Edit opens an editing workflow. Status messages, result icons, tags, and validation
feedback retain their usual success, warning, error, and information meanings. Color is accompanied
by the action label and icon.

For a new action, first check its counterpart in the list, details, and exam context. Use that action
family rather than choosing a different color because one page presents it as navigation and another
presents it as a prominent button. Use blue for a new main workflow action and neutral for an ordinary
supporting utility when no established family applies. Opening Edit is yellow; saving the form is a
separate primary action. Keep destructive actions red even when they are secondary in the layout.
The impact of an operation takes precedence over its general family: the programming grading page
uses red for Re-evaluate All and Trigger All because they affect student results or run builds for
the whole exercise. This differs from opening a yellow configuration or quiz re-evaluation workflow.

Multiple blue navigation actions can appear together in an exercise-management toolbar. For forms
and dialogs, prefer one main primary action and neutral alternatives. Equivalent utility actions share
the same severity and variant: the repository toolbar uses neutral **Open Commit History**, **Open
Access Log**, **Code**, and **Download Repository**, all at the same small size. Transfer is a distinct
functional category that shares gray with other supporting utilities. Labels and import/export/download
icons identify the operation. On exercise details, **Participations** remains blue,
**Statistics** cyan, and **Edit** yellow according to their action families.

Here, neutral means the `secondary` button's gray-toned background and theme-appropriate foreground:
dark text in the light theme, light text in the dark theme. It is an enabled supporting action.
Disabled state is a separate behavior, conveyed by disabled semantics and reduced emphasis; a gray
button alone does not mean the action is unavailable.

Use `variant="outlined"` or `variant="text"` to reduce emphasis without changing the action family.
For example, Check Consistency uses an outlined primary action, Version History is a link, and Suggest
Competencies uses a text action. Lighter/darker blue shades, outlines, and disabled styling are not
additional action categories. Use `contrast` only when the surrounding surface requires the inverse
theme treatment. Ordinary menu entries follow the menu component's presentation; moving an action
into More actions does not require a colored button inside the menu.

### Coverage and contextual differences

The course list's `ExerciseActionsComponent` and the exam list's `ExamExerciseRowButtonsComponent`
define matching colors for Participations/Teams, Edit/Edit in Editor/Create Variant, quiz
Statistics/Preview/Solution/Re-evaluate, Example Submissions, and Delete. The programming details,
`NonProgrammingExerciseDetailCommonActionsComponent`, and `QuizExerciseManageButtonsComponent`
retain these categories. `QuizExerciseLifecycleButtonsComponent` is shared by the course list and
quiz details, keeping Start green, Show Now yellow, and End Now red in both locations.

The source comparison also includes the course list's title, bulk and group controls; detail-page
repository/build controls and Administration; and representative exercise forms, grading controls,
and the assessment dashboard. It is a source audit of these workflows, not an application-wide visual
audit.

Some labels need their context to determine the category:

- **Import, export, and download:** standalone buttons use gray (`secondary`) for data transfer,
  including dialog launchers, result/report exports, and repository archive downloads. Reserve cyan
  for opening analytics and assessment views. Use the same transfer styling in the course list and
  details. Quiz Export inside
  More actions retains the menu component's presentation. Save or Confirm buttons keep the role of
  their form or dialog rather than inheriting the launcher's color automatically.
- **Start or retry:** starting a quiz or batch is green. The programming build trigger normally uses
  primary blue. Its existing failed-submission recovery state uses red; this is a specific existing
  exception, not a rule that new retry buttons should be red. Show errors in status feedback and keep
  an ordinary recovery action primary or secondary.
- **Preview or assess:** opening reference examples from exercise management is green. Starting a
  tutor's assessment workflow can be a primary action on the assessment dashboard.
- **Reset:** resetting student participations is destructive and red. The code-analysis grading
  table currently has a neutral Reset button even though it calls the server to reset categories.
  Review that existing exception with the grading workflow; use the actual effect of a reset to
  decide its severity, including whether saved work is replaced.

When changing a complete action group, preserve these shared meanings and resolve differences for
the same action together. Avoid a broad recoloring of established workflows as a side effect of a
single toolbar change.

Use `size="small"` consistently within compact toolbars, including nested Code and download controls.
Match the sizes within an existing form action group; the default size suits new standalone actions.
Keep sufficient space between controls, allow the
group to wrap on narrow screens, and retain accessible names when a visible label collapses to an icon.
The existing `jhi-button` adapter maps `ButtonType.SECONDARY` and `ButtonSize.SMALL` to the same TUM AET UI
secondary/small styling; new standalone controls should use the package directly.

```html
<div class="flex flex-wrap items-center gap-2">
    <a tumAetUiButton severity="secondary" size="small" [routerLink]="historyRoute">
        <span jhiTranslate="artemisApp.repository.commitHistory.openCommitHistory"></span>
    </a>
    <button tumAetUiButton severity="secondary" size="small" type="button" (click)="download()">
        <span jhiTranslate="artemisApp.programmingExercise.export.downloadRepo"></span>
    </button>
</div>
```

Let the component select the paired foreground token for its background. Do not force white or black
text, color the icon separately, or combine framework button classes with TUM AET UI. Verify normal,
hover, focus, loading, and disabled states in both themes. Normal-size button text needs at least 4.5:1
contrast. Labels, icons, confirmation dialogs, and disabled semantics carry the meaning alongside color.
White text is not automatically more readable: yellow, green, or cyan surfaces can require a dark
foreground. Use the theme's paired contrast token instead of selecting a text color by appearance.

## Adding or changing a theme role

Before adding a property, search the existing semantic roles and the
[TUM AET UI theme contract](/developer/guidelines/tum-aet-ui-kit#theme-contract). If a new role is necessary:

1. Name it after purpose rather than hue or a single screen.
2. Add values to
   `src/main/webapp/content/scss/themes/_default-variables.scss` and
   `_dark-variables.scss`.
3. Check text and non-text contrast on every surface where the role is used.
4. Add a semantic Tailwind mapping only when application markup needs a utility.
5. Add a `--tumaet-ui-*` mapping only when package components need that supported customization
   axis; update the package reference theme and validation with it.
6. Verify the real component in both themes, compact layouts, forced-colors mode, and its relevant
   interaction states.

Avoid theme-specific component selectors in `theme-default.scss` or `theme-dark.scss`. They are a
last resort for legacy global integrations. A new application or TUM AET UI component should consume
semantic properties instead.

## Reading and changing the active theme

CSS should normally react through `data-theme` and semantic properties without TypeScript. When
behavior genuinely depends on the active theme, consume the `ThemeService.currentTheme` signal:

```ts
private readonly themeService = inject(ThemeService);

protected readonly isDark = computed(() => this.themeService.currentTheme() === Theme.DARK);
```

Code that reads resolved CSS values after a stylesheet swap, such as a canvas chart, must also
depend on `ThemeService.appliedThemeRevision`. This signal changes only after the selected theme
stylesheet is active.

Call `applyThemePreference()` only in response to an explicit user choice. Pass `undefined` to
restore system-preference mode:

```ts
this.themeService.applyThemePreference(Theme.DARK);
this.themeService.applyThemePreference(undefined);
```

Do not subscribe manually to theme changes or mirror the current theme into a mutable field.

## Migration coexistence

Bootstrap is still global, and PrimeNG remains in screens whose TUM AET UI capability is incomplete.
Their cascade and source-scanning constraints are documented in
[Client Development: Styling](/developer/guidelines/client-development#styling).
