# Database Migration Consolidation

Every major Artemis release folds the Liquibase changelogs of the previous release cycle into one initial schema
file, `00000000000000_initial_schema.xml`. This page is the procedure for doing that, and it is written to be
followed once per major version.

## Why

**Startup time.** Liquibase reads every changelog on startup to decide whether it still has to run. Dozens of
incremental changelogs make that measurably slower, and the cost is paid over and over in the server test suite,
where database contexts are created fresh.

**Readability.** Hundreds of incremental changelogs spanning several major versions are hard to reason about. A
consolidated schema states the current shape of the database in one place instead of as a replay of its history.

## The moving parts

| File | Role |
|------|------|
| `changelog/00000000000000_initial_schema.xml` | The consolidated schema, in three changesets: database-agnostic, MySQL/H2, PostgreSQL |
| `changelog/20240331151800_cleanup.xml` | Removes stale `DATABASECHANGELOG` rows on upgrade. Gets a fresh changeset ID each consolidation |
| `master.xml` | The manifest. After a consolidation it lists the initial schema, the cleanup, and the changelogs that are newer than the release branch |
| `core/config/migration/DatabaseMigration.java` | Validates the upgrade path on startup and clears the initial schema checksum once |
| `authorities.csv` | Seed rows for `jhi_authority`, loaded by the initial schema |
| `consolidate-changelogs.sh` | Verifies that your consolidated schema matches what `develop` produces |

### The three changesets

The split exists because a few columns cannot have one type across both supported databases.

1. **`00000000000001`**, database-agnostic. Every table, column, index and foreign key that can be expressed the same
   way everywhere. Columns needing a per-database type are deliberately **absent** here.
2. **`00000000000002`**, MySQL and H2 only, selected by `preConditions`. Adds those columns with `enum` and
   `varbinary` types.
3. **`00000000000003`**, PostgreSQL only. Adds the same columns with `varchar`, `text` and `bytea`.

Any index or foreign key touching one of those columns has to move into the database-specific changesets too,
otherwise it references a column that does not exist yet.

### What happens on startup

| Situation | Behaviour |
|---|---|
| Fresh install | No stored `artemis_version`, so apply the schema, the cleanup (a no-op here), and any newer changelogs, then store the version |
| Upgrade from a supported version | Clear the initial schema checksum once, let Liquibase recalculate it, run the cleanup and the newer changelogs, store the version |
| Upgrade from too old a version | Log an error and `System.exit(15)`. The operator has to upgrade to the required intermediate version first |
| Any later start | The cleanup changeset is already recorded, so the checksum step is skipped entirely |

## The procedure

Consolidating 9.0.0 out of the 8.8.x cycle is the running example. Substitute your own versions.

### Prerequisites

- Docker running, for the schema comparison.
- The release branch finalized, with its last bugfix tag cut (`8.8.6`).
- `develop` checked out, with a `master.xml` listing everything accumulated since.

### Step 1: Decide what to fold

Changelogs present on both the release branch and `develop` get folded. Changelogs that exist only on `develop` are
newer than the release and must stay as incremental migrations, because servers already running them have them
recorded.

```bash
# Only on develop: KEEP these as incremental migrations.
comm -13 \
  <(git show release/8.8.x:src/main/resources/config/liquibase/master.xml | grep 'include file' | sed 's/.*changelog\///' | sed 's/".*//' | sort) \
  <(grep 'include file' src/main/resources/config/liquibase/master.xml | sed 's/.*changelog\///' | sed 's/".*//' | sort)

# On both: FOLD these into the initial schema.
comm -12 \
  <(git show release/8.8.x:src/main/resources/config/liquibase/master.xml | grep 'include file' | sed 's/.*changelog\///' | sed 's/".*//' | sort) \
  <(grep 'include file' src/main/resources/config/liquibase/master.xml | sed 's/.*changelog\///' | sed 's/".*//' | sort)
```

Keep the "only on develop" list to hand. It is needed again in steps 4 and 5.

### Step 2: Edit the initial schema

Apply the **net structural effect** of the folded changelogs: add tables they created, drop tables they removed
along with the indexes and foreign keys pointing at them, and add, remove or retype columns, indexes and foreign
keys accordingly.

Skip their data migration SQL. Those statements move data in a database that already exists, and the initial schema
only ever runs against a fresh one.

<Callout variant={CalloutVariant.warning}>

    <strong>Do not regenerate the schema from a database dump.</strong> A dump reformats everything and silently
    changes types and constraint names, which turns the review into an unreadable diff and buries the changes that
    matter. Hand-apply the structural changes to the existing file instead.

</Callout>

Columns whose type differs per database go into changesets `00000000000002` and `00000000000003`, never into
`00000000000001`. The same applies to the indexes and foreign keys that reference them.

### Step 3: Verify the schema is equivalent

The consolidated schema must produce a database structurally identical to the one `develop` produces, on both MySQL
and PostgreSQL. `consolidate-changelogs.sh` checks exactly this: it starts four containers, applies `develop` to two
of them and your branch to the other two, dumps all four schemas and diffs them.

```bash
bash src/main/resources/config/liquibase/consolidate-changelogs.sh
```

<Callout variant={CalloutVariant.info}>

    Despite its name, the script only verifies. Editing the schema in step 2 stays manual.

    It needs Docker, a worktree of `develop` (it uses `/tmp/artemis-develop-verify`), and the Gradle Liquibase
    plugin, and it binds ports 3310 and 3311 for MySQL and 5440 and 5441 for PostgreSQL, so stop any local database
    on those first.

</Callout>

Pay particular attention to what a diff of dumps reports quietly: primary key names, unique constraint names, and
named `NOT NULL` constraints. Those are easy to lose when hand-editing and they do not surface in testing.

### Step 4: Update the cleanup changeset

Give the changeset in `20240331151800_cleanup.xml` a new timestamp ID so it runs again on upgrade, and exclude every
changelog from your "only on develop" list, because a test or staging server may already have applied them:

```xml
<changeSet id="20260406120000" author="krusche">
    <sql>
        DELETE FROM DATABASECHANGELOG WHERE ID not like '0000000000000%'
            AND FILENAME NOT LIKE '%20260205132454%'
            AND FILENAME NOT LIKE '%20260301010101%'
            AND FILENAME NOT LIKE '%20260304120000%';
    </sql>
    <sql>
        DELETE FROM migration_changelog;
    </sql>
</changeSet>
```

`ID not like '0000000000000%'` is what preserves the three initial schema changesets. Each `FILENAME NOT LIKE`
preserves one develop-only changelog; drop one and that server will try to apply it a second time.

<Callout variant={CalloutVariant.warning}>

    `DatabaseMigration.isSchemaConsolidationCompleted()` looks for this changeset ID to decide whether the
    consolidation has already run. Change the ID here and you <strong>must</strong> change the hardcoded ID in that
    method to match, or every startup will redo the checksum work.

</Callout>

### Step 5: Update `DatabaseMigration.java`

Add the version an operator must reach before they may upgrade to the new major:

```java
migrationPaths.add(new MigrationPath("5.12.9")); // required for migration to 6.0.0 until 7.0.0
migrationPaths.add(new MigrationPath("6.9.6"));  // required for migration to 7.0.0 until 8.0.0
migrationPaths.add(new MigrationPath("7.10.5")); // required for migration to 8.0.0 until 9.0.0
migrationPaths.add(new MigrationPath("8.8.6"));  // required for migration to 9.0.0 until 10.0.0
```

Then update the cleanup changeset ID in `isSchemaConsolidationCompleted()`, as step 4 requires. Those two are the
only edits this file needs.

`updateInitialChecksum()` also stamps the `DATABASECHANGELOG.LIQUIBASE` column, but it takes the value from
`MarkChangeSetRanGenerator.getLiquibaseBuildVersion()`, which is the same helper Liquibase uses for a normally
executed changeset. So it follows a Liquibase upgrade on its own and is nothing to maintain here. It used to be a
literal that had to be bumped by hand, and it drifted, because a stale value changes nothing observable: the
compatibility shims that read this column key on versions below 4.26 and on the 4.31.0 to 5.0.1 range, and they only
run to validate a stored checksum, which these rows do not have while `MD5SUM` is null.

### Step 6: Update `master.xml`

Remove every folded include. What remains is the initial schema, the cleanup, and the develop-only changelogs, in
that order.

### Step 7: Delete the folded changelog files

Remove their XML files from `src/main/resources/config/liquibase/changelog/`. Take the opportunity to delete
orphans as well, meaning files still on disk that nothing in `master.xml` includes.

### Step 8: Update `authorities.csv`

If a folded changelog inserted rows into `jhi_authority` with SQL, add them to `authorities.csv` instead. The
initial schema populates that table with `loadData` from this file, so an authority that only ever existed as an
`INSERT` in a deleted changelog would silently disappear from fresh installs.

### Step 9: Verify

```bash
./gradlew test -x webapp                          # server tests, PostgreSQL via Testcontainers
./run-e2e-tests-local-fast.sh                     # end-to-end
./gradlew spotlessCheck checkstyleMain -x webapp   # formatting and linting
```

Re-run the schema comparison from step 3 if you touched the schema after running it.

Finally, record the new upgrade path in the [Admin Upgrade Guide](/admin/upgrade-guide), since it is what tells
operators which version they have to pass through.

## Checklist

- [ ] Last bugfix tag on the release branch identified
- [ ] Develop-only changelogs identified and kept
- [ ] Initial schema edited by hand to the net structural effect, not regenerated from a dump
- [ ] Per-database columns, and their indexes and foreign keys, in changesets 2 and 3
- [ ] Constraint names checked: primary keys, unique constraints, named `NOT NULL`
- [ ] Schema equivalence verified on MySQL and PostgreSQL
- [ ] Cleanup changeset given a new ID, with a `FILENAME NOT LIKE` for every develop-only changelog
- [ ] Same ID updated in `isSchemaConsolidationCompleted()`
- [ ] New `MigrationPath` added
- [ ] `master.xml` reduced to the initial schema, the cleanup, and the develop-only changelogs
- [ ] Folded and orphaned changelog files deleted
- [ ] `authorities.csv` updated if an authority was added by SQL
- [ ] Server tests, end-to-end tests, and code quality all green
- [ ] Upgrade path documented in the [Admin Upgrade Guide](/admin/upgrade-guide)
