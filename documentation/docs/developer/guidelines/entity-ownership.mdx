Every row in the Artemis database belongs to something. A quiz question belongs to its quiz, a
submission to its participation, a lecture to its course. When the link that expresses that is
missing, the row becomes an **orphan**: it is still stored, still counted, still backed up, and no
longer reachable from anywhere in the application.

An orphan is worse than a leak. It is invisible in the user interface, so it reads as deleted, and
it is invisible to the deletion routines, so it never actually is. Account deletion and the data
privacy cleanup both walk the object graph downwards from the account and the course; a row nobody
points at is not on that walk, which means personal data can survive a deletion that reported
success.

This page records, for every entity, what it belongs to and whether the database guarantees it.

## What makes an entity orphan-proof

Three things have to hold, and only the first is about the entity itself:

1. **The owning foreign key is `NOT NULL`.** A nullable owner column is a standing invitation: any
   write that forgets to set it, any bulk update that clears it, any import that half-finishes,
   produces a row belonging to nothing. Where an entity may belong to one of two parents, the
   alternative is a check constraint over both columns — see `CHECK_EXERCISE_COURSE_OR_EXERCISE_GROUP`
   on `exercise` and `CHECK_DESTINATION_POST_OR_ANSWER` on `forwarded_message`.
2. **Deleting the parent reaches the child.** `ON DELETE CASCADE` removes it, `RESTRICT` refuses
   until the application has removed it. `ON DELETE SET NULL` on an *owning* key does neither: it
   manufactures the orphan on purpose. It is right for a reference (an assessor, a verifier), wrong
   for a parent.
3. **The child holds the key, not the parent.** A one-to-one where the parent carries the pointer
   leaves the child with no foreign key at all. Nulling the pointer, or deleting the parent after
   nulling it, strands the row with nothing left in the schema to find it by.

## Ownership by module

`Root` means the entity owns itself and has no parent by design. `Required` means the database
refuses a row without its parent. `Held by the parent` is the inverse one-to-one described above.

## Where orphans are possible today

Of the 147 tables behind the 186 entities, 62 have a required parent, 24 are roots by design and 18
are join entities whose parents are all required. Two carry a check constraint over alternative
parents. That leaves **41 tables where the schema permits an orphan**, in four shapes.

### An owning foreign key that is nullable

The largest group. The application sets the column on every path that creates one of these; the
database does not require it, so a path that does not is a silent bug rather than an error.

`Attachment`, `Slide`, `Lecture`, `TutorialGroup`, `ExerciseVariantGroup`, `Participation`,
`Submission`, `ExampleSubmission`, `TutorParticipation`, `GradingCriterion`, `GradingInstruction`,
`Feedback`, `QuizQuestion`, `TextBlock`, `ProgrammingExerciseTestCase`, `ProgrammingExerciseTask`,
`AuxiliaryRepository`, `StaticCodeAnalysisCategory`, `PlagiarismComparison`,
`PlagiarismSubmissionElement`, `IrisMessage`, `LLMTokenUsageRequest`, `DataExport`, `KnowledgeArea`.

`KnowledgeArea` is the one deliberate case: it is a tree, and a null parent means a root node.

### Alternative parents with nothing enforcing the choice

The shape `exercise` had before `CHECK_EXERCISE_COURSE_OR_EXERCISE_GROUP`, and `forwarded_message`
had before `CHECK_DESTINATION_POST_OR_ANSWER`. Both columns are nullable, so the database accepts a
row with neither, and usually also a row with both.

| Entity | Alternatives | Both set | Neither set |
| --- | --- | --- | --- |
| `GradingScale` | Course or Exam | Meaningless | Orphan |
| `Post` | Conversation or PlagiarismCase | Meaningless | Orphan |
| `Reaction` | Post or AnswerPost | Meaningless | Orphan |
| `PlagiarismSubmission` | PlagiarismCase or PlagiarismComparison | Possible | Orphan |
| `IrisSession` | Course, Post or User | Varies by subclass | Orphan |

`Complaint` and `ParticipantScore` are a softer version: their owner (a result, an exercise) is
required, but the participant they are about is a nullable student *or* a nullable team, so a row
can name neither.

### One-to-one where the parent holds the pointer

Ten tables have no foreign key of their own. Nothing in the schema connects them to anything, and
the only thing keeping them reachable is a nullable column on the parent.

`CourseAthenaConfig`, `CourseConfiguration`, `OnlineCourseConfiguration`,
`TutorialGroupsConfiguration`, `TeamAssignmentConfig`, `PlagiarismDetectionConfig`,
`SubmissionPolicy`, `BuildPlan`, `ProgrammingExerciseBuildConfig`, `LearnerProfile`.

### No foreign key at all

`LearningPath` stores `course_id` and `user_id` as plain nullable columns, and `VcsAccessLog` stores
a `NOT NULL participation_id` the same way. Nothing prevents them pointing at rows that no longer
exist. `ScienceEvent.resource_id`, `ApollonDiagram.course_id` and
`ProgrammingExerciseBuildStatistics` are untyped pointers of the same kind, which is why they are
listed as roots above: there is no relationship to enforce.

Every other shape listed above came back zero, including `Exercise`, which is what made the check
constraint safe to add without a data repair. The counts are worth re-running before acting on any
one of them, since a shape that is empty today is only one unguarded write path away from not being.

The `Slide` and `LearnerProfile` rows are the clearest illustration of the problem. Slides are
detached by the schema itself, deliberately, on every attachment unit deletion. Learner profiles
hold per-course study preferences for a named account and are reachable only from
`jhi_user.learner_profile_id`; once that is null, nothing finds them again, including the routine
that deletes an account's data.

## Options for closing the gap

None of these is free, and they are not alternatives to each other so much as a sequence.

**Make the owning column `NOT NULL`.** The strongest guarantee and the cheapest to enforce: one
`ALTER TABLE` and no runtime cost, since the check is part of writing the row. It needs the existing
violations repaired first, and a repair is only writable where the parent can be derived. For
`Slide` and `Submission` it cannot be, which is what makes those the expensive ones.

**Add a check constraint over alternative parents.** The right tool where an entity genuinely has
two possible owners. It costs two null tests on INSERT and UPDATE, nothing on read, and it is the
only way to express "exactly one of these". `20260916083344_changelog.xml` is the worked example,
including how to deal with rows that already violate it: repair where the answer is derivable, halt
where it is not.

**Replace `ON DELETE SET NULL` with `CASCADE` on owning keys.** For `Slide` this converts a silent
leak into the deletion that was intended. It has to be read carefully per column, because the same
clause is correct on a reference: `answer_post.verified_by_id` should survive the verifier's account.

**Give the child the foreign key in a one-to-one.** Moving the pointer from `course.athena_config_id`
to `course_athena_config.course_id` makes the config deletable by cascade and countable by query. It
is a migration with an application change attached, so it is worth doing where the child holds
personal data — `LearnerProfile` first — and arguably not worth it for a build plan.

**Add the missing foreign keys.** `LearningPath` and `VcsAccessLog` reference rows without declaring
it. Declaring it is a small migration and turns two invisible relationships into enforced ones.

**Make orphans visible.** Whatever is not fixed should at least be counted. A query per shape, run
as an architecture test or a scheduled admin check, turns "we think this cannot happen" into a
number that can be watched. This is worth having even for the constraints that do exist, because it
is how the next gap gets noticed before it reaches six figures.

## When adding an entity

- Give it a `NOT NULL` foreign key to its parent, or a check constraint if it has two possible ones.
- Choose the delete rule deliberately: `CASCADE` when the child has no meaning without the parent,
  `RESTRICT` when the application must clean up first, `SET NULL` only for references.
- In a one-to-one, put the foreign key on the child.
- If the entity holds personal data, say in the pull request how an account deletion reaches it.
