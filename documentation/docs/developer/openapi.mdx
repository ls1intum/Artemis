We migrate the Artemis server to an API-driven development approach using OpenAPI specifications. This especially helps us with client generation to avoid subtle bugs that are often unnoticed in code reviews.

Currently, the OpenAPI specs are generated for the `globalsearch`, `tutorialgroup`, `hyperion`, `calendar`, and `quiz` modules. We only support API-driven development for endpoints that are DTO-only and do not return domain objects.

<Callout variant={CalloutVariant.info}>
    If you want to make use of the OpenAPI specs, you need to ensure that the endpoint you are working on is a DTO-only endpoint. This means that the endpoint should not return or
    expect any domain objects, but only Data Transfer Objects (DTOs) or primitives.
</Callout>

## Generating OpenAPI Specs and Client Files

When you update a REST endpoint or a DTO, you need to generate a new OpenAPI spec and generate new client files.

Follow these steps to generate the OpenAPI spec and client files:

### Generate the OpenAPI Spec

To generate the OpenAPI spec, run the following command in the root directory:

```bash
./gradlew generateOpenApiDocs pruneOpenApiSpec -x webapp
```

This starts a throwaway server, reads its specification and writes an `openapi.yaml` file to the `config/openapi` directory. The server
uses port 8080 and its SSH server port 7921. If a development server already uses them, add `-PopenApiServerPort=<port>` and
`-PopenApiSshPort=<port>` to move it.

### Generate the Client Files

To generate the client files, run the following command in the root directory:

```bash
./gradlew openApiGenerate
```

This command:

- Prunes the specs file to only include DTO-only endpoints
- Generates the client files based on the OpenAPI spec
- Post-processes generated files: removes unused imports and strips the numeric suffixes that duplicate operation ids leave in method names

The generator returns the full `HttpResponse` for operations that declare a response header (`observeResponseHeaders`), so callers can read it.

The generated client files are stored in the `src/main/webapp/app/openapi` directory.

## Quiz Contract Check in CI

The generated client is built from the committed `config/openapi/openapi.yaml`. If a pull request changes a quiz endpoint or DTO
without regenerating that file, the client misses the change, and nothing fails at compile time.

The **Quiz OpenAPI Contract** job (`.github/workflows/ci-quiz-openapi.yml`) prevents this for the quiz module. It runs when quiz server
code, the specification or `gradle/openapi.gradle` changes. It regenerates the specification and fails when an operation under
`/api/quiz/`, or a component that such an operation references, differs from the committed file. The job output lists each
difference.

To fix a failure, regenerate the specification and the client as described above, and commit `config/openapi/openapi.yaml` and
`src/main/webapp/app/openapi`. To run the check locally:

```bash
cp config/openapi/openapi.yaml build/committed-openapi.yaml
./gradlew generateOpenApiDocs pruneOpenApiSpec checkOpenApiContract -x webapp \
    -PcommittedOpenApiSpec=build/committed-openapi.yaml -PopenApiContractPathPrefix=/api/quiz/
```

The check covers only the quiz operations. The other modules in the specification are not compared. The job does not run
for a change outside the quiz module that alters a DTO which a quiz operation references; the next quiz change detects it.

## The Agent API Specification

A second specification lists only the endpoints that a personal access token can call. It is not used to generate a client; it is
published at `/agent/openapi.yaml` for coding agents. It is generated by the same task with `-PopenApiGroup=agent` and written to
`documentation/static/agent/openapi.yaml`. How to opt an endpoint in, and why a test fails when this file is out of date, is described in
[Agent Access for Developers](/developer/agent-access).
