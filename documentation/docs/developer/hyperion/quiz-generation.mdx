This page describes the architecture behind Hyperion's AI-assisted quiz authoring, covering both question generation, in its free-topic and competency-grounded modes, and question refinement, applied to a single question or in bulk.
For instructor-facing usage documentation, see [Quiz Exercise: Generate Multiple-Choice Questions with AI](../../instructor/exercises/quiz-exercise#generate-multiple-choice-questions-with-ai) and [Refine Multiple-Choice Questions with AI](../../instructor/exercises/quiz-exercise#refine-multiple-choice-questions-with-ai).

## Components

Hyperion hosts two new server components for quiz authoring, backed by a set of prompt templates. The diagram below decomposes the subsystem and shows how it connects to the rest of Artemis and to the external services it depends on.

<Image src={subsystemDecomposition} alt="Subsystem Decomposition" size={ImageSize.large} caption="Subsystem Decomposition: Hyperion's Quiz Generation and Competency Context Components" />

The diagram groups the system into four parts: the Artemis server, the Artemis quiz client, and the external services Edutelligence and the LLM provider. Hyperion hosts the two new server components shown above, `HyperionQuizQuestionGenerationService` (Quiz Generation) and `HyperionCompetencyContextService` (Competency Context).

Quiz Generation builds structured prompts, calls the LLM provider through its service, and parses and validates the responses into valid Artemis questions. Competency Context aggregates the course context and exposes it to Quiz Generation, drawing entirely on existing Artemis services: it reads the competencies, their typed relations, and the linked exercises from Atlas's Competency Service, which in turn resolves the exercises through its own competency-exercise links; fetches the corresponding lecture units from the Lecture Service and calls Edutelligence's Lecture Snippet Service for embedded lecture retrieval.

Both components are backed by Spring AI prompt files under `src/main/resources/prompts/hyperion/`, rendered by `HyperionPromptTemplateService`. All three service beans are lazily initialized and only registered in the Spring context when Hyperion is enabled through configuration; see [Hyperion Setup](../../admin/hyperion) for details.

## Question Generation

The system supports two generation modes: a free-topic mode, where the instructor supplies a topic and optional guidance, and a competency-grounded mode, where questions are grounded in the course's competencies and their related lecture content.

### Free-Topic and Competency-Grounded Generation

Both modes render a different user-prompt template against the same system prompt. The free-topic template takes the topic, an optional custom prompt, the language, and the desired question counts and difficulty. The competency-grounded template instead takes the selected competencies, their relations, and the assembled lecture context, alongside the same options as the free-topic template. The two templates are `generate_quiz_questions_user.st` and `generate_quiz_questions_user_competency.st`, both rendered against the shared `generate_quiz_questions_system.st` system prompt.

### Competency-Grounded Context Assembly

The `computeContext` method on `HyperionCompetencyContextService` assembles this context in three steps:

1. It first loads all the course's competencies and resolves the requested IDs against that set. Any ID that is not part of the course triggers a bad-request error.
2. It then resolves the relations (assumes, extends, and matches) that involve the selected competencies.
3. Finally, it gathers lecture and exercise context from three independent sources, merged and de-duplicated:
   - **Pyris semantic search** surfaces pre-indexed lecture content ranked by relevance to the competency titles, capped at 20 results and scoped to the course. If Pyris is unreachable, this source is dropped with a logged warning.
   - **Text units linked to the competencies** are pulled in directly, since their content is already available plain text.
   - **Exercises linked to the competencies** contribute indirectly: problem statements are not passed to the quiz-generation prompt directly. Instead, each exercise (capped at 10) is first summarized by a separate LLM call that extracts its core challenges and learning objectives from the problem statement and, where available, the reference solution. Because the summarization calls are independent of each other, they run in parallel.

### Output Validation

The LLM response is parsed into a nested record structure, then mapped and re-validated into the DTO shape used by the rest of the system. This mapping step rejects the response if:

- Title is blank or exceeds 500 characters
- Question text is blank or exceeds 10,000 characters
- Fewer than 2 options
- Any option text is blank or exceeds 2,000 characters
- The correct-option count doesn't match the question type's structural rule (`validateCorrectOptionCount`): exactly 1 for single-choice, ≥1 for multiple-choice, exactly 2 options with exactly 1 correct for true/false

## Question Refinement

Refinement takes the question as currently edited in the UI, together with a free-text refinement prompt, and returns either a refined question or an error, reusing the same output-validation path as generation.

The response is modeled as a sealed interface with two variants, a success case and a failure case, discriminated by a `type` field:

```java
public sealed interface QuizQuestionRefinementResponseDTO permits QuizQuestionRefinementSuccessDTO, QuizQuestionRefinementFailureDTO {
    record QuizQuestionRefinementSuccessDTO(GeneratedQuizQuestionDTO question, String reasoning, String type) {}
    record QuizQuestionRefinementFailureDTO(String error, String type) {}
}
```

For bulk refinement this means that a single question's LLM call failing must not fail the whole batch.

The refined question can be restored to its previous state via a restore button, since the client snapshots each question before applying the refinement.

### Bulk refinement

Bulk refinement reuses the architecture of the single-question refinement mechanism and parallelizes the requests across the questions, calling the same single-question refinement logic for each with the shared refinement prompt, and catches exceptions per question rather than letting one bad question abort the whole batch. Results are returned in the same order as the input questions.

## Quiz Question Pool

Separately from the on-demand generation in the quiz editor, Hyperion keeps a per-course pool of pre-generated and pre-judged multiple-choice questions. The pool is a grid of cells, one per combination of competency, lecture unit linked to that competency, language, question type and difficulty, and every cell holds the number of items the course's settings assign to it. Every question is grounded in the material of its lecture unit. Instructors review the pool on its own page in course management; quizzes are later assembled from the approved questions.

### Cells and Settings

`HyperionQuizQuestionPoolBuildService.enqueue` derives the cells from the course's competencies (Atlas), the lecture units linked to each of them that carry readable material, the course language, and the course's settings, then tops every cell up to its target. `HyperionQuizQuestionPoolMaterialService` decides which linked units count: text units with content, and attachment video units with a stored PDF or a transcript; online units, exercise units and units without text get no cells, and a competency without such a unit gets no questions. The targets come from the course's `HyperionCourseSettings`: the single-choice count per lecture unit and competency (default 12) and, when multiple-choice questions are enabled, the multiple-choice count (default 12) are each split over the difficulties by the course's shares (default 20 % easy, 50 % medium, 30 % hard; whole numbers first, the remainder to the largest fractions), so each type yields exactly the configured number of questions per unit; a difficulty whose share comes to no question gets no cell. Enqueuing is idempotent: cells that already hold their target gain nothing.

The settings are stored as a JSON payload in `hyperion_course_settings`, keyed by course. The row is created with the course (`CourseRepository.ensureDefaultConfigurations`), a migration adds it for existing courses, and updates replace the payload in place; a course whose row is missing reads as the defaults and receives the row on its next update. `poolGenerationEnabled` is read by the scheduled overnight build.

### Build Loop

A build is started from the pool page and runs on the dedicated `hyperionQuizQuestionPoolTaskExecutor`; the request returns `202 Accepted` at once, or `409 Conflict` while a build of the same course runs anywhere in the cluster. Before enqueuing, the request takes the course's lease in the distributed map `hyperion-quiz-pool-builds`. The lease value is the build's token and the time of its last renewal; a lease renewed more than `build-lease-minutes` ago counts as expired. Taking over an expired lease, renewing and releasing are each one compare-and-set on that value, so renewal fails the moment another build replaced the lease, a crashed node frees the course once its lease expires, and no build can touch another build's lease. A build whose lease expired while it waited in the executor queue takes the lease again when the course is free and drops itself when another build holds it, and a running build that finds its lease gone stops after its current unit of work. One build per course therefore runs at a time as long as no single unit of work, one generation batch or one judgement, outlasts the lease; a model call that does can overlap the next build for that one unit, and the item version fences its writes. `HyperionQuizQuestionPoolBuildService.build` then works the pool to completion:

1. Claims older than `stale-claim-minutes` are returned to their stable state, and items whose last attempt failed on a model call (`CALL_FAILED`) or an unusable verdict (`FILTER_UNUSABLE`) are revived with a fresh attempt budget.
2. While there are generated items awaiting the filter, one is claimed and judged.
3. Otherwise up to `generation-batch-size` pending items of one cell are claimed and generated with a single model call; the questions are assigned to the claimed items in order, and items left without a usable question fail with `NO_VALID_QUESTION` and are retried up to three times. A question the filter rejects is discarded and its item is generated again while the item has generation attempts left (three in total), so only a question rejected on the last attempt stays in the pool as rejected.
4. The loop ends when nothing is left to claim.

Every item carries a version that each write increments. Claims are conditional updates that name the state and the version they expect (`QuizQuestionPoolItemRepository.claim`), the release of stale claims and the revival of failed items increment the version as well, and the completion writes go through the entity's optimistic lock, so a worker whose claim another node released and took over cannot overwrite the newer state: its save fails and the result is discarded (`saveIfStillOwned`). The cell coordinates and the item index are unique in the database, so two nodes cannot enqueue the same item twice. The item states are `PENDING`, `GENERATING`, `GENERATED`, `FILTERING`, `FILTERED`, `FAILED_GENERATION` and `FAILED_FILTER`; `review_state` records the instructor's later decision.

### Generation and Filter

Generation uses `generate_quiz_question_pool_system.st` and `generate_quiz_question_pool_user.st`, which ask for self-contained questions with four answer options and an explanation at the cognitive level the competency states: recall of stated facts at REMEMBER, at least one step of reasoning at UNDERSTAND and above. Lecture material is the text of the cell's lecture unit, extracted once per unit and build by `HyperionQuizQuestionPoolMaterialService` (text unit content, the PDF text of an attachment video unit via PDFBox, and its transcript), cut to `max-material-characters` and passed as a fenced block headed by the lecture and unit name. Items whose competency or lecture unit has disappeared, or whose unit no longer yields text, fail with `COMPETENCY_MISSING`, `LECTURE_UNIT_MISSING` or `NO_MATERIAL` and are not retried. Questions that fail the deterministic checks in `HyperionQuizQuestionChecks` (wrong type or option count, duplicate or contained options, "all of the above" style options, a reference to a figure the question does not contain, a conspicuously long correct option) are dropped before the filter sees them.

`HyperionQuizQuestionFilterService` renders `filter_quiz_question_system.st` and `filter_quiz_question_user.st` and asks the judge for a severity from 0 to 1 on each of the five failure modes in `QuizQuestionFailureMode`: factual error, ambiguous correct answer, off topic, near duplicate and ill-formed distractors. A verdict that omits a mode is discarded. The aggregate score is one minus the worst severity among the gating modes, and the question is accepted when the aggregate reaches 0.7. Near duplicate is reported but never gates, because a question grounded in lecture material necessarily resembles it. Every verdict is stored with the item, so the pool page can show why a question was flagged or rejected.

The generator and the judge model are set by the administrator under `artemis.hyperion.quiz-pool.generator-model` and `judge-model`; a blank value uses the default chat model. Both are bound onto the request through `ChatOptions`, and every call is recorded through `LLMTokenUsageService` under the pipeline ids `HYPERION_QUIZ_POOL_GENERATION` and `HYPERION_QUIZ_QUESTION_FILTER`.

### Pool Page

The pool has its own page in course management, `course-management/:courseId/smart-quizzes`, reachable for editors and above when Hyperion and Atlas are enabled. `QuizQuestionPoolComponent` loads the course to know the user's role, then progress, questions and, for instructors, the settings through `QuizQuestionPoolService`, which wraps the generated `HyperionQuizQuestionPoolApi`. Instructors start a build from the page and change the two pool settings; editors and instructors review. While a build runs the page polls progress and questions every few seconds and stops when the server reports the build as finished. A `409 Conflict` from the build endpoint is shown as "already running" rather than as an error.

Questions are grouped by competency and, within a competency, by lecture unit. Inside a unit's list, `QuizQuestionPoolItemListComponent` shows judged questions in three sections, accepted but flagged on at least one mode first, then accepted, then rejected by the filter, with a badge per flagged mode carrying the filter's justification and an expandable verdict. Approve and exclude set the item's review state through the review endpoint; taking the same decision again returns the question to "not reviewed". Questions that are still being generated or judged, and questions that failed, are only counted.

## Prompt-Injection Mitigation

Both pipelines sanitize every piece of user- or instructor-authored text before it is used in a prompt template:

1. Strips control characters.
2. Strips any `-----BEGIN/END ... -----`-style delimiter text the input itself might contain, preventing a competency title, lecture snippet, or refinement instruction from forging its own fake delimiter and breaking out of its untrusted block.
3. Strips `{{...}}`-style template variable syntax, preventing the input from being (mis)interpreted as a StringTemplate variable reference when the template is re-rendered.

Blocks of instructor-authored but still untrusted content (competency lists, competency relations, lecture snippets) are wrapped in the templates with explicit `-----BEGIN UNTRUSTED INPUT-----` / `-----END UNTRUSTED INPUT-----` markers and an instruction to the model to parse the content as data only.

This is the equivalent delimiter-and-instruction pattern used by the [Consistency Check](./consistency-check) pipeline for problem-statement content.

## Client Integration

On the client, `QuizAiGenerationService` wraps the generated OpenAPI client and maps the DTOs and the editor's `MultipleChoiceQuestion` / `GeneratedQuestion` models. The generation dialog and the inline per-question refinement panel plug into the existing Multiple-Choice question editor, while the quiz exercise update view hosts the bulk-refinement action, shown only when Hyperion is enabled and the quiz has at least one Multiple-Choice question.

Before applying a refinement, both the single-question and bulk flows snapshot the pre-refinement question with a deep clone, which is what enables the restore-previous-version action in the refinement UI. The refinement itself then mutates the original question object in place.
