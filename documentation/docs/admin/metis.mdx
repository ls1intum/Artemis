Metis asks students comprehension questions about the code they wrote themselves for a programming exercise. After the
due date, Artemis compares each student's submitted repository with the exercise template, picks one changed file per
question at random, and asks a language model for questions about exactly those files. Students answer in a time
window the instructor chooses, for the whole course or per tutorial group, with a timer per question. The model rates
every answer on a 5- or 7-point scale, and a weak answer gets up to the configured number of follow-up questions. The
check is formative: it creates no result, no score and no grade.

Editors and instructors switch the check on per exercise in the **Comprehension check (Metis)** section, which the
edit form of an existing course programming exercise in individual mode shows in its advanced mode; team exercises get
no check. They can review the generated questions before students see them, and follow the answers on a dashboard with
a CSV export. Everything runs inside Artemis; no EduTelligence service is involved. Metis talks to an
OpenAI-compatible chat completions endpoint of its own, configured under `artemis.metis.llm`, and never uses the
shared Spring AI endpoint of Hyperion and Atlas (`spring.ai.openai.*`).

<Callout variant={CalloutVariant.warning}>
    Metis sends student source code to the endpoint you configure, and there is deliberately no default endpoint for
    production. Decide whether you are permitted to send student code to that endpoint before you enable the module,
    and set `hosting` to what the endpoint really is, because it decides whose consent suffices. Involve your data
    protection officer if you are unsure.
</Callout>

## Prerequisites

- Programming exercises on the integrated version control. Metis reads the students' repositories directly from it
  and never checks them out.
- One node that runs both the `core` and the `scheduling` profile, as every installation has.
- An OpenAI-compatible chat completions endpoint that you are permitted to send student code to, with a model that
  understands code and follows JSON format instructions reliably. The development configuration uses
  `qwen3-coder:30b` on Ollama.

## Enable the Metis module

Metis is disabled by default. Set `artemis.metis.enabled` to `true` on every node that runs the `core` profile, either
in the configuration the server reads at startup from its configuration directory (for example `application-prod.yml`)
or as the environment variable `ARTEMIS_METIS_ENABLED=true`:

```yaml
artemis:
    metis:
        enabled: true
```

The packaged `application-artemis.yml` contains `enabled: true`, but that value does not take effect: the packaged
`application-core.yml` sets the flag to `false`, and since the profile lists activate `core` after `artemis` (for
example `artemis,scheduling,core,prod,docker`), the later profile wins. Your own configuration file and the environment
variable override both packaged files. Build agents do not need the module, and `application-buildagent.yml` keeps it
off, so set the flag only on nodes with the `core` profile.

After a restart, `/management/info` lists `metis` in `activeModuleFeatures`, and the **Features** page of the
administration shows **Metis comprehension checks** as active under **Module Features**. Without the flag, Artemis
loads none of the Metis services and endpoints, and the client shows none of its views.

There is no runtime feature toggle. Once the module is on, instructors decide per exercise, and a check runs only for
exercises whose comprehension check they switched on. Switching the module off later hides the feature and stops all
generation; stored checks, questions and answers stay in the database.

## The scheduling node

Questions are generated by exactly one node: the one that runs both the `core` and the `scheduling` profile. In a
cluster this is the node that also runs the other scheduled tasks, see
[Multiple Artemis instances](/admin/production-setup/multiple-artemis-instances#scheduling). Its poller starts 60
seconds after the node has started and then runs every `generation.poll-interval-seconds`. It creates the checks,
generates their questions and rates answers whose live rating failed. Every node with the module enabled, the
scheduling node included, serves students and instructors: it rates answers while the student waits and regenerates
single questions on request. Without a scheduling node that has the module enabled, no checks are created
automatically and no questions are generated.

The state of the poller lives in memory on that node: its circuit breaker, its failure counters and the time it first
saw each exercise switched on. After a restart, the first poll puts every check that a crash or a shutdown left in
generation back into the queue and treats every switched-on exercise as settled, so no enable delay applies.

To pause generation without switching the module off, for example while the endpoint is being maintained, set
`artemis.metis.generation.scheduler-enabled: false` on the scheduling node and restart it. Until you set it back, no
checks are created automatically, no pending check gets its questions and no stored answer is rated in the
background. Students and instructors keep their views, and live ratings and the regeneration of single questions
still call the endpoint: while it is down, answers are stored unrated, to be rated in the background later, and a
regeneration fails with an error. **Generate missing questions** still creates checks, which then wait as pending.

## Configure the LLM endpoint

Neither `application.yml` nor `application-artemis.yml` sets an endpoint. Only the `dev` profile
(`application-dev.yml`) points at a local Ollama server, for development. Until both `artemis.metis.llm.base-url` and
`artemis.metis.llm.model` are set, generation and rating are paused, and the server logs at startup:

```text
Metis LLM endpoint is not configured (artemis.metis.llm.base-url and model); generation and rating are paused
```

Set the keys on every node with the module enabled, since every node rates answers. The base URL is the root of the
OpenAI-compatible API including its version prefix, usually `/v1`; Artemis appends `/chat/completions` itself.

### Ollama

```yaml
artemis:
    metis:
        llm:
            base-url: https://ollama.example.org/v1
            model: qwen3-coder:30b
            hosting: LOCAL
```

Ollama serves plain HTTP without authentication, so the example assumes a reverse proxy in front of it that
terminates TLS. For an Ollama server on the same host as Artemis, use `http://localhost:11434/v1`. Ollama needs no
key, so `api-key` stays empty unless the proxy asks for one. Check the context length of the model before the first
exercise, see [Ollama settings](#ollama-settings).

### Other OpenAI-compatible endpoints

Any other server that implements the OpenAI chat completions API works the same way, for example vLLM, a LiteLLM
gateway or a commercial provider:

```yaml
artemis:
    metis:
        llm:
            base-url: https://llm.example.org/v1
            model: name-of-the-model
            hosting: CLOUD
```

Use `hosting: LOCAL` instead if the server runs on infrastructure your institution operates, see
[Whose code is sent](#whose-code-is-sent).

Pass the key as the environment variable `ARTEMIS_METIS_LLM_APIKEY` rather than writing it into a file. Artemis never
logs it. Every other key can be set as an environment variable as well, for example `ARTEMIS_METIS_LLM_BASEURL`,
`ARTEMIS_METIS_LLM_MODEL` and `ARTEMIS_METIS_LLM_HOSTING`.

On startup, a configured node logs `Configuring the Metis LLM clients` with the base URL, the model and the hosting.

### All configuration keys

Every key has a default, so you only set what differs. Artemis reads the keys at startup, so a change takes effect
after a restart of the node. When the module is enabled, a misspelled key under `artemis.metis` or an invalid value
shuts the server down during startup, so a typo cannot silently fall back to a default. Every number must be positive;
`temperature`, `batch-max-retries`, `delay-after-due-date-seconds`, `enable-delay-minutes` and `answer-grace-seconds`
may also be `0`.

| Key | Default | Meaning |
| --- | --- | --- |
| `artemis.metis.enabled` | `false` | Loads the module, see [Enable the Metis module](#enable-the-metis-module). |
| `artemis.metis.llm.base-url` | empty | Root of the endpoint including the version prefix. Empty means not configured. |
| `artemis.metis.llm.api-key` | empty | Key of the endpoint. Leave it empty for a server without authentication. |
| `artemis.metis.llm.model` | empty | Model id sent with every request. Empty means not configured. |
| `artemis.metis.llm.hosting` | `LOCAL` | `LOCAL` for an endpoint on infrastructure your institution runs, `CLOUD` for a cloud service. Decides whose consent suffices. |
| `artemis.metis.llm.temperature` | `0.2` | Sampling temperature. |
| `artemis.metis.llm.batch-timeout-seconds` | `180` | Timeout of a generation call and of a background rating. |
| `artemis.metis.llm.interactive-timeout-seconds` | `60` | Timeout of a call someone waits for: the rating of an answer and the regeneration of a question. Keep it plus `interactive-permit-wait-seconds` below the read timeout of your reverse proxy. |
| `artemis.metis.llm.batch-max-retries` | `2` | Retries of a generation call or background rating after a network error, a timeout, a rate limit or a server error. Calls someone waits for are never retried. |
| `artemis.metis.llm.max-concurrent-calls` | `4` | Metis LLM calls one node makes at the same time, see [Rating capacity](#rating-capacity). |
| `artemis.metis.llm.interactive-permit-wait-seconds` | `10` | How long a live rating or a regeneration waits for a free permit. An answer that gets none in time is stored unrated. |
| `artemis.metis.generation.scheduler-enabled` | `true` | Runs the generation poller on the scheduling node. |
| `artemis.metis.generation.poll-interval-seconds` | `30` | Pause between two polls. |
| `artemis.metis.generation.delay-after-due-date-seconds` | `60` | How long a participation's effective due date must have passed before its check is created. |
| `artemis.metis.generation.enable-delay-minutes` | `10` | How long the scheduling node waits after it first sees the check of an exercise switched on. |
| `artemis.metis.generation.horizon-days` | `30` | How far back the automatic creation of checks, its sweeps and the background rating look, see [When checks are created](#when-checks-are-created). |
| `artemis.metis.generation.max-concurrent-tasks` | `2` | Generations and background ratings that run at the same time on the scheduling node. |
| `artemis.metis.generation.min-changed-lines` | `5` | Added plus removed lines a file needs to become a focus file. If no file has that many, every changed file qualifies. |
| `artemis.metis.generation.max-focus-file-characters` | `12000` | Largest focus file whose full content is sent; larger files are sent as their diff only. Also the limit of each diff. |
| `artemis.metis.generation.max-prompt-characters` | `60000` | Size of one generation prompt. Over the limit, full file contents are left out first, the largest first, then every diff is shortened. |
| `artemis.metis.generation.max-problem-statement-characters` | `6000` | Length of the problem statement excerpt in the prompt. |
| `artemis.metis.generation.max-transient-failures` | `3` | Generation attempts with an unavailable endpoint after which a check fails with `LLM_UNAVAILABLE`. |
| `artemis.metis.conversation.answer-grace-seconds` | `15` | Grace after a question's deadline and after the end of the window, for answers still in transit. |
| `artemis.metis.conversation.max-answer-characters` | `10000` | Longer answers are cut, never rejected. |

## Data protection and consent

### What is sent to the endpoint

Each generation attempt sends one prompt for all questions of the student, and the same prompt once more if the
output was unusable. Network errors, timeouts, rate limits and server errors are retried up to `batch-max-retries`
times, an unavailable endpoint is tried again for up to `max-transient-failures` attempts, and a check that goes back
into the queue, for example after an extension of the due date or with **Generate missing questions**, is generated
again from the student's code. Every generation prompt contains:

- the title and the programming language of the exercise, the first `max-problem-statement-characters` characters of
  its problem statement, and the instructor's hint for the question generator;
- the paths of the files the student changed against the template, with the number of added and removed lines;
- for every question one focus file: its full content if it has at most `max-focus-file-characters` characters, and
  its diff against the template.

Only the student's own code counts. Changed files that are tests, build files, IDE and tool settings, build output,
dependencies, exercise metadata or documentation, binary files and files larger than 512 KiB are never sent.

Every answer that is not empty is rated with at most one call while the student waits; if that rating fails, the
scheduling node tries again in the background, see [Rating capacity](#rating-capacity) for the number of calls. A
rating call contains the focus file of the question (its content, only its diff if the file is too large, or nothing
if the repository cannot be read), the earlier questions and answers about the same main question, the question
itself and the answer. When an editor or instructor regenerates a single question, one call, never retried, contains
the exercise information above, the old question, the student's other questions and the focus file.

No call contains names, logins, e-mail addresses or registration numbers. The code goes out as the student wrote it,
comments included, so anything a student writes into their code, such as an author line with their name, reaches the
endpoint. Metis never writes prompts, code, answers or ratings to the server log; only the method logging of the
`dev` profile, which a production server does not run, prints the arguments of every service call.

Use HTTPS for an endpoint on another host, since every call carries student code or answers. Ollama serves plain
HTTP without authentication, so put a reverse proxy that terminates TLS in front of it, or keep it on the same host
or in a private network.

### Whose code is sent

Metis sends a student's code only if the student's choice in the **Choose Your AI Experience** dialog allows the
endpoint. It checks this when the check is created, again before it reads the student's repository for the
questions, when the student starts and with every answer, before a question is regenerated and before a stored answer
is rated in the background. What counts depends on `artemis.metis.llm.hosting`:

| Choice of the student | `hosting: LOCAL` | `hosting: CLOUD` |
| --- | --- | --- |
| **Cloud** | takes part | takes part |
| **On-premise** | takes part | skipped |
| **No AI** | skipped | skipped |
| no choice yet | skipped | skipped |

A skipped student gets no questions and causes no LLM call; the dashboard lists their check as skipped
(`NO_AI_CONSENT`). The tab asks a student without a choice to make one, and tells a student who chose on-premise
processing while the endpoint is a cloud service that Metis needs cloud consent. When a student later makes a choice
that allows the endpoint, the check is queued again, at the latest when the student opens the tab.

Set `hosting` to what the endpoint really is. `LOCAL` is right only for an endpoint on infrastructure your institution
runs, because that is what students who chose on-premise processing agreed to. The dialog describes the cloud option
as GDPR-compliant processing on Azure and the on-premise option as processing only in university datacenters; choose
the endpoint so that these statements stay true for Metis.

With `hosting: LOCAL`, also set `info.localLLMDeploymentEnabled: true` (environment variable
`INFO_LOCALLLMDEPLOYMENTENABLED=true`). Only then does the dialog offer **On-premise**. Without it, a student who wants
on-premise processing has to accept cloud AI for every AI feature of Artemis to take part in Metis. The flag applies
to the whole instance: the dialog offers the option for every AI feature.

### What Artemis stores

For every check, Artemis stores its status, the reason of a skip or failure, the commit the questions were generated
from, the model, the prompt version and the timestamps. For every question it stores the text, the focus file path and
its number of changed lines, the time limit, the answer, the rating, the model's rationale and the timestamps. Tutors,
editors and instructors of the course see all of this on the dashboard and can export it as a CSV file with the
students' logins and names. Students see their own answers, and the ratings with their rationale once their window
has ended, or right after they completed the check if the window has no end.

The data belongs to the participation: deleting the participation, the exercise or the course, resetting the course,
or deleting the student's account removes it. The data export of a user account does not contain Metis answers.

## Generation throughput

Generation runs only on the scheduling node, with `generation.max-concurrent-tasks` slots (2 by default). A slot
processes one check at a time: it reads the student's repository, makes one LLM call for all questions of the student
and stores them. As soon as a slot finishes, it claims the next pending check itself instead of waiting for the next
poll. Pending checks are claimed in the order of the students' window starts, across all exercises: the earliest
window of a tutorial group the student belongs to, else the window of the exercise, else the due date. The group
whose window opens first is therefore generated first. Answers waiting for their background rating, see
[Rating capacity](#rating-capacity), take a free slot before the next pending check does.

With a 30B model, one check takes roughly 20 to 40 seconds, depending on the hardware and the size of the student's
code. Two slots therefore generate about 3 to 6 checks per minute, so a course with 300 students needs about 50 to 100
minutes after the due date. Tell instructors to open the window only once generation has finished; until then,
students see that their questions are being prepared. To generate faster, raise `max-concurrent-tasks`, keep
`max-concurrent-calls` above it, and stay within the parallel slots of the LLM server: tasks beyond them only queue
there.

## Rating capacity

Every answer that is not empty gets at most one rating call while the student waits, on the node that serves the
request. That call waits at most `interactive-timeout-seconds` for the model and is never retried. An empty answer,
and an answer that arrives more than `answer-grace-seconds` after the question's deadline and is therefore stored
empty, gets the lowest rating without a call. All Metis calls of a node share `llm.max-concurrent-calls` permits:
generation and background ratings wait for a permit as long as it takes, a live rating at most
`interactive-permit-wait-seconds`.

One node therefore rates about `max-concurrent-calls` divided by the mean rating latency answers per second. With 4
permits and about 5 seconds per rating with a 30B model, that is about 0.8 answers per second, or 48 per minute. The
answers of a group arrive spread over the time limits of the questions, so a seminar group of about 30 students fits;
a burst beyond that waits for a permit.

An answer that finds no permit in time, whose rating call fails or whose rating is unusable, is stored unrated. The
student gets no follow-up question for it and continues with the next question. The scheduling node rates such
answers later in the background, once they are at least 85 seconds old (the permit wait, the interactive timeout and
the answer grace together), if their check was started within the last `horizon-days` and while the comprehension
check of the exercise is switched on. Each background attempt sends the rating prompt once more if the output is
unusable, and retries network errors, timeouts, rate limits and server errors up to `batch-max-retries` times. An
unavailable endpoint pauses this background rating just like generation. If the background rating of an answer fails
three times for another reason, for example because the output is unusable, with five minutes between the attempts,
the scheduling node gives up on that answer until its next restart.

If the endpoint is unavailable for three live calls in a row on a node, that node stops calling it for live ratings
and regenerations for 60 seconds and stores the answers of that minute unrated at once, instead of letting every
student wait for the full timeout. Permit timeouts do not count towards this, since they mean local load rather than a
broken endpoint.

The parallelism of the LLM server is the real limit. Size `max-concurrent-calls`, summed over all nodes, to its
parallel request slots, for Ollama `OLLAMA_NUM_PARALLEL`. Permits beyond that only queue at the server, and the
waiting counts against the interactive timeout. On the scheduling node, running generation holds up to
`max-concurrent-tasks` permits, so keep `max-concurrent-calls` above `max-concurrent-tasks`; Artemis logs a warning at
startup otherwise. While a live rating waits for a permit there, the scheduling node starts no new generation or
background rating.

## When checks are created

The scheduling node creates the check of a participation once all of the following hold:

- The comprehension check of the exercise is switched on, and the scheduling node has seen it switched on for at
  least `generation.enable-delay-minutes`. The settings form saves on every change, so the delay gives an instructor
  who switches the check on after the due date time to set the window, the hint and the review before questions are
  generated. Exercises that are switched on when the scheduling node starts count as settled, and switching a check
  off and on again starts the delay anew.
- The participation's effective due date, its individual due date if it has one and else the due date of the
  exercise, lies at least `generation.delay-after-due-date-seconds` in the past, so that pushes still in transit are
  included. The questions are generated from the latest submission up to the effective due date, judged by the time
  Artemis received the push rather than by the commit time. An exercise without a due date never gets checks.
- The exercise is recent: its due date, an individual due date, the end of its window or the end of a tutorial group
  window lies less than `generation.horizon-days` in the past, or in the future.

Only graded participations of a single student that have a repository get a check, and only if the user holds the
student role in the course and no tutor, editor or instructor role. Practice participations, team exercises, exam
exercises and course staff never get one.

For an exercise outside the horizon, an instructor presses **Generate missing questions** on the comprehension check
dashboard. It creates the missing checks at once, without the enable delay, and queues failed checks again, as well as
checks skipped for missing consent or a closed window. The scheduling node then generates them with its next poll.
The instructor settings mention the default enable delay of 10 minutes and the default horizon of 30 days; if you
change these keys, tell your instructors.

When an instructor extends a student's due date, a check the student has not started goes back to pending and is
generated again after the new due date. A started check is never changed.

## Model costs for self-hosted models

Every Metis call that returns a response with token counts is recorded in the LLM token usage of Artemis under the
service `METIS`, with the pipeline `METIS_QUESTION_GENERATION`, `METIS_QUESTION_REGENERATION` or
`METIS_ANSWER_RATING`, the course and the exercise. A call that fails, for example with a timeout, is not recorded.
Generation and rating are attributed to the student whose code is processed, a regeneration to the editor or
instructor who asked for it. The cost comes from `artemis.llm.model-costs`, matched against the model the endpoint
reports. A model without an entry is recorded with zero cost, and every recorded call logs the warning
`No LLM cost configured for model`. For a self-hosted model, register zero cost explicitly:

```yaml
artemis:
    llm:
        model-costs:
            "[qwen3-coder:30b]":
                input-cost-per-million-eur: 0
                output-cost-per-million-eur: 0
```

A key with dots or colons needs the brackets. As environment variables, the same entry is
`ARTEMIS_LLM_MODELCOSTS_QWEN3CODER30B_INPUTCOSTPERMILLIONEUR=0` and
`ARTEMIS_LLM_MODELCOSTS_QWEN3CODER30B_OUTPUTCOSTPERMILLIONEUR=0`: keys and model names are compared without the
characters that are neither letters nor digits. Configure the entry in one of the two forms only: both reduce to the
same key, and the server stops right after startup with `Conflicting LLM model cost keys`. See also
[token usage tracking](/admin/hyperion#token-usage-tracking).

## Ollama settings

A generation prompt can reach `max-prompt-characters` characters plus the instructions and the model's answer, which
is in the order of 15,000 to 20,000 tokens for typical code. Depending on its version and the available memory,
Ollama's default context window can be smaller than that, and Ollama then shortens the prompt instead of rejecting
it: the model loses part of the instructions or of the student's code and produces weaker or unusable questions. Give
the model a context of at least 32,768 tokens, either with `OLLAMA_CONTEXT_LENGTH=32768` on the Ollama server or with
a model variant whose Modelfile contains `PARAMETER num_ctx 32768`, configured as `model`. `ollama ps` shows the
context of a loaded model in its `CONTEXT` column.

`OLLAMA_NUM_PARALLEL` sets the parallel request slots that the `max-concurrent-calls` of all nodes with the module
enabled, added up, should match, and the memory Ollama needs for the context grows with it. Ollama also unloads an
idle model after five minutes by default. Loading a 30B model again can take longer than
`interactive-timeout-seconds`, so the first answers after a pause would be stored unrated: keep the model loaded while
windows are open, for example with `OLLAMA_KEEP_ALIVE`.

## Troubleshooting

### Checks stay pending

Instructors see the rows of the dashboard stay **Pending**, and students see that their questions are being prepared.
The log of the scheduling node tells why:

- `The Metis LLM endpoint is not configured (artemis.metis.llm.base-url and model), so no questions are generated and
  no stored answers are rated`, repeated at most once per hour: set the endpoint keys.
- `The Metis LLM endpoint is unavailable; generation and rating backfill pause until ...`: a generation or a
  background rating failed because the endpoint was unreachable, overloaded, failed with a server error or did not
  answer in time. An authentication error (401, 403) and a model that the endpoint reports as not found (404) count as
  an unavailable endpoint too, because they concern every check, not one. The circuit breaker pauses generation and
  the background rating for 60 seconds, doubles the pause with every further failure up to 15 minutes, and closes
  with the next successful generation (`The Metis LLM endpoint answers again; the circuit breaker is closed`). Set
  `logging.level.de.tum.cit.aet.artemis.metis: DEBUG` to see the reason of every failed call.
- Nothing at all: check that the node with the `core` and `scheduling` profiles has the module enabled and that
  `generation.scheduler-enabled` is not `false`.

Live ratings that wait for a permit on the scheduling node also hold back new generation, but only for seconds. A
check that stays **Generating** after a crash or a restart goes back to pending with the first poll after the
scheduling node has started.

### No checks on the dashboard

The dashboard lists a row only once a check exists. Before that, check the conditions in
[When checks are created](#when-checks-are-created): the effective due date and the delay after it, the enable delay
of an exercise switched on after its due date, and the horizon. Course staff and practice participations never get a
check. **Generate missing questions** creates the missing checks of an exercise at once.

### Answers stay unrated

`The live rating of the answer to Metis question ... failed as UNAVAILABLE` means that the answer found no permit in
time or that the endpoint was unavailable, as described under [Checks stay pending](#checks-stay-pending).
`The Metis LLM endpoint was unavailable for 3 interactive calls in a row` means that the node pauses live ratings for
a minute. Both are resolved by the background rating on the scheduling node once the endpoint answers again. If
permits are the bottleneck during busy windows, see [Rating capacity](#rating-capacity).

`... failed as REJECTED` means that the endpoint refused the request, as described for `LLM_REJECTED` under
[Skipped and failed checks](#skipped-and-failed-checks).
`The backfill gives up on rating the answer to Metis question ... after 3 failures` means that the background rating
of that answer failed three times, for example because the model kept returning unusable output or the endpoint
refused the request; it is tried again after the next restart of the scheduling node.

### Skipped and failed checks

Instructors see the reason of every skipped or failed check on the **Review questions** page, and in the
`failure_reason` column of the CSV export. **Generate missing questions** queues every failed check again, as well as
checks skipped for missing consent or a closed window. A check skipped for a missing submission or missing own code
stays skipped, because neither can change after the due date; only an extension of the due date evaluates it again.

| Code | Status | Meaning and what to do |
| --- | --- | --- |
| `NO_AI_CONSENT` | Skipped | The student's AI choice does not allow the endpoint. The check is queued again once the student makes a choice that allows it. |
| `NO_SUBMISSION` | Skipped | No submission before the effective due date. |
| `NO_OWN_CODE` | Skipped | The student changed no own code: nothing at all, or only tests, build files, documentation or whitespace. |
| `WINDOW_CLOSED` | Skipped | At generation time, the student's window had ended, was empty because of an extension past its end, or left less time than the shortest time limit of a question. Changing a window of the exercise queues such checks again. |
| `REPOSITORY_UNAVAILABLE` | Failed | The repository could not be read, or the submitted commit is not in it. The server log names the repository. |
| `INVALID_LLM_RESPONSE` | Failed | The model returned unusable output twice. Check the context length (see [Ollama settings](#ollama-settings)) or use a model that follows JSON instructions more reliably. |
| `LLM_REJECTED` | Failed | The endpoint rejected the request with status 400, 413 or 422, usually because the prompt exceeds the context of the model. Lower `max-prompt-characters` or give the model a larger context. Some gateways, such as LiteLLM, also answer an unknown model name with 400; since a rejection does not pause generation, every pending check then fails quickly. If all checks fail this way, check `artemis.metis.llm.model` first, then press **Generate missing questions** on the dashboard of each affected exercise to queue its failed checks again. |
| `LLM_UNAVAILABLE` | Failed | The endpoint was unavailable for `max-transient-failures` attempts. |
| `INTERNAL_ERROR` | Failed | An unexpected error; the server log holds its stack trace. A `max-prompt-characters` value too small for the diffs of the focus files ends here as well, logged as `The Metis generation prompt leaves ...`. |
