# Hyperion Service

Hyperion extends Artemis with AI-assisted authoring features for programming exercises. It offers consistency checks for problem statements and exercise artefacts and can rewrite instructions with the help of generative AI. The functionality is provided entirely by Artemis and Spring AI, so no EduTelligence service needs to be deployed.

<Callout variant={CalloutVariant.info}>
    For local development setups using LM Studio, refer to the [Spring AI Development Guide](/developer/spring-ai) in the Developer documentation.
</Callout>

## Prerequisites

- A running Artemis instance that loads the `core` profile.
- Network access to an LLM provider that is supported by Spring AI (for example OpenAI or Azure OpenAI).
- A valid API key for the chosen provider.

<Callout variant={CalloutVariant.warning}>
    <strong>
        Agentic whole-exercise generation and adaptation require the integrated LocalCI/LocalVC lifecycle (the <code>localci</code> profile).
    </strong>{' '}
    They drive a resource-bounded, network-isolated sandbox on a LocalCI build agent, persist through LocalVC with a LocalCI trigger, and verify with the production LocalCI
    test/SCA parsers, so they are automatically disabled on Jenkins deployments (the endpoints are not registered and the client hides the entry points). The other Hyperion
    features — consistency check and problem-statement rewriting — do not depend on LocalCI and work with any supported CI system.
</Callout>

## Enable the Hyperion module

Hyperion is disabled by default. Activate it by overriding the `artemis.hyperion.enabled` property in the configuration that the server reads on startup (for example `application-prod.yml`).

```yaml
artemis:
    hyperion:
        enabled: true
```

## Configure Spring AI

Hyperion delegates all model interactions to Spring AI. Artemis ships the single OpenAI module (backed by the official OpenAI Java SDK), which serves OpenAI, Azure OpenAI / Microsoft Foundry, and OpenAI-compatible local servers from one configuration tree.

### OpenAI

```yaml
spring:
    ai:
        model:
            chat: openai
        openai:
            api-key: <openai-api-key>
            timeout: 5m # Connection-level HTTP timeout (default 60s); reasoning models and tool-calling loops can exceed it
            chat:
                model: gpt-5-mini # Or another (reasonably capable) model
                temperature: 1.0 # Required to be 1.0 for gpt-5
```

The OpenAI SDK owns bounded transport retries. Hyperion itself only re-samples once when a successful response contains neither text nor tool calls; it does not add another transport-retry layer. `spring.ai.retry.*` is not used for OpenAI chat calls in this setup.

Set `artemis.hyperion.agent.context-window-tokens` to the provider's usable context window (the default is 128,000). Hyperion uses
`max_completion_tokens` by default and leaves enough room for reasoning-model output: 16,384 tokens for agent turns and up to 32,768 for semantic review. If an older
OpenAI-compatible endpoint only accepts `max_tokens`, configure `spring.ai.openai.chat.options.max-tokens` explicitly. Otherwise, use
`spring.ai.openai.chat.options.max-completion-tokens` only when the provider requires a lower output ceiling. Do not configure both fields. Hyperion clamps agent and reviewer
requests to the configured provider ceiling and remaining context; low ceilings can make the fail-closed review return `NEEDS_REVIEW`.

### Azure OpenAI / Microsoft Foundry

```yaml
spring:
    ai:
        model:
            chat: openai
        openai:
            api-key: <azure-openai-api-key>
            base-url: https://<your-resource-name>.openai.azure.com
            microsoft-foundry: true # routes auth as an Azure api-key header; keep false/omitted for plain OpenAI or OpenAI-compatible endpoints
            timeout: 5m # Connection-level HTTP timeout (default 60s); reasoning models and tool-calling loops can exceed it
            chat:
                model: <azure-deployment> # the Azure deployment name; used as the request model. gpt-5-mini deployment recommended
                temperature: 1.0 # Required to be 1.0 for gpt-5
```

### Token Usage Tracking

Artemis tracks LLM token usage and costs per request. Configure model pricing under `artemis.llm.model-costs` to enable accurate cost reporting in admin dashboards.

```yaml
artemis:
    llm:
        model-costs:
            gpt-5-mini:
                input-cost-per-million-eur: 0.23
                output-cost-per-million-eur: 1.84
```

Add entries for each model you use. The key must match the model name returned by your provider (without date suffixes like `-2024-07-18`). If a model has no cost entry, costs default to zero but token counts are still recorded.

### Observability (Optional)

Enabling observability during development helps you understand how LLM-based features behave, why they produce certain outputs, and how to optimize them. Since LLMs are non-deterministic and sensitive to prompts, parameters, and context, traditional logging is often not enough.

Key benefits of adding observability:

- Full visibility into prompts, responses, parameters, and token usage
- Reproducible debugging through stored traces
- Faster prompt iteration with comparison and tracking
- Early cost and token monitoring
- Insight into multi-step pipelines and performance bottlenecks
- Primarily used in development, but can also be enabled in production environments if deeper analysis or incident debugging is required

#### Langfuse

Langfuse is a platform for observability and tracing of LLM applications and agents. It captures everything happening during an LLM interaction: inputs, outputs, tool usage, retries, latencies and costs.

#### Setup Guide

1. See how to create and setup a Langfuse account (See only "Get API keys") [here](https://langfuse.com/docs/observability/get-started).

2. Request to join a Organization from an Edutelligence maintainer.

3. You will be added to the Project as **Member**.

    > ℹ️ **Note**
    > Project Members can _use_ Langfuse and access existing API keys.
    > Only **Project Admins** can create new API keys.
    > If you cannot view API keys, ask the maintainer to generate them for you.

4. Once the Project Admin provides the **Public Key** and **Secret Key**, store them securely.
   These keys authenticate your application when sending observability data to Langfuse.

5. Identify your Langfuse host URL.
   It appears in the Langfuse UI as: **https://\<host\>**.

Your **OTLP HTTP ingestion endpoint** follows the standard OTLP HTTP spec and is constructed as:
**https://\<host\>/api/public/otel/v1/traces**

- `/api/public/otel` → Langfuse OTLP receiver root
- `/v1/traces` → Standard OTLP HTTP route
    > For more info: See how Langfuse can receive traces on the OLTP endpoint [here](https://langfuse.com/integrations/native/opentelemetry)

6. Generate the Basic Authentication token for Langfuse.
   Use Base64 encoding with the format: base64(public_key:secret_key)

Example generation command:

```bash
echo -n "<public_key>:<secret_key>" | base64
```

7. Add the OTLP endpoint and authorization header to your Spring configuration.

Use the OTLP endpoint constructed in Step 5 and the Base64 token generated in Step 6.
These values can be provided through **active Spring profile YAML** (e.g. `application-local.yaml`, `application-dev.yaml`) or via **environment variables**.

You will need to set the following properties:

- `management.otlp.tracing.endpoint` → `https://<host>/api/public/otel/v1/traces`
- `management.otlp.tracing.headers.Authorization` → `Basic <base64(public_key:secret_key)>`

To avoid committing secrets, prefer supplying these values via environment variables and referencing them in YAML.

#### Configure Langfuse

> Below is the current configuration used in development profile to view the LLM traces of Hyperion services on Langfuse.

```yaml
management:
    # Set true to display contextual name in @Observed on Langfuse
    observations:
        annotations:
            enabled: true
    # Configuration for exporting LLM traces to Langfuse (set to true to enable Artemis' custom exporter)
    langfuse:
        enabled: true
    tracing:
        sampling:
            probability: 1.0
    otlp:
        tracing:
            # LangFuse accepts OTLP over HTTP at the traces path only
            # (example: https://langfuse.aet.cit.tum.de/api/public/otel/v1/traces)
            endpoint: https://example.com
            transport: http
            headers:
                # Provide "Basic <base64(public_key:secret_key)>" via env var to avoid committing secrets
                Authorization: 'Basic <base64(public_key:secret_key)>'
            # Important: Set export.enabled: false to disable the *default* OTLP exporter.
            # Artemis uses its own custom exporter to send Spring AI LLM traces to Langfuse.
            # so disabling the default exporter will NOT stop LLM trace export.
            export:
                enabled: false
```

## Verifying the integration

1. Restart the Artemis server and confirm that `hyperion` appears in `activeModuleFeatures` on `/management/info`.
2. Log in as an instructor and open the programming exercise problem statement editor. New Hyperion actions appear in the markdown editor toolbar (rewrite and consistency check).
3. Run a consistency check to ensure the LLM call succeeds. Inspect the server logs for `Hyperion` entries if the request fails; misconfigured credentials and missing network egress are the most common causes.

## Build-agent placement (multi-node)

Agentic exercise generation runs inside a **resource-bounded, network-isolated Docker sandbox on a LocalCI build agent**. The agent can be shared with normal LocalCI work or dedicated to generation. Each generation job uses exactly one slot and one sandbox container from workspace setup through automated checks. The container is released before repository persistence and LocalCI synchronization. Jobs can run for several minutes and consume CPU, memory, and Docker resources throughout.

To keep generation from ever competing with exam builds by accident, **hosting is opt-in per build agent and off by default**:

```yaml
artemis:
    continuous-integration:
        # Required on a mixed host so normal LocalCI concurrency can be sized explicitly alongside generation slots.
        specify-concurrent-builds: true
        concurrent-build-size: 1
        build-agent:
            # Maximum concurrent generation jobs on this agent. Each job uses one slot and one container; 0 disables hosting (default).
            max-generation-sandbox-slots: 0
            # Keep true on normal CI agents. Set false only on dedicated Hyperion sandbox hosts that should not run student/exam builds.
            run-build-jobs: true
```

<Callout variant={CalloutVariant.warning}>
    Leave <code>max-generation-sandbox-slots</code> at <strong>0</strong> on every exam-critical build agent. Set it to the measured number of generation jobs that may run
    concurrently on that agent: each job reserves one slot and runs one container. On a single-node integrated deployment (core + build agent on one host), the co-located node
    still uses the relay and this capacity setting.
</Callout>

Generation slots and normal LocalCI build slots are separate admission limits. Artemis does not dynamically subtract one from the other. On a mixed host, set
`specify-concurrent-builds: true` and choose `concurrent-build-size` so the combined CPU and memory ceilings of normal builds and generation sandboxes fit the host. Start with one
generation slot on a mixed non-exam agent. On a dedicated generation agent, set `run-build-jobs: false` and also start with one generation slot. Keep generation disabled on exam agents.
Increase these values only after representative load tests meet defined CPU-pressure, throttling, latency, memory, Docker-disk, and failure-rate thresholds.

Additional controls:

- **Pausing a build agent** (from the LocalCI build-agent admin page) stops it accepting **new** Hyperion generation jobs, so you can drain it before maintenance or an exam. In-flight jobs finish and their containers are removed cleanly.
- Orphaned sandbox containers are reaped automatically after `generation-sandbox-idle-timeout-minutes` (default 90).

Every concurrently running build-agent process must have a unique `short-name`. Do not overlap two process incarnations with the same short name during a rolling replacement: relay routing and sandbox reconciliation use that value as the agent identity.

## Generation admission controls

Agentic generation can run for several minutes and consume many model tokens. Configure these server-side limits before enabling it for production courses:

| Property                                                        | Default     | Purpose                                                                                                                                                                                                                                                                    |
| --------------------------------------------------------------- | ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `artemis.hyperion.generation.max-concurrent-jobs-per-core-node` | `2`         | Conservative node-local admission fallback, not a production sizing recommendation. Starts beyond this cap fail fast instead of waiting in memory. Jobs do not spill from a saturated core node to an idle one; the cluster upper bound is the sum of the node-local caps. |
| `artemis.hyperion.agent.max-job-duration`                       | `PT30M`     | Admission-to-cancellation deadline. Cancellation is cooperative: provider, sandbox, verification, and repository operations must also have bounded timeouts.                                                                                                               |
| `artemis.hyperion.agent.context-window-tokens`                  | `128000`    | Usable provider context window. Hyperion keeps prompt and completion headroom within this limit; set it to the deployed model/proxy's real limit.                                                                                                                          |
| `artemis.hyperion.agent.max-turns`                              | `40`        | Per-attempt model-turn cap. The orchestrator can still retry verification-guided near misses (currently up to four attempts per job), but one runaway attempt is bounded.                                                                                                  |
| `artemis.hyperion.agent.max-tokens-per-job`                     | `3000000`   | Per-job post-response cost guard and the amount reserved against enabled rolling budgets while a job runs. The job is cancelled before the next agent turn once reached.                                                                                                   |
| `artemis.hyperion.agent.token-budget-window`                    | `PT24H`     | Rolling window for admission budgets.                                                                                                                                                                                                                                      |
| `artemis.hyperion.agent.admission-max-tokens-per-user`          | `12000000`  | Rolling per-user admission limit. `0` disables the limit.                                                                                                                                                                                                                  |
| `artemis.hyperion.agent.admission-max-tokens-per-course`        | `120000000` | Rolling per-course admission limit. `0` disables the limit.                                                                                                                                                                                                                |
| `artemis.hyperion.agent.admission-max-tokens-global`            | `600000000` | Rolling global admission limit. `0` disables the limit.                                                                                                                                                                                                                    |
| `artemis.hyperion.agent.owner-heartbeat-interval`               | `PT15S`     | How often the worker node refreshes its ownership heartbeat.                                                                                                                                                                                                               |
| `artemis.hyperion.agent.stale-job-timeout`                      | `PT35M`     | How long another node waits before recovering a job whose owner left the cluster. Keep this above `max-job-duration`.                                                                                                                                                      |
| `artemis.hyperion.agent.stale-job-scan-ms`                      | `60000`     | Scan interval for cooperative deadline/stale-slot cleanup.                                                                                                                                                                                                                 |
| `artemis.hyperion.agent.provider-hard-failure-cooldown`         | `PT5M`      | Shared cooldown for provider quota/auth/configuration failures; transient rate limits still use per-call backoff.                                                                                                                                                          |
| `artemis.version-control.git-operation-timeout-seconds`         | `120`       | Inactivity timeout applied to clone, fetch, pull, push, and remote-list operations.                                                                                                                                                                                        |

## Operational considerations

- **Capacity:** Sandboxes inherit the build agent's `default-docker-flags` (2 CPUs, 2 GiB memory, no container swap, and 1,000 PIDs by default). These are elastic hard ceilings, not reservations: an idle container does not reserve 2 GiB, while a busy container may consume up to its limits. Generation and normal LocalCI use separate admission pools, so a mixed host must be sized for their combined configured ceilings. A five-job generation-only profile is not evidence that five jobs are safe beside sustained LocalCI traffic. Start with one generation slot per host, then increase one step at a time only when representative load tests preserve headroom. Size core workers, aggregate sandbox slots, normal build slots, provider concurrency, and token budgets together.
- **Cost control:** Define usage policies and rate limits with your provider. Hyperion requests can process the full problem statement, so costs scale with exercise size. Keep provider context/output limits aligned with `max-tokens-per-job`; the server token guard runs after provider responses are recorded. Provider retries and timed-out calls can consume quota without usable response metadata, so the server-side token counters are not a hard spend ceiling. The finite defaults allow several worst-case jobs but are not cost recommendations; lower them to match provider pricing and course size.
- **Multi-node ownership:** Hyperion uses shared job slots, owner heartbeats, and repository ownership checks to reduce duplicate writers. This is cooperative fencing, not a CP transaction. If a node disappears while saving, Artemis marks the run partial, releases capacity, and requires repository review before use.
- **Data protection:** Model providers receive exercise content. Obtain consent and align with institutional policies before enabling Hyperion in production.
- **Sandbox image trust:** Use only institutionally approved, immutable build images that contain no credentials. Generation refuses unbounded CPU, memory, or PID settings and disables swap, host mounts, capabilities, and networking, but the build-agent process still controls the Docker daemon and must run on a trusted host.
- **Exam safety:** Because generation shares build-agent hosts with exam builds, keep `max-generation-sandbox-slots` at 0 on exam agents (see _Build-agent placement_).
