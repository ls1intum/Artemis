# Hyperion Service

Hyperion extends Artemis with AI-assisted authoring features for programming exercises. It offers consistency checks for problem statements and exercise artefacts and can rewrite instructions with the help of generative AI. On LocalCI/LocalVC deployments it can additionally generate or adapt a complete exercise — problem statement, template, solution, and tests — with a sandboxed agent. The functionality is provided entirely by Artemis and Spring AI, so no EduTelligence service needs to be deployed.

<Callout variant={CalloutVariant.info}>
    For local development setups using LM Studio, refer to the [Spring AI Development Guide](/developer/spring-ai) in the Developer documentation.
</Callout>

## Prerequisites

- A running Artemis instance that loads the `core` profile.
- Network access to an LLM provider that is supported by Spring AI (for example OpenAI or Azure OpenAI).
- A valid API key for the chosen provider.

<Callout variant={CalloutVariant.warning}>
    <strong>
        Agentic whole-exercise generation and adaptation require the integrated LocalCI/LocalVC lifecycle (the <code>localci</code> and <code>localvc</code> profiles).
    </strong>{' '}
    They drive a resource-bounded, network-isolated sandbox on a LocalCI build agent, persist through LocalVC with a LocalCI trigger, and verify with the production LocalCI
    test/SCA parsers, so they are automatically disabled on Jenkins deployments (the endpoints are not registered and the client hides the entry points). The other Hyperion
    features — consistency check and problem-statement rewriting — do not depend on LocalCI and work with any supported CI system.
</Callout>

## Enable the Hyperion module

Hyperion is disabled by default. Activate it by overriding the `artemis.hyperion.enabled` property in the configuration that the server reads on startup (for example `application-prod.yml`).

```yaml
artemis:
    hyperion:
        enabled: true
```

This enables the general Hyperion authoring features, such as consistency checks and problem-statement rewriting. Agentic whole-exercise generation and adaptation have a separate,
off-by-default safety switch:

```yaml
artemis:
    hyperion:
        enabled: true
        exercise-generation:
            enabled: true
```

Both properties must be `true`, and the server must load the `core`, `localci`, and `localvc` profiles. Leaving `artemis.hyperion.exercise-generation.enabled` unset or `false`
keeps the whole-exercise endpoints and orchestration components unregistered without disabling the other Hyperion features.

<Callout variant={CalloutVariant.warning}>
    These two properties alone are not sufficient. Generation additionally needs a build agent that is explicitly configured to host sandboxes — see{' '}
    <a href="#configure-exercise-generation">Configure exercise generation</a>. Until then, every start request is rejected with{' '}
    <code>503 generationCapacityUnavailable</code>, including on a single-node deployment that runs the build agent in the same process.
</Callout>

Configuration flags and capacity limits are read at startup; restart the affected Artemis server and build-agent processes after changing them.

### Provider data boundary

Whole-exercise generation sends the instructor's request, problem statement, relevant repository text, and model tool observations to the configured provider. Enable it only for
courses and repositories whose contents may be processed under that provider's data policy. Keep credentials out of exercise repositories and enforce the institution's normal
secret-scanning or pre-receive controls before content reaches Artemis.

Hyperion blocks a narrow set of high-confidence credential files and token formats as defense in depth: dotenv files, well-known credential and cloud/CLI configuration files,
private-key files and keystores, PEM private-key blocks, and AWS/GitHub/GitLab token formats. This is not data-loss prevention and not an authorization boundary — generic
assignments, high-entropy strings, JWTs, and transformed or novel secrets are not recognized. The sandbox's disabled network prevents generated code from making network requests,
but it does not prevent Artemis itself from sending exercise context to the configured model provider.

## Configure Spring AI

Hyperion delegates all model interactions to Spring AI. Artemis ships the single OpenAI module (backed by the official OpenAI Java SDK), which serves OpenAI, Azure OpenAI / Microsoft Foundry, and OpenAI-compatible local servers from one configuration tree.

### OpenAI

```yaml
spring:
    ai:
        model:
            chat: openai
        openai:
            api-key: <openai-api-key>
            timeout: 5m # Connection-level HTTP timeout (default 60s); reasoning models and tool-calling loops can exceed it
            chat:
                model: gpt-5-mini # Or another (reasonably capable) model
                temperature: 1.0 # Required to be 1.0 for gpt-5
```

The OpenAI SDK owns transport retries, bounded by `spring.ai.openai.max-retries`. Hyperion itself only re-samples once when a successful response contains neither text nor tool
calls; it does not add another transport-retry layer, and `spring.ai.retry.*` is not used for OpenAI chat calls in this setup.

Set `artemis.hyperion.agent.context-window-tokens` to the provider's usable context window (the default is 128,000). Hyperion sends `max_completion_tokens` by default, sized to
leave room for reasoning-model output: 16,384 tokens per agent turn, and between 4,096 and 32,768 for a review pass depending on how much of the exercise that pass inspects. It
clamps every request to the remaining context, and fails the call rather than sending a request with too little room left.

Override the ceiling only if the provider demands it:

- If an older OpenAI-compatible endpoint accepts only `max_tokens`, set `spring.ai.openai.chat.options.max-tokens`. Hyperion then switches to that wire field.
- If the provider enforces a lower output ceiling than the defaults above, set `spring.ai.openai.chat.options.max-completion-tokens`.
- Do not set both: `max-completion-tokens` silently wins and `max-tokens` is ignored.

A configured value replaces the built-in per-turn default in both directions, so raising it also raises the agent-turn ceiling. Setting it too low does not fail loudly — review
responses are truncated, the fail-closed quality review reports itself unavailable, and runs finish as **Needs review** even when the exercise is mechanically sound.

### Azure OpenAI / Microsoft Foundry

```yaml
spring:
    ai:
        model:
            chat: openai
        openai:
            api-key: <azure-openai-api-key>
            base-url: https://<your-resource-name>.openai.azure.com
            microsoft-foundry: true # routes auth as an Azure api-key header; keep false/omitted for plain OpenAI or OpenAI-compatible endpoints
            timeout: 5m # Connection-level HTTP timeout (default 60s); reasoning models and tool-calling loops can exceed it
            chat:
                model: <azure-deployment> # the Azure deployment name; used as the request model. gpt-5-mini deployment recommended
                temperature: 1.0 # Required to be 1.0 for gpt-5
```

### Token Usage Tracking

Artemis tracks LLM token usage and costs per request. Configure model pricing under `artemis.llm.model-costs` to enable accurate cost reporting in admin dashboards.

```yaml
artemis:
    llm:
        model-costs:
            gpt-5-mini:
                input-cost-per-million-eur: 0.23
                output-cost-per-million-eur: 1.84
```

Add entries for each model you use. The key must match the model name returned by your provider (without date suffixes like `-2024-07-18`). If a model has no cost entry, costs default to zero but token counts are still recorded.

### Observability (Optional)

Enabling observability during development helps you understand how LLM-based features behave, why they produce certain outputs, and how to optimize them. Since LLMs are non-deterministic and sensitive to prompts, parameters, and context, traditional logging is often not enough.

Key benefits of adding observability:

- Full visibility into prompts, responses, parameters, and token usage
- Reproducible debugging through stored traces
- Faster prompt iteration with comparison and tracking
- Early cost and token monitoring
- Insight into multi-step pipelines and performance bottlenecks
- Primarily used in development, but can also be enabled in production environments if deeper analysis or incident debugging is required

#### Langfuse

Langfuse is a platform for observability and tracing of LLM applications and agents. It captures everything happening during an LLM interaction: inputs, outputs, tool usage, retries, latencies and costs.

#### Setup Guide

1. See how to create and setup a Langfuse account (See only "Get API keys") [here](https://langfuse.com/docs/observability/get-started).

2. Request to join a Organization from an Edutelligence maintainer.

3. You will be added to the Project as **Member**.

    > ℹ️ **Note**
    > Project Members can _use_ Langfuse and access existing API keys.
    > Only **Project Admins** can create new API keys.
    > If you cannot view API keys, ask the maintainer to generate them for you.

4. Once the Project Admin provides the **Public Key** and **Secret Key**, store them securely.
   These keys authenticate your application when sending observability data to Langfuse.

5. Identify your Langfuse host URL.
   It appears in the Langfuse UI as: **https://\<host\>**.

Your **OTLP HTTP ingestion endpoint** follows the standard OTLP HTTP spec and is constructed as:
**https://\<host\>/api/public/otel/v1/traces**

- `/api/public/otel` → Langfuse OTLP receiver root
- `/v1/traces` → Standard OTLP HTTP route
    > For more info: See how Langfuse can receive traces on the OLTP endpoint [here](https://langfuse.com/integrations/native/opentelemetry)

6. Generate the Basic Authentication token for Langfuse.
   Use Base64 encoding with the format: base64(public_key:secret_key)

Example generation command:

```bash
echo -n "<public_key>:<secret_key>" | base64
```

7. Add the OTLP endpoint and authorization header to your Spring configuration.

Use the OTLP endpoint constructed in Step 5 and the Base64 token generated in Step 6.
These values can be provided through **active Spring profile YAML** (e.g. `application-local.yaml`, `application-dev.yaml`) or via **environment variables**.

You will need to set the following properties:

- `management.otlp.tracing.endpoint` → `https://<host>/api/public/otel/v1/traces`
- `management.otlp.tracing.headers.Authorization` → `Basic <base64(public_key:secret_key)>`

To avoid committing secrets, prefer supplying these values via environment variables and referencing them in YAML.

#### Configure Langfuse

> Below is the current configuration used in development profile to view the LLM traces of Hyperion services on Langfuse.

```yaml
management:
    # Set true to display contextual name in @Observed on Langfuse
    observations:
        annotations:
            enabled: true
    # Configuration for exporting LLM traces to Langfuse (set to true to enable Artemis' custom exporter)
    langfuse:
        enabled: true
    tracing:
        sampling:
            probability: 1.0
    otlp:
        tracing:
            # LangFuse accepts OTLP over HTTP at the traces path only
            # (example: https://langfuse.aet.cit.tum.de/api/public/otel/v1/traces)
            endpoint: https://example.com
            transport: http
            headers:
                # Provide "Basic <base64(public_key:secret_key)>" via env var to avoid committing secrets
                Authorization: 'Basic <base64(public_key:secret_key)>'
            # Important: Set export.enabled: false to disable the *default* OTLP exporter.
            # Artemis uses its own custom exporter to send Spring AI LLM traces to Langfuse.
            # so disabling the default exporter will NOT stop LLM trace export.
            export:
                enabled: false
```

## Configure exercise generation

Skip this section if `artemis.hyperion.exercise-generation.enabled` is `false`. Otherwise work through all three parts — build-agent hosting, cluster topology, and admission
controls — before the feature is usable.

### Build-agent placement

Agentic exercise generation runs inside a **resource-bounded, network-isolated Docker sandbox on a LocalCI build agent**. The agent can be shared with normal LocalCI work or dedicated to generation. Each generation job uses exactly one slot and one sandbox container from workspace setup through automated checks. The container is released before repository persistence and LocalCI synchronization. Jobs can run for several minutes and consume CPU, memory, and Docker resources throughout.

Core nodes reach the sandbox over a cluster relay addressed by build-agent `short-name`. There is no direct in-process shortcut, so a deployment that runs `core` and `buildagent`
in the same JVM uses the same relay and the same per-agent capacity setting as a distributed one.

To keep generation from ever competing with exam builds by accident, **hosting is opt-in per build agent and off by default**:

```yaml
artemis:
    continuous-integration:
        # Required on a mixed host so normal LocalCI concurrency can be sized explicitly alongside generation slots.
        specify-concurrent-builds: true
        concurrent-build-size: 1
        build-agent:
            # Maximum concurrent generation jobs on this agent. Each job uses one slot and one container; 0 disables hosting (default).
            max-generation-sandbox-slots: 0
            # Keep true on normal CI agents. Set false only on dedicated Hyperion sandbox hosts that should not run student/exam builds.
            run-build-jobs: true
```

<Callout variant={CalloutVariant.warning}>
    <code>max-generation-sandbox-slots</code> defaults to <strong>0</strong>, which means the agent never hosts generation. Leave it at 0 on every exam-critical build agent. At
    least one agent in the cluster must be raised above 0 or no generation can start anywhere.
</Callout>

Generation slots and normal LocalCI build slots are separate admission limits. Artemis does not dynamically subtract one from the other. On a mixed host, set
`specify-concurrent-builds: true` and choose `concurrent-build-size` so the combined CPU and memory ceilings of normal builds and generation sandboxes fit the host.

Start with one generation slot, on a mixed non-exam agent or on a dedicated agent with `run-build-jobs: false`. Raise it one step at a time, and only after a load test
representative of the host's real mix leaves headroom in CPU pressure and throttling, build latency, memory, and Docker disk.

Additional controls:

- **Pausing a build agent** (from the LocalCI build-agent admin page) stops it accepting **new** Hyperion generation jobs, so you can drain it before maintenance or an exam. In-flight jobs keep their containers and run to completion; only normal build-job intake stops immediately.
- Orphaned sandbox containers are checked every `generation-sandbox-cleanup-interval-minutes` (default 15) and reaped after `generation-sandbox-idle-timeout-minutes` (default 90).

Every concurrently running build-agent process must have a unique `short-name`; Artemis validates its format but cannot detect a duplicate. Two live processes sharing one short
name overwrite each other's capacity advertisement, and one of them stops answering relay requests — including teardown for sandboxes it owns. Do not overlap two process
incarnations during a rolling replacement. Restarting an agent removes its prior generation containers rather than resuming them; if an agent is renamed, remove containers
associated with its previous short name manually.

### Cluster topology

Configure the expected Hazelcast data-member topology explicitly on every Artemis node before enabling exercise generation:

```yaml
jhipster:
    cache:
        hazelcast:
            expected-data-member-count: 3
```

Set this value to the exact number of core/data Hazelcast members. Do not count standalone build-agent clients or lite members. Artemis derives a strict majority from this value
for Hyperion's protected maps and checks the locally visible member count while holding the exercise's coordination lock before each generation or mutation-slot admission. A
membership change still has Hazelcast's normal failure-detection delay, so this is cooperative protection rather than a CP fence. When scaling, stop new generation, drain active
jobs, update every core node consistently, verify the complete cluster, and only then reopen admission.

### Admission controls

Agentic generation can run for several minutes and consume many model tokens. Review these server-side limits before enabling it for production courses:

## Verifying the integration

1. Restart the Artemis server and confirm that `hyperion` appears in `activeModuleFeatures` on `/management/info`.
2. Log in as an instructor and open the programming exercise problem statement editor. New Hyperion actions appear in the markdown editor toolbar (rewrite and consistency check).
3. Run a consistency check to ensure the LLM call succeeds. Inspect the server logs for `Hyperion` entries if the request fails; misconfigured credentials and missing network egress are the most common causes.

If whole-exercise generation is enabled, continue:

4. Confirm that `hyperion-exercise-generation` also appears in `activeModuleFeatures`. If it does not, the dedicated property is off or one of the `core`, `localci`, `localvc` profiles is missing.
5. Open a Java Maven programming exercise that has no student participations, no auxiliary repositories, and a release date in the future, and confirm that **Generate exercise** is offered.
6. Start one generation run end to end. A `503` at this point means no build agent is advertising a free generation slot — check `max-generation-sandbox-slots` on the agents and that they are not paused.

## Operational considerations

- **Capacity:** Sandboxes inherit the build agent's `default-docker-flags` (2 CPUs, 2 GiB memory, no container swap, and 1,000 PIDs by default), then additionally drop all capabilities, disable networking, and mount a read-only root filesystem. The resource values are hard ceilings, not reservations: an idle container does not hold 2 GiB, while a busy one may consume up to its limits. Generation and normal LocalCI use separate admission pools, so a mixed host must be sized for their combined configured ceilings, and a generation-only benchmark does not predict behaviour beside sustained LocalCI traffic. Size core workers, aggregate sandbox slots, normal build slots, provider concurrency, and token budgets together.
- **Cost control:** Define usage policies and rate limits with your provider. Hyperion requests can process the full problem statement, so costs scale with exercise size. Keep provider context/output limits aligned with `max-tokens-per-job`; the server token guard runs after provider responses are recorded. If completed usage cannot be recorded, or a worker disappears while provider usage is uncertain, Hyperion retains the worst-case reservation for the configured budget window. Provider retries and timed-out calls can still consume quota without returning a response, so server-side counters are not a hard spend ceiling. The finite defaults allow several worst-case jobs but are not cost recommendations; lower them to match provider pricing and course size.
- **Multi-node ownership:** Hyperion uses shared job slots, owner heartbeats, and repository ownership checks to reduce duplicate writers. This is cooperative fencing, not a CP transaction. If a node disappears while saving, Artemis marks the run partial, releases capacity, and requires repository review before use.
- **Break-glass recovery:** External mutation slots never expire automatically because the original HTTP, SSH, Git, or database writer cannot be fenced by Hazelcast membership alone. Before calling the admin recovery endpoint, terminate the recorded owner process, verify repository and database activity has stopped, restore the configured Hazelcast topology, and inspect the affected exercise. Recovery requires the exact slot token plus a nonblank incident reason, and it only proceeds once the owning node is gone from the cluster. A persistent audit event is written before the slot is removed; if audit persistence fails, recovery remains blocked.
- **Data protection:** Model providers receive exercise content. Obtain consent and align with institutional policies before enabling Hyperion in production. `artemis.hyperion.agent.transcript-dir` additionally writes prompts, repository file contents, and tool output to local disk without redaction; leave it unset outside deliberate debugging, and treat any such directory as sensitive.
- **Sandbox image trust:** Use only institutionally approved, immutable build images that contain no credentials. Generation refuses unbounded CPU, memory, or PID settings and disables swap, host mounts, capabilities, and networking, but the build-agent process still controls the Docker daemon and must run on a trusted host.
- **Exam safety:** Because generation shares build-agent hosts with exam builds, keep `max-generation-sandbox-slots` at 0 on exam agents (see _Build-agent placement_).
