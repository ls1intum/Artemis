# Hyperion Service

Hyperion provides consistency checks, problem-statement rewriting, and whole-exercise generation for programming exercises. It runs in Artemis using Spring AI; no separate Hyperion service is required. Whole-exercise generation uses a Docker container on a LocalCI build agent to write and test the statement, template, solution, and tests before saving them.

<Callout variant={CalloutVariant.info}>
    For local development setups using LM Studio, refer to the [Spring AI Development Guide](/developer/spring-ai) in the Developer documentation.
</Callout>

## Prerequisites

For all Hyperion features:

- A running Artemis instance that loads the `core` profile.
- Network access to an LLM provider that is supported by Spring AI (for example OpenAI or Azure OpenAI).
- A valid API key for the chosen provider.

Whole-exercise generation and adaptation additionally require:

- The `core`, `localci`, and `localvc` profiles together on the generation core nodes. Jenkins is not supported for whole-exercise generation.
- Hazelcast for a multi-node deployment. Redis/Valkey does not expose the data-node topology required by generation admission, so requests fail closed with `hyperionDataMemberTopologyUnavailable`. The local distributed-data backend is limited to a single process.
- At least one LocalCI build agent with generation capacity allocated, as described under [Allocate generation capacity](#allocate-generation-capacity).
- A **Java** exercise with Maven tests (`PLAIN_MAVEN`, `MAVEN_MAVEN`, or the legacy unset project type). Gradle and other project types/languages are rejected with `400 unsupportedGenerationLanguage`.
- New AI-created exercises always use `PLAIN_MAVEN`: plain Java student sources and a Maven test project. `MAVEN_MAVEN` additionally gives the student source repositories Maven projects; it remains eligible for existing exercises but is not a choice in the AI creation flow. These names describe repository layouts, not whether a Maven wrapper is used.
- The configured Java LocalCI image must contain the Maven toolchain. With the default offline network policy it also needs a complete dependency cache; with approved outbound access Maven can resolve missing dependencies. See [Sandbox networking and build images](#sandbox-networking-and-build-images).

Consistency checks and problem-statement rewriting do not require LocalCI generation capacity.

## Enable Hyperion

Whole-exercise generation is off by default. Enable both core-node feature flags and allocate capacity on at least one build agent.

Configuration flags and capacity limits are read at startup; restart the affected Artemis server and build-agent processes after changing them.

### Step 1: enable the module on core nodes

Override `artemis.hyperion.enabled` in the configuration that the server reads on startup (for example `application-prod.yml`). This activates the authoring features that need no CI integration — consistency checks and problem-statement rewriting:

```yaml
artemis:
    hyperion:
        enabled: true
```

Whole-exercise generation and adaptation sit behind a second, separately off-by-default switch. Both properties must be `true`, and the node must load the `core`, `localci`, and `localvc` profiles:

```yaml
artemis:
    hyperion:
        enabled: true
        exercise-generation:
            enabled: true
```

Both feature flags ship as `false`. Leaving the exercise-generation flag disabled keeps its endpoints and orchestration components unregistered without disabling other Hyperion features.

### Step 2: allocate generation capacity on build agents

The properties above make the feature available; they do not make it runnable. A LocalCI build agent hosts generation sandboxes only if it has been given capacity explicitly,
through `artemis.continuous-integration.build-agent.max-generation-sandbox-slots`, which defaults to `0`. Raise it on at least one agent — see
[Allocate generation capacity](#allocate-generation-capacity) for the full configuration, sizing guidance, and exam-safety considerations.

<Callout variant={CalloutVariant.warning}>
    <strong>A deployment with no allocated capacity anywhere never runs a generation job.</strong> Every start request is rejected with{' '}
    <code>503 generationCapacityUnavailable</code>, and the <code>hyperionGenerationCapacity</code> health component reports <code>DOWN</code>. This applies equally to a
    single-node deployment that runs the build agent in the same process: core nodes always reach the sandbox through the cluster relay, so there is no in-process shortcut around
    the setting.
</Callout>

## Provider data boundary

Whole-exercise generation sends the instructor's request, problem statement, relevant repository text, and model tool observations to the configured provider. Enable it only for
courses and repositories whose contents may be processed under that provider's data policy. Keep credentials out of exercise repositories and enforce the institution's normal
secret-scanning or pre-receive controls before content reaches Artemis.

As defense in depth, Hyperion refuses to read a narrow set of high-confidence credential files and token formats: dotenv files (`.env`, `.env.*`), well-known credential and
cloud/CLI configuration files (for example `.npmrc`, `.netrc`, `.git-credentials`, `.aws/credentials`, `.docker/config.json`, `.kube/config`), private-key files and keystores
(`id_rsa` and siblings, `.key`, `.p12`, `.pfx`, `.jks`, `.keystore`), PEM private-key blocks, AWS access key IDs, and GitHub and GitLab personal access tokens. This is not
data-loss prevention and not an authorization boundary — generic assignments, high-entropy strings, JWTs, AWS secret keys, and transformed or novel secrets are not recognized.
The default offline network policy prevents container egress, but does not prevent Artemis from sending exercise context to the configured model provider. With outbound networking enabled, shell commands and generated code can also contact destinations permitted by the deployment firewall; container isolation alone does not prevent data exfiltration.

## Configure Spring AI

Hyperion delegates all model interactions to Spring AI. Artemis ships the single OpenAI module (backed by the official OpenAI Java SDK), which serves OpenAI, Azure OpenAI / Microsoft Foundry, and OpenAI-compatible local servers from one configuration tree.

### OpenAI

```yaml
spring:
    ai:
        model:
            chat: openai
        openai:
            api-key: <openai-api-key>
            # Provider request timeout, applied to both the SDK clients and model request options.
            # A chat-specific spring.ai.openai.chat.timeout overrides this value.
            timeout: 5m
            chat:
                model: gpt-5-mini # Or another (reasonably capable) model
                temperature: 1.0 # Required to be 1.0 for gpt-5
```

The OpenAI SDK owns transport retries, bounded by `spring.ai.openai.max-retries` (Artemis ships `1`, so a call is attempted at most twice; the default timeout is long enough that
the SDK default would multiply it). Hyperion itself only re-samples once when a successful response contains neither text nor tool calls; it does not add another transport-retry
layer, and `spring.ai.retry.*` is not used for OpenAI chat calls in this setup.

Set `artemis.hyperion.agent.context-window-tokens` to the provider's usable context window (the default is 128,000). Hyperion sizes the completion allowance of every request
against that value: it subtracts the estimated prompt plus a safety margin, caps the remainder at a built-in per-call ceiling, and fails the call rather than sending a request
that leaves too little room for a complete response. The ceilings are generous because they must also cover a reasoning model's hidden output — 16,384 tokens for an agent turn
and 32,768 for a review pass.

Override the ceiling only if the provider demands it:

- If an older OpenAI-compatible endpoint accepts only `max_tokens`, set `spring.ai.openai.chat.options.max-tokens`. Hyperion then switches to that wire field.
- If the provider enforces a lower output ceiling than the built-in ones, set `spring.ai.openai.chat.options.max-completion-tokens`.
- Do not set both: `max-completion-tokens` silently wins and `max-tokens` is ignored.

A configured value caps review passes and _replaces_ the built-in agent-turn ceiling, so raising it also raises what a single agent turn may spend. Setting it too low does not
fail loudly — review responses are truncated, the fail-closed quality review reports itself unavailable, and runs finish as **Needs review** even when the exercise is
mechanically sound.

### Azure OpenAI / Microsoft Foundry

```yaml
spring:
    ai:
        model:
            chat: openai
        openai:
            api-key: <azure-openai-api-key>
            base-url: https://<your-resource-name>.openai.azure.com
            # Routes auth as an Azure api-key header. Auto-detected for *.openai.azure.com base URLs; set it explicitly
            # for a custom domain, and keep it false or omitted for plain OpenAI and OpenAI-compatible endpoints.
            microsoft-foundry: true
            timeout: 5m # Default for provider requests
            chat:
                model: <azure-deployment> # The Azure deployment name; used as the request model. A gpt-5-mini deployment is recommended
                temperature: 1.0 # Required to be 1.0 for gpt-5
```

### Token usage tracking

Artemis tracks LLM token usage per request and estimates cost only from prices supplied by the deployment operator. No prices are built in because provider rates and currencies
change independently of an Artemis release. Record the rate source and retrieval time in your deployment or evaluation evidence, then configure the corresponding EUR rates under
`artemis.llm.model-costs`.

```yaml
artemis:
    llm:
        model-costs:
            # A key containing a dot must be bracket-quoted, for example "[gpt-5.4]".
            my-model-name:
                input-cost-per-million-eur: 0.23
                output-cost-per-million-eur: 1.84
                cached-input-cost-per-million-eur: 0.05 # Required for a complete estimate when cache-read tokens are nonzero
```

The key must match the model name your provider returns. Date suffixes such as `-2024-07-18` are stripped before the lookup, and so is every other non-alphanumeric character, so
`gpt-5.4` and its environment-variable form `GPT54` resolve to the same entry — which is also why configuring one model both in YAML and through an environment variable fails at
startup. A model with no matching complete price is recorded with a zero estimate marked incomplete; token accounting remains available and a warning names the configured keys.

### Observability (optional)

The filtered GenAI exporter sends spans marked `ai.span=true` to an OTLP/HTTP-compatible backend. Content capture is **off by default**. Enabling Langfuse opts in unless
`artemis.telemetry.gen-ai.capture-content` is explicitly set to `false`; other OTLP collectors require setting it to `true`. Prompts, completions, reasoning, and tool content are
then attached to spans. Protect the collector and apply an appropriate retention policy before turning it on.

For Langfuse, create or obtain project API keys as described in the [Langfuse OpenTelemetry guide](https://langfuse.com/integrations/native/opentelemetry). Its trace endpoint is
`https://<host>/api/public/otel/v1/traces`. Generate the required Basic authentication value without storing the keys in the repository:

```bash
echo -n "<public_key>:<secret_key>" | base64
```

```yaml
artemis:
    telemetry:
        gen-ai:
            capture-content: false # Set true only for an approved, protected collector
            max-attribute-bytes: 2000000 # Ceiling for one serialized content attribute, in UTF-8 bytes
management:
    langfuse:
        enabled: true
    tracing:
        sampling:
            probability: 1.0
        export:
            otlp:
                enabled: false # Avoid duplicate export through Spring Boot's unfiltered exporter
    opentelemetry:
        tracing:
            export:
                otlp:
                    endpoint: https://<host>/api/public/otel/v1/traces
                    headers:
                        Authorization: 'Basic <base64(public_key:secret_key)>'
```

Supply the endpoint and authorization header through deployment secrets. The corresponding property names are
`management.opentelemetry.tracing.export.otlp.endpoint` and `management.opentelemetry.tracing.export.otlp.headers.Authorization`; `management.langfuse.enabled=true` registers the
filtered exporter.

`max-attribute-bytes` bounds one serialized content attribute. A span whose content exceeds it keeps its metadata, loses that attribute, and is marked
`artemis.gen_ai.content.complete=false`. Size the limit together with the collector’s actual request-size limit; a request may contain multiple attributes and spans.

## Configure exercise generation

Skip this section if `artemis.hyperion.exercise-generation.enabled` is `false`. Otherwise work through generation capacity, cluster topology, and admission controls before the
feature is usable.

### Allocate generation capacity

Agentic exercise generation runs inside a **resource-bounded Docker sandbox on a LocalCI build agent**. The agent can be shared with normal LocalCI work or dedicated to generation. Each generation job uses exactly one slot and one sandbox container from workspace setup through automated checks. The container is released before repository persistence and LocalCI synchronization. Jobs can run for several minutes and consume CPU, memory, and Docker resources throughout.

Generation requires a **Docker-backed build agent** (`artemis.continuous-integration.build-runner=docker`). Kubernetes-backed LocalCI builds remain supported independently, but the interactive generation sandbox has no Kubernetes implementation; do not allocate generation slots on Kubernetes-only agents.

#### Distributed-store upgrade

This feature changes the build-agent registration wire format and replaces the legacy code-generation job record. Distributed-data schema version 2 migrates from version 1 through the standard Redis/Valkey startup migrator. Queued/running student builds, unprocessed results, feature toggles, and expiring Pyris jobs are carried over without changing their wire format or resetting their lifetime. Agent registrations and legacy generation jobs are discarded and re-created as appropriate. There is no relational database migration.

Drain in-flight generation before upgrading and follow the [distributed-store upgrade procedure](./production-setup/distributed-data.mdx#prepare-an-upgrade); mixed old/new schema nodes must not process different namespaces concurrently. Terminal replay is not a durable archive: export any evidence that must survive deployment.

Core nodes reach the sandbox over a cluster relay addressed by the build agent's `short-name`. There is no direct in-process shortcut, so a deployment that runs `core` and
`buildagent` in the same JVM uses the same relay and the same per-agent capacity setting as a distributed one.

**Hosting is opt-in per build agent.** Configure only the agents selected for generation:

```yaml
artemis:
    continuous-integration:
        build-agent:
            # Maximum concurrent generation jobs on this agent. Each job takes one slot and one container; 0 (the default) disables hosting.
            max-generation-sandbox-slots: 1
            # Keep true on normal CI agents. Set false only on dedicated Hyperion sandbox hosts that should not run student or exam builds.
            run-build-jobs: true
            # Orphaned sandbox containers are checked on this interval and reaped once idle for longer than the timeout.
            generation-sandbox-cleanup-interval-minutes: 15
            generation-sandbox-idle-timeout-minutes: 90
```

<Callout variant={CalloutVariant.warning}>
    Leave <code>max-generation-sandbox-slots</code> at <strong>0</strong> on every exam-critical build agent, and raise it above 0 on at least one other agent — otherwise no
    generation can start anywhere in the cluster.
</Callout>

Generation slots and normal LocalCI build slots are separate admission limits; Artemis does not dynamically subtract one from the other. On a host that serves both, size them
together — set `artemis.continuous-integration.specify-concurrent-builds: true` and choose `artemis.continuous-integration.concurrent-build-size` so that the combined CPU and
memory ceilings of normal builds and generation sandboxes fit the host. Without `specify-concurrent-builds`, the normal build pool is derived from the available processors and
does not account for sandboxes at all.

Prefer a dedicated generation host with `run-build-jobs: false`; do not place it on the same resource-constrained machine as exam agents. One slot is a conservative starting point, not a system limit. Increase capacity after testing representative load, including CPU throttling, memory, disk use, and student-build latency on any shared host.

### Cluster topology

Configure the expected Hazelcast data-member topology explicitly on every Artemis node before enabling exercise generation:

```yaml
jhipster:
    cache:
        hazelcast:
            expected-data-member-count: 3
```

Set this value to the exact number of core/data Hazelcast members. Do not count standalone build-agent clients or lite members. Artemis compares it against the locally visible
member count while holding the exercise's coordination lock before each generation or mutation-slot admission, and rejects the request with `503
hyperionDataMemberTopologyMismatch` when the two differ. [Wedged-slot recovery](#recovering-a-wedged-exercise) uses a weaker rule — a strict majority — for the reason explained
there. A membership change still has Hazelcast's normal failure-detection delay, so this is cooperative protection rather than a CP fence. When scaling, stop new generation,
drain active jobs, update every core node consistently, verify the complete cluster, and only then reopen admission.

### Admission controls

Agentic generation can run for several minutes and consume many model tokens. Review these server-side limits before enabling it for production courses.

Startup validation requires: `max-job-duration` must be positive,
`owner-heartbeat-interval` must be positive and shorter than it, `stale-job-timeout` must exceed the longest `max-job-duration` of the deployment default and of every effort
profile, and `max-semantic-repairs` must be between 1 and 12. Effort profiles are also validated at startup. Some other settings are validated when their component is first used; verify a generation request before opening the feature to instructors.

| Property                                                        | Default      | Purpose                                                                                                                                                                                                    |
| --------------------------------------------------------------- | ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `jhipster.cache.hazelcast.expected-data-member-count`           | `1`          | Expected Hazelcast data members, excluding build-agent clients and lite members. Admission requires the exact count.                                                                                       |
| `artemis.hyperion.generation.max-concurrent-jobs-per-core-node` | `2`          | Worker limit per core, without a queue or automatic redistribution to another core. Must be at least 1.                                                                                                    |
| `artemis.hyperion.agent.max-job-duration`                       | `PT45M`      | Cooperative deadline before saving starts. Saving and LocalCI synchronization may exceed it; bound provider and build timeouts separately.                                                                 |
| `artemis.hyperion.agent.context-window-tokens`                  | `128000`     | Usable model context window, including prompt and completion headroom.                                                                                                                                     |
| `artemis.hyperion.agent.max-turns`                              | `60`         | Model-turn cap per attempt, not per generation run.                                                                                                                                                        |
| `artemis.hyperion.agent.max-semantic-repairs`                   | `6`          | Quality-repair rounds; 1–12. Higher values increase the possible run duration.                                                                                                                             |
| `artemis.hyperion.agent.max-tokens-per-job`                     | `3000000`    | Per-job token guard and rolling-budget reservation. Checked after provider responses; a verified candidate can still be saved when exhausted.                                                              |

| `artemis.hyperion.agent.admission-max-tokens-per-course`        | `120000000`  | Per-course rolling limit; same validation as the per-user limit.                                                                                                                                           |
| `artemis.hyperion.agent.admission-max-tokens-global`            | `600000000`  | Global rolling limit; same validation as the per-user limit.                                                                                                                                               |
| `artemis.hyperion.agent.owner-heartbeat-interval`               | `PT15S`      | Ownership heartbeat interval. Positive and shorter than max-job-duration.                                                                                                                                  |
| `artemis.hyperion.agent.stale-job-timeout`                      | `PT50M`      | Must exceed every profile’s max-job-duration. Stale live owners are asked to stop; cancellable slots are reclaimed after owner departure. Saving, revert, and external-edit slots require manual recovery. |
| `artemis.hyperion.agent.stale-job-scan-ms`                      | `60000`      | Stale-slot scan interval in milliseconds; independent of per-job deadlines.                                                                                                                                |
| `artemis.hyperion.agent.provider-hard-failure-cooldown`         | `PT5M`       | Cluster-wide cooldown after provider quota, billing, authentication, or model-configuration failures. Ordinary rate limits and 5xx responses do not open it.                                               |
| `artemis.hyperion.generation.test-case-sync-timeout`            | `PT10M`      | Maximum wait for LocalCI test-case synchronization, including queueing. Timeout produces PARTIAL and disables automatic undo.                                                                              |
| `artemis.hyperion.generation.test-case-sync-poll`               | `PT3S`       | Polling interval for LocalCI synchronization.                                                                                                                                                              |
| `artemis.hyperion.generation.terminal-replay-ttl`               | `PT4H`       | Lifetime of a finished run’s bounded status events, specification, file changes, and usage. Positive; not a durable conversation archive.                                                                  |

| `artemis.hyperion.agent.staged-generation`                      | `true`       | Stage specification, executable artifacts, then statement. Applies to GENERATE; an existing authoritative statement skips specification authoring.                                                         |
| `artemis.hyperion.agent.staged-context`                         | `CONTINUOUS` | CONTINUOUS retains context between specification and executable authoring; FRESH starts each stage without prior conversation. Statement authoring always starts fresh.                                    |
| `artemis.hyperion.agent.transcript-dir`                         | unset        | Optional local Markdown conversation snapshots. May contain compacted history; sensitive, not a complete per-call archive.                                                                                 |

### Effort profiles

Named effort profiles inherit unspecified values from the deployment defaults. No profiles are configured by default.

```yaml
artemis:
    hyperion:
        agent:
            default-profile: standard # Used when a request names none. Must name one of the profiles below.
            profiles:
                draft:
                    label: 'Quick draft'
                    model: gpt-5-mini
                    max-turns: 20
                    max-job-duration: PT12M
                    max-tokens-per-job: 600000
                standard:
                    label: 'Standard' # Uses deployment defaults.
                thorough:
                    label: 'Thorough'
                    model: gpt-5.4
                    max-turns: 90
                    max-job-duration: PT48M # Must stay below stale-job-timeout; raise that first to go higher.
                    max-tokens-per-job: 6000000
                    context-window-tokens: 256000 # Set to the deployed model/proxy context limit.
```

Also settable per profile: `temperature`, `top-p`, `reasoning-effort`, `verbosity`, `max-completion-tokens`, `staged-generation`, and `staged-context`.

Admins define, users select. A request may send only a profile **name** from this set, plus `maxTokens` and `maxJobDuration` bounds that can lower a ceiling but never raise one.
The profile listing returns names and labels only; run status and usage can expose applied settings and model identifiers to the run owner. A name this deployment does not configure is rejected with `400
unknownEffortProfile` rather than silently falling back to the default.

The whole set is validated at startup: at most 20 profiles, names matching `[a-z][a-z0-9_]{0,63}`, labels at most 100 characters, positive durations and token ceilings,
`temperature` in [0, 2], `top-p` in [0, 1], and provider-valid `reasoning-effort` and `verbosity`. Two cross-property constraints apply: raising `max-job-duration` on any profile
requires raising `stale-job-timeout` above it, and raising `max-tokens-per-job` on any profile raises the floor every enabled admission budget is validated against.

## Verifying the integration

1. Restart the Artemis server and confirm that `hyperion` appears in `activeModuleFeatures` on `/management/info`.
2. Log in as an instructor and open the programming exercise problem statement editor. The Hyperion actions (rewrite and consistency check) appear in the Markdown editor toolbar.
3. Run a consistency check to ensure the LLM call succeeds. Inspect the server logs for `Hyperion` entries if the request fails; misconfigured credentials and missing network egress are the most common causes.

If whole-exercise generation is enabled, continue:

4. Confirm that `hyperion-exercise-generation` also appears in `activeModuleFeatures`. If it does not, the dedicated property is off or one of the `core`, `localci`, `localvc` profiles is missing.
5. Check that `/management/health` reports the `hyperionGenerationCapacity` component as `UP` — see [Health and capacity](#health-and-capacity).
6. Open a Java Maven programming exercise that has no student participations and no auxiliary repositories, and confirm that **Generate exercise** is offered. The date on which students could first participate — start date, else release date, else the exam's start date — must be set and in the future; an exercise with no such date counts as already released and is rejected.
7. Start one generation run end to end. If it is rejected, look the error key up under [Why a generation request was rejected](#why-a-generation-request-was-rejected).

## Creating an exercise from a brief

In course administration, instructors provide a brief; Artemis derives a title, difficulty, and valid course-specific identifiers. New drafts use Java with `PLAIN_MAVEN`, 10 points, and a future release date. Metadata inference has a deterministic fallback. Draft creation uses the normal exercise API and retries a conflicting derived name once.

The draft already exists before generation starts. If starting fails, the dialog offers retry on that same exercise or deletion of the unused draft, preserving the brief. Generated content is saved only after verification. On the first successful generation into a blank statement, a valid level-one heading can update the title; repository identifiers and package remain unchanged. Existing exercises retain their instructor-assigned title. Undo restores the pre-save title.

Instructors must review the generated content, settings, and release date before release. **Run again** starts a new run, not a continuation, and asks for the brief or adaptation feedback again. Earlier instructions and selected review comments are not carried over. A draft without an authoritative problem statement requires a brief.

## Sandbox networking and build images

Networking is an operator policy, not an instructor or model choice. The default remains `none`. To allow Maven downloads and HTTP access from agent tools, configure the same policy on generation core nodes and all build agents that can execute generation or its LocalCI synchronization builds:

```yaml
artemis:
    continuous-integration:
        build-agent:
            generation-sandbox-network: hyperion-egress
```

`hyperion-egress` must be an existing Docker **bridge-driver** network on each eligible host. The interactive sandbox resolves it to its network ID and rejects non-bridge drivers, host networking, and joining another container's network namespace. A session may explicitly request `none` for stricter isolation; it cannot select an arbitrary network. Synchronization builds use the configured network and continue to strip exercise-provided environment variables. Restart the affected core and build-agent processes after changing the policy.

Use a dedicated [user-defined Docker bridge](https://docs.docker.com/engine/network/drivers/bridge/), not the shared default bridge, in production. A Docker bridge is not an outbound firewall; follow the guidance for [Docker-aware firewall rules](https://docs.docker.com/engine/network/firewall-iptables/) appropriate to the host backend. Before enabling access, provision host/network controls that deny internal services, host management endpoints, cloud metadata, and other tenants, and permit only the destinations your institution approves. Do not attach generation containers to the Artemis/database control-plane network. Restrict inbound and inter-container traffic too. An HTTP proxy alone is insufficient if direct outbound traffic remains possible. Ordinary LocalCI system-proxy settings may apply to synchronization builds; do not expose credential-bearing proxy configuration to untrusted code. Interactive sessions do not automatically inherit those proxy environment variables.

For a dependency-only policy, permit the approved Maven repositories or an institutional mirror. A broader internet policy can also let the agent consult public documentation through its existing shell tools, but there is no separate web-search API or search-provider integration. Availability depends on the image's HTTP tools and network policy. Retrieved pages and tool output are untrusted; the agent is instructed not to transmit exercise contents or credentials and not to make graded tests depend on live services. These instructions are not an egress enforcement mechanism. Broader access changes the privacy, supply-chain, and reproducibility boundary and requires institutional approval.

**Build-image choices:**

- With `none`, use an approved image with the complete Maven dependency/plugin cache required by the deployed templates. Refresh that image when the templates change.
- With outbound dependency access, a compatible Maven image can fetch missing artifacts into the sandbox's bounded, private writable repository. It does not need every template dependency baked in. This removes a dependency on a particular cache-warming image release; it does not remove toolchain compatibility, repository availability, or artifact provenance requirements.
- Use the normal [Artemis build-image project](https://github.com/ls1intum/artemis-maven-docker) or an institutionally maintained image, scan it, publish it, and configure `artemis.continuous-integration.build.images.java.default` with its immutable digest. This setting also affects ordinary Java builds. Do not downgrade security pins or mount a shared mutable host cache to compensate for an unsuitable image.

Verify the selected image and policy together:

```bash
HYPERION_TEST_JAVA_BUILD_IMAGE=registry.example.edu/artemis-java@sha256:<digest> \
HYPERION_TEST_SANDBOX_NETWORK=hyperion-egress \
  ./gradlew test --tests '*HyperionBuildReadinessDockerIntegrationTest' -x webapp
```

Omit `HYPERION_TEST_SANDBOX_NETWORK` for the offline policy. Require all four Maven readiness cases to execute and pass. These tests use the production exercise templates without rewriting their POMs to fit the image; image/build incompatibilities fail rather than being skipped. Only local environments without Docker may skip. Also verify normal LocalCI synchronization, denied internal-network access, and the explicit offline mode on the target deployment. For reproducible evaluation, pin the network policy and dependency source along with the image and Artemis revisions.

## Operating exercise generation

### Health and capacity

`/management/health` exposes a `hyperionGenerationCapacity` component on every core node with exercise generation enabled. Core nodes ship `show-details: when_authorized`, so
authenticate as an admin to see its details.

```json
"hyperionGenerationCapacity": {
    "status": "UP",
    "details": {
        "generationSandboxCapacity": "GenerationSandboxCapacity[reachableAgents=3, hostingAgents=1, totalSlots=1, reservedSlots=0]"
    }
}
```

- `reachableAgents` counts every build agent currently `ACTIVE` or `IDLE`. A paused agent is excluded from all four numbers and is not a placement candidate.
- `hostingAgents` counts those with `max-generation-sandbox-slots` above 0. **`hostingAgents=0` is reported as `DOWN`** with a hint naming the property, because unlike a merely
  busy fleet it never resolves on its own. The same condition is logged once at startup and, rate-limited to one message every five minutes, whenever a request is rejected for it.
- `totalSlots` minus `reservedSlots` is the number of runs that can still start. When it reaches 0 the component stays `UP` with a hint: the fleet is configured correctly and
  merely saturated.
- `DOWN` with a hint about a missing relay client means the node cannot address build agents at all — check that it loads the `localci` profile.

Admins can additionally list a specific agent's live sandboxes with `GET /api/admin/build-agents/{agentName}/generation-sandboxes`, and cancel a run through its job API rather than deleting the Docker container directly
with `DELETE /api/admin/exercises/{exerciseId}/hyperion-generation-jobs/{jobId}/cancel`.

### Recovering a wedged exercise

Three kinds of coordination slot are never released by the automatic stale-job scan, because losing cluster membership does not prove the writer stopped: `GENERATION` past its
point of no return (saving to Git and the database), `REVERT`, and `EXTERNAL_MUTATION` (an authorized REST edit). If the owning node dies inside one of these, the slot stays
claimed and blocks generation, revert **and** ordinary REST edits of that exercise indefinitely. Recovery is a deliberate, audited operator action:

1. Read the slot, which is the only way to obtain the token recovery requires:

    ```bash
    curl -u <admin> https://<artemis-host>/api/admin/exercises/<exerciseId>/hyperion-wedged-slot
    ```

    The response reports `token`, `kind`, `ownerNodeId`, `startedAt`, and `ownerLeftCluster`. A 404 means the exercise has no slot requiring manual recovery.

2. Terminate the process named by `ownerNodeId` and confirm its Git and database activity has stopped. Cluster departure alone is not sufficient evidence — a partitioned node
   can still be writing.
3. Restore the configured Hazelcast topology and inspect the exercise's repositories.
4. Release the slot with the exact token and a non-blank incident reason:

    ```bash
    curl -u <admin> -X DELETE \
      "https://<artemis-host>/api/admin/exercises/<exerciseId>/hyperion-wedged-slots/<token>?reason=<incident>"
    ```

    `204` means recovered, `400` a blank reason, `404` no matching slot — including the case where the token is stale because a newer owner has since claimed the exercise. A
    persistent audit event carrying the admin login, token, kind, owner, and reason is written before the slot is removed; if audit persistence fails, recovery is blocked. A
    recovered generation slot is terminalized like a stale one, so the instructor sees that the run stopped and is warned to review the repositories.

<Callout variant={CalloutVariant.warning}>
    Recovery requires a strict majority of <code>expected-data-member-count</code> to be visible, so that a minority island cannot clear a slot whose owner is merely partitioned
    away. <strong>A two-member deployment therefore cannot self-recover</strong>: the majority of 2 is 2, and one of the two is by definition the dead owner. Restore a member, or
    run three data members, before you need this.
</Callout>

### Draining a build agent

Pausing a build agent from the LocalCI build-agent admin page stops it accepting **new** Hyperion generation jobs, so you can drain it before maintenance or an exam. Sandboxes
that are already running keep their containers and stay fully usable; the relay continues to serve their commands. Normal build-job intake stops immediately, and running build
jobs are cancelled and re-queued after the configured pause grace period. A process shutdown, unlike a pause, does destroy the agent's sandbox sessions.

### Build-agent identity

Every concurrently running build-agent process must have a unique `artemis.continuous-integration.build-agent.short-name`. Artemis validates the format (lowercase letters,
digits, and hyphens) at startup but cannot detect a duplicate. Two live processes sharing one short name overwrite each other's capacity advertisement, and one of them stops
answering relay requests — including teardown for sandboxes it owns. Do not overlap two process incarnations during a rolling replacement. Restarting an agent removes its prior
generation containers rather than resuming them; if an agent is renamed, remove containers associated with its previous short name manually.

## Security posture

Generated code is untrusted and is executed. Container hardening limits host access; network reachability is a separate operator policy. Neither Docker nor the model instructions prove that arbitrary generated code is safe.

What the sandbox enforces, on top of the resource limits from `artemis.continuous-integration.build.default-docker-flags` — the same flags normal LocalCI builds use (2 CPUs,
2 GiB memory with swap disabled, and 1,000 PIDs by default):

- **Operator-owned networking.** Default `none`; an explicitly configured Docker bridge may provide outbound access. Sessions cannot select an arbitrary network. Deployment firewalls, not Docker filesystem isolation, enforce destination restrictions.
- **No capabilities and no privilege escalation.** All Linux capabilities are dropped and `no-new-privileges` is set.
- **Read-only root filesystem.** Writes are possible only in bounded `tmpfs` mounts: `/workspace` and `/tmp` at 512 MiB each, `/opt/hyperion` at 256 MiB, a 64 MiB readiness
  fixture, and 256 MiB for each volume path the image declares. Nothing survives a container restart.
- **No host paths and no secrets.** The sandbox binds no host directory, receives no Artemis credentials, and is created from an immutable image ID rather than a mutable tag.
- **Fail-closed startup.** A sandbox refuses to start unless CPU, memory, and PID limits are all positive and memory-swap equals memory, and it declines images that declare more
  than 16 volumes or a volume under `/`, `/proc`, `/sys`, or `/dev`.

What it is **not**:

- Not protection from a compromised Docker daemon or build-agent host. Container escapes can compromise the host and other workloads. Use dedicated hosts where required, and approved images without credentials.
- Not a data-protection boundary towards the model provider. Exercise content leaves Artemis over the network before the sandbox is involved at all — see
  [Provider data boundary](#provider-data-boundary).
- Not a guarantee that the generated exercise is correct or pedagogically sound. Verification is differential and mechanical; instructors review before release.

## Operational considerations

### Core-node shutdown

The core handling a generation owns its running model conversation; another core does not resume that conversation after failure. Shared status remains available while its retention window and distributed store survive. If an owner leaves before saving starts, the stale-job scan stops the run and releases its cancellable slot; a stale heartbeat from a still-present owner requests cancellation without handing its slot to another writer.

During graceful shutdown, the generation executor stops accepting work and interrupts runs that have not started saving. It waits up to `shutdown-drain-timeout` for in-flight saves, then interrupts any remaining workers. Allow enough process-termination time for this drain. A forced kill bypasses it. If an owner disappears while saving, the coordination slot stays claimed: follow [Recovering a wedged exercise](#recovering-a-wedged-exercise), rather than starting a replacement writer.

### Evidence and privacy

There are three different records:

- **Run status:** bounded events, usage, specification, and file changes retained for `terminal-replay-ttl`. This supports reconnecting to a run; it is not a full model conversation archive.
- **Local conversation snapshots:** optional `artemis.hyperion.agent.transcript-dir` Markdown files. They include prompts, repository content, and tool output from finished sessions, but earlier messages may have been compacted. Protect the directory and manage retention; do not publish these files as ordinary CI artifacts.
- **Per-call OTel evidence:** enable content capture only for an approved collector. Check sampling, delivery, content limits, and completeness attributes before treating it as a complete record. Metadata-only spans cannot reconstruct the conversation.

For evaluation with [exgen-bench](https://github.com/ls1intum/exgen-bench), use its [Artemis adapter](https://github.com/ls1intum/exgen-bench/blob/main/adapters/artemis/README.md) against the authenticated production APIs. Pin both repositories, model configuration, build image, network policy, and dependency sources. Export required evidence before its retention expires. There is no benchmark-only generation API or replay service in Artemis.

Set `spring.ai.openai.max-retries: 0` when exact provider accounting is required. With SDK retries enabled, Artemis conservatively reports accounting as `INCOMPLETE`; missing usage must not be interpreted as zero. Content completeness and usage completeness are separate checks. Mocked-model integration tests validate execution and persistence contracts, not the quality of generated exercises.

### Cost limits

Size core workers, sandbox slots, normal build slots, provider concurrency, and token budgets together. Docker limits are ceilings, not reserved resources. A generation-only load test does not establish that a shared host can handle simultaneous student builds.

Provider retries and timed-out calls may consume tokens without returning usage. Hyperion checks its token guard after responses, so it is not a hard monetary ceiling. Configure provider-side spending limits too. Uncertain accounting retains the worst-case admission reservation for the budget window. Price estimates require operator-supplied rates and are not invoices.
