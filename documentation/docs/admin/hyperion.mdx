# Hyperion Service

Hyperion extends Artemis with AI-assisted authoring features for programming exercises. It checks problem statements and exercise artefacts for consistency and rewrites instructions with the help of generative AI. Where the Integrated Code Lifecycle is in use, it can additionally generate or adapt a complete exercise — problem statement, template, solution, and tests — with a sandboxed agent. The functionality is provided entirely by Artemis and Spring AI, so no EduTelligence service needs to be deployed.

<Callout variant={CalloutVariant.info}>
    For local development setups using LM Studio, refer to the [Spring AI Development Guide](/developer/spring-ai) in the Developer documentation.
</Callout>

## Prerequisites

For all Hyperion features:

- A running Artemis instance that loads the `core` profile.
- Network access to an LLM provider that is supported by Spring AI (for example OpenAI or Azure OpenAI).
- A valid API key for the chosen provider.

Whole-exercise generation and adaptation additionally require:

- The `localci` and `localvc` profiles on the same node. Generation drives a resource-bounded, network-isolated sandbox on a LocalCI build agent, persists through LocalVC with a LocalCI trigger, and verifies with the production LocalCI test and static-code-analysis parsers. There is no equivalent path for external CI systems, so on a Jenkins deployment the endpoints are never registered and the client hides the entry points.
- At least one LocalCI build agent with generation capacity allocated, as described under [Allocate generation capacity](#allocate-generation-capacity).

Consistency checks and problem-statement rewriting have neither requirement and work with any supported CI system.

## Enable Hyperion

Every Hyperion feature is off by default. Whole-exercise generation needs **two independent opt-ins that live on different node types**, and both are mandatory.

Configuration flags and capacity limits are read at startup; restart the affected Artemis server and build-agent processes after changing them.

### Step 1: enable the module on core nodes

Override `artemis.hyperion.enabled` in the configuration that the server reads on startup (for example `application-prod.yml`). This activates the authoring features that need no CI integration — consistency checks and problem-statement rewriting:

```yaml
artemis:
    hyperion:
        enabled: true
```

Whole-exercise generation and adaptation sit behind a second, separately off-by-default switch. Both properties must be `true`, and the node must load the `core`, `localci`, and `localvc` profiles:

```yaml
artemis:
    hyperion:
        enabled: true
        exercise-generation:
            enabled: true
```

Leaving `artemis.hyperion.exercise-generation.enabled` unset or `false` keeps the whole-exercise endpoints and orchestration components unregistered without disabling the other Hyperion features.

### Step 2: allocate generation capacity on build agents

The properties above make the feature available; they do not make it runnable. A LocalCI build agent hosts generation sandboxes only if it has been given capacity explicitly,
through `artemis.continuous-integration.build-agent.max-generation-sandbox-slots`, which defaults to `0`. Raise it on at least one agent — see
[Allocate generation capacity](#allocate-generation-capacity) for the full configuration, sizing guidance, and exam-safety considerations.

<Callout variant={CalloutVariant.warning}>
    <strong>A deployment with no allocated capacity anywhere never runs a generation job.</strong> Start requests that reach the capacity check are rejected with{' '}
    <code>503 generationCapacityUnavailable</code>. This applies equally to a single-node deployment that runs the build agent in the same process: core nodes always reach the
    sandbox through the cluster relay, so there is no in-process shortcut around the setting.
</Callout>

## Provider data boundary

Whole-exercise generation sends the instructor's request, problem statement, relevant repository text, and model tool observations to the configured provider. Enable it only for
courses and repositories whose contents may be processed under that provider's data policy. Keep credentials out of exercise repositories and enforce the institution's normal
secret-scanning or pre-receive controls before content reaches Artemis.

As defense in depth, Hyperion refuses to read a narrow set of high-confidence credential files and token formats: dotenv files (`.env`, `.env.*`), well-known credential and
cloud/CLI configuration files (for example `.npmrc`, `.netrc`, `.git-credentials`, `.aws/credentials`, `.docker/config.json`, `.kube/config`), private-key files and keystores
(`id_rsa` and siblings, `.key`, `.p12`, `.pfx`, `.jks`, `.keystore`), PEM private-key blocks, AWS access key IDs, and GitHub and GitLab personal access tokens. This is not
data-loss prevention and not an authorization boundary — generic assignments, high-entropy strings, JWTs, AWS secret keys, and transformed or novel secrets are not recognized.
The sandbox's disabled network prevents generated code from making network requests, but it does not prevent Artemis itself from sending exercise context to the configured model
provider.

## Configure Spring AI

Hyperion delegates all model interactions to Spring AI. Artemis ships the single OpenAI module (backed by the official OpenAI Java SDK), which serves OpenAI, Azure OpenAI / Microsoft Foundry, and OpenAI-compatible local servers from one configuration tree.

### OpenAI

```yaml
spring:
    ai:
        model:
            chat: openai
        openai:
            api-key: <openai-api-key>
            # HTTP client request timeout (default 60s); reasoning models and tool-calling loops can exceed it.
            # It must be set at this level: the chat-level timeout key does not reach the HTTP client.
            timeout: 5m
            chat:
                model: gpt-5-mini # Or another (reasonably capable) model
                temperature: 1.0 # Required to be 1.0 for gpt-5
```

The OpenAI SDK owns transport retries, bounded by `spring.ai.openai.max-retries` (Artemis ships `1`, so a call is attempted at most twice; the default timeout is long enough that
the SDK default would multiply it). Hyperion itself only re-samples once when a successful response contains neither text nor tool calls; it does not add another transport-retry
layer, and `spring.ai.retry.*` is not used for OpenAI chat calls in this setup.

Set `artemis.hyperion.agent.context-window-tokens` to the provider's usable context window (the default is 128,000). Hyperion sizes the completion allowance of every request
against that value: it subtracts the estimated prompt plus a safety margin, caps the remainder at a built-in per-call ceiling, and fails the call rather than sending a request
that leaves too little room for a complete response. The ceilings are generous because they must also cover a reasoning model's hidden output — 16,384 tokens for an agent turn
and 32,768 for a review pass.

Override the ceiling only if the provider demands it:

- If an older OpenAI-compatible endpoint accepts only `max_tokens`, set `spring.ai.openai.chat.options.max-tokens`. Hyperion then switches to that wire field.
- If the provider enforces a lower output ceiling than the built-in ones, set `spring.ai.openai.chat.options.max-completion-tokens`.
- Do not set both: `max-completion-tokens` silently wins and `max-tokens` is ignored.

A configured value caps review passes and *replaces* the built-in agent-turn ceiling, so raising it also raises what a single agent turn may spend. Setting it too low does not
fail loudly — review responses are truncated, the fail-closed quality review reports itself unavailable, and runs finish as **Needs review** even when the exercise is
mechanically sound.

### Azure OpenAI / Microsoft Foundry

```yaml
spring:
    ai:
        model:
            chat: openai
        openai:
            api-key: <azure-openai-api-key>
            base-url: https://<your-resource-name>.openai.azure.com
            # Routes auth as an Azure api-key header. Auto-detected for *.openai.azure.com base URLs; set it explicitly
            # for a custom domain, and keep it false or omitted for plain OpenAI and OpenAI-compatible endpoints.
            microsoft-foundry: true
            timeout: 5m # As above; must be set at this level
            chat:
                model: <azure-deployment> # The Azure deployment name; used as the request model. A gpt-5-mini deployment is recommended
                temperature: 1.0 # Required to be 1.0 for gpt-5
```

### Token Usage Tracking

Artemis tracks LLM token usage and cost per request. A small set of models ships with seeded prices; add an entry under `artemis.llm.model-costs` for any other model you use, or
to override a seeded price.

```yaml
artemis:
    llm:
        model-costs:
            # A key containing a dot must be bracket-quoted, for example "[gpt-5.4]".
            my-model-name:
                input-cost-per-million-eur: 0.23
                output-cost-per-million-eur: 1.84
```

The key must match the model name your provider returns. Date suffixes such as `-2024-07-18` are stripped before the lookup, and so is every other non-alphanumeric character, so
`gpt-5.4` and its environment-variable form `GPT54` resolve to the same entry — which is also why configuring one model both in YAML and through an environment variable fails at
startup. A model with no matching entry is recorded with zero cost and logs a warning naming the keys it does know.

### Observability (Optional)

Enabling observability during development helps you understand how LLM-based features behave, why they produce certain outputs, and how to optimize them. Since LLMs are non-deterministic and sensitive to prompts, parameters, and context, traditional logging is often not enough.

Key benefits of adding observability:

- Full visibility into prompts, responses, parameters, and token usage
- Reproducible debugging through stored traces
- Faster prompt iteration with comparison and tracking
- Early cost and token monitoring
- Insight into multi-step pipelines and performance bottlenecks
- Primarily used in development, but can also be enabled in production environments if deeper analysis or incident debugging is required

#### Langfuse

Langfuse is a platform for observability and tracing of LLM applications and agents. It captures everything happening during an LLM interaction: inputs, outputs, tool usage, retries, latencies and costs.

#### Setup Guide

1. See how to create and setup a Langfuse account (See only "Get API keys") [here](https://langfuse.com/docs/observability/get-started).

2. Request to join a Organization from an Edutelligence maintainer.

3. You will be added to the Project as **Member**.

    > ℹ️ **Note**
    > Project Members can _use_ Langfuse and access existing API keys.
    > Only **Project Admins** can create new API keys.
    > If you cannot view API keys, ask the maintainer to generate them for you.

4. Once the Project Admin provides the **Public Key** and **Secret Key**, store them securely.
   These keys authenticate your application when sending observability data to Langfuse.

5. Identify your Langfuse host URL.
   It appears in the Langfuse UI as: **https://\<host\>**.

Your **OTLP HTTP ingestion endpoint** follows the standard OTLP HTTP spec and is constructed as:
**https://\<host\>/api/public/otel/v1/traces**

- `/api/public/otel` → Langfuse OTLP receiver root
- `/v1/traces` → Standard OTLP HTTP route
    > For more info: See how Langfuse can receive traces on the OLTP endpoint [here](https://langfuse.com/integrations/native/opentelemetry)

6. Generate the Basic Authentication token for Langfuse.
   Use Base64 encoding with the format: base64(public_key:secret_key)

Example generation command:

```bash
echo -n "<public_key>:<secret_key>" | base64
```

7. Add the OTLP endpoint and authorization header to your Spring configuration.

Use the OTLP endpoint constructed in Step 5 and the Base64 token generated in Step 6.
These values can be provided through **active Spring profile YAML** (e.g. `application-local.yaml`, `application-dev.yaml`) or via **environment variables**.

You will need to set the following properties:

- `management.otlp.tracing.endpoint` → `https://<host>/api/public/otel/v1/traces`
- `management.otlp.tracing.headers.Authorization` → `Basic <base64(public_key:secret_key)>`

To avoid committing secrets, prefer supplying these values via environment variables and referencing them in YAML.

#### Configure Langfuse

> Below is the current configuration used in development profile to view the LLM traces of Hyperion services on Langfuse.

```yaml
management:
    # Set true to display contextual name in @Observed on Langfuse
    observations:
        annotations:
            enabled: true
    # Configuration for exporting LLM traces to Langfuse (set to true to enable Artemis' custom exporter)
    langfuse:
        enabled: true
    tracing:
        sampling:
            probability: 1.0
    otlp:
        tracing:
            # LangFuse accepts OTLP over HTTP at the traces path only
            # (example: https://langfuse.aet.cit.tum.de/api/public/otel/v1/traces)
            endpoint: https://example.com
            transport: http
            headers:
                # Provide "Basic <base64(public_key:secret_key)>" via env var to avoid committing secrets
                Authorization: 'Basic <base64(public_key:secret_key)>'
            # Important: Set export.enabled: false to disable the *default* OTLP exporter.
            # Artemis uses its own custom exporter to send Spring AI LLM traces to Langfuse.
            # so disabling the default exporter will NOT stop LLM trace export.
            export:
                enabled: false
```

## Configure exercise generation

Skip this section if `artemis.hyperion.exercise-generation.enabled` is `false`. Otherwise work through all three parts — generation capacity, cluster topology, and admission
controls — before the feature is usable.

### Allocate generation capacity

Agentic exercise generation runs inside a **resource-bounded, network-isolated Docker sandbox on a LocalCI build agent**. The agent can be shared with normal LocalCI work or dedicated to generation. Each generation job uses exactly one slot and one sandbox container from workspace setup through automated checks. The container is released before repository persistence and LocalCI synchronization. Jobs can run for several minutes and consume CPU, memory, and Docker resources throughout.

Core nodes reach the sandbox over a cluster relay addressed by the build agent's `short-name`. There is no direct in-process shortcut, so a deployment that runs `core` and
`buildagent` in the same JVM uses the same relay and the same per-agent capacity setting as a distributed one.

So that generation can never compete with exam builds by accident, **hosting is opt-in per build agent and off by default**. Set this on the build agents that should host
sandboxes:

```yaml
artemis:
    continuous-integration:
        build-agent:
            # Maximum concurrent generation jobs on this agent. Each job takes one slot and one container; 0 (the default) disables hosting.
            max-generation-sandbox-slots: 1
            # Keep true on normal CI agents. Set false only on dedicated Hyperion sandbox hosts that should not run student or exam builds.
            run-build-jobs: true
            # Orphaned sandbox containers are checked on this interval and reaped once idle for longer than the timeout.
            generation-sandbox-cleanup-interval-minutes: 15
            generation-sandbox-idle-timeout-minutes: 90
```

<Callout variant={CalloutVariant.warning}>
    Leave <code>max-generation-sandbox-slots</code> at <strong>0</strong> on every exam-critical build agent, and raise it above 0 on at least one other agent — otherwise no
    generation can start anywhere in the cluster.
</Callout>

Generation slots and normal LocalCI build slots are separate admission limits; Artemis does not dynamically subtract one from the other. On a host that serves both, size them
together — set `artemis.continuous-integration.specify-concurrent-builds: true` and choose `artemis.continuous-integration.concurrent-build-size` so that the combined CPU and
memory ceilings of normal builds and generation sandboxes fit the host. Without `specify-concurrent-builds`, the normal build pool is derived from the available processors and
does not account for sandboxes at all.

Start with one generation slot, on a mixed non-exam agent or on a dedicated agent with `run-build-jobs: false`. Raise it one step at a time, and only after a load test
representative of the host's real mix leaves headroom in CPU pressure and throttling, build latency, memory, and Docker disk.

**Draining an agent.** Pausing a build agent from the LocalCI build-agent admin page stops it accepting **new** Hyperion generation jobs, so you can drain it before maintenance
or an exam. Sandboxes that are already running keep their containers and run to completion. Normal build-job intake stops immediately, and running build jobs are cancelled and
re-queued after the configured pause grace period.

**Agent identity.** Every concurrently running build-agent process must have a unique `artemis.continuous-integration.build-agent.short-name`; Artemis validates its format but
cannot detect a duplicate. Two live processes sharing one short name overwrite each other's capacity advertisement, and one of them stops answering relay requests — including
teardown for sandboxes it owns. Do not overlap two process incarnations during a rolling replacement. Restarting an agent removes its prior generation containers rather than
resuming them; if an agent is renamed, remove containers associated with its previous short name manually.

### Cluster topology

Configure the expected Hazelcast data-member topology explicitly on every Artemis node before enabling exercise generation:

```yaml
jhipster:
    cache:
        hazelcast:
            expected-data-member-count: 3
```

Set this value to the exact number of core/data Hazelcast members. Do not count standalone build-agent clients or lite members. Artemis derives a strict majority from this value
for Hyperion's protected maps and checks the locally visible member count while holding the exercise's coordination lock before each generation or mutation-slot admission. A
membership change still has Hazelcast's normal failure-detection delay, so this is cooperative protection rather than a CP fence. When scaling, stop new generation, drain active
jobs, update every core node consistently, verify the complete cluster, and only then reopen admission.

## Verifying the integration

1. Restart the Artemis server and confirm that `hyperion` appears in `activeModuleFeatures` on `/management/info`.
2. Log in as an instructor and open the programming exercise problem statement editor. The Hyperion actions (rewrite and consistency check) appear in the Markdown editor toolbar.
3. Run a consistency check to ensure the LLM call succeeds. Inspect the server logs for `Hyperion` entries if the request fails; misconfigured credentials and missing network egress are the most common causes.

If whole-exercise generation is enabled, continue:

4. Confirm that `hyperion-exercise-generation` also appears in `activeModuleFeatures`. If it does not, the dedicated property is off or one of the `core`, `localci`, `localvc` profiles is missing.
5. Open a Java Maven programming exercise that has no student participations, no auxiliary repositories, and a start or release date in the future, and confirm that **Generate exercise** is offered.
6. Start one generation run end to end. A `503 generationCapacityUnavailable` at this point means no build agent is advertising a free generation slot — check `max-generation-sandbox-slots` on the agents and that they are not paused.

## Operational considerations

- **Capacity:** Sandboxes inherit the resource limits from `artemis.continuous-integration.build.default-docker-flags`, the same flags normal LocalCI builds use (2 CPUs, 2 GiB memory with swap disabled, and 1,000 PIDs by default), then additionally drop all capabilities, disable networking, mount a read-only root filesystem with bounded `tmpfs` scratch space, and set `no-new-privileges`. The resource values are hard ceilings, not reservations: an idle container does not hold 2 GiB, while a busy one may consume up to its limits. Generation and normal LocalCI use separate admission pools, so a mixed host must be sized for their combined configured ceilings, and a generation-only benchmark does not predict behaviour beside sustained LocalCI traffic. Size core workers, aggregate sandbox slots, normal build slots, provider concurrency, and token budgets together.
- **Cost control:** Define usage policies and rate limits with your provider. Hyperion requests can process the full problem statement, so costs scale with exercise size. Keep provider context/output limits aligned with `max-tokens-per-job`; the server token guard runs after provider responses are recorded. If completed usage cannot be recorded, or a worker disappears while provider usage is uncertain, Hyperion retains the worst-case reservation for the configured budget window. Provider retries and timed-out calls can still consume quota without returning a response, so server-side counters are not a hard spend ceiling. The finite defaults allow several worst-case jobs but are not cost recommendations; lower them to match provider pricing and course size.
- **Multi-node ownership:** Hyperion uses shared job slots, owner heartbeats, and repository ownership checks to reduce duplicate writers. This is cooperative fencing, not a CP transaction. If a node disappears while saving, Artemis marks the run partial, releases capacity, and requires repository review before use.
- **Break-glass recovery:** External mutation slots never expire automatically, because the original HTTP, SSH, Git, or database writer cannot be fenced by Hazelcast membership alone. The admin recovery endpoint is `DELETE /api/admin/exercises/{exerciseId}/hyperion-external-mutations/{token}?reason={incidentReason}`. Before calling it, terminate the recorded owner process, verify repository and database activity has stopped, restore the configured Hazelcast topology, and inspect the affected exercise. Recovery requires the exact slot token plus a nonblank incident reason, and it only proceeds once the owning node is gone from the cluster. A persistent audit event is written before the slot is removed; if audit persistence fails, recovery remains blocked.
- **Data protection:** Model providers receive exercise content. Obtain consent and align with institutional policies before enabling Hyperion in production. `artemis.hyperion.agent.transcript-dir` additionally writes prompts, repository file contents, and tool output to local disk without redaction; leave it unset outside deliberate debugging, and treat any such directory as sensitive.
- **Sandbox image trust:** Use only institutionally approved, immutable build images that contain no credentials. A sandbox refuses to start unless CPU, memory, and PID limits are all positive and swap is disabled (memory-swap equal to memory), it never binds host paths, and it declines images that declare unsafe volumes. But the build-agent process still controls the Docker daemon and must run on a trusted host.
- **Exam safety:** Because generation shares build-agent hosts with exam builds, keep `max-generation-sandbox-slots` at 0 on exam agents (see [Allocate generation capacity](#allocate-generation-capacity)).
