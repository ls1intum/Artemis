The error analysis shows which errors happen on your Artemis installation, on the server and in the browsers of your users, without a separate monitoring service. Open it under **Administration > Error Analysis**.

## What the page shows

Errors that are alike are one row. A row has the severity, the location (**Server** or **Client**), the message, how often the error happened in the selected time span, when it happened first, and when it happened last. The most frequent errors come first. Numbers, identifiers, UUIDs and email addresses in a message are replaced by placeholders, so `Could not find exercise 17` and `Could not find exercise 42` are one row with the message `Could not find exercise <n>`.

The filters above the table select the time span (last day, last week or last month, the last day by default), the location (all by default) and the least serious errors to show. The severity is a minimum: **Error**, the default, shows errors and critical errors, **Warning** adds warnings, and **Critical** shows only the errors that stop the application from working at all. The time when an error happened first is the first time since the server started, so it can be earlier than the selected time span.

## Where the errors come from

The server counts every warning and error that it writes to its log, with the name of the logger as part of the message, and the type of the exception if there is one. The errors of the clients are the reports that the browsers send, see [Client Error Reports](/admin/client-error-reports). A hint, which a client reports with the severity `INFO`, is not an error and is not counted.

## What to know before you rely on it

Nothing is stored in the database, so the analysis cannot fill it, and it needs no maintenance. The counts live in the distributed data of the cluster, the same store that Artemis uses for its other shared state, so every core node answers with the errors of all core nodes. The answer is computed again each time you open the page or change a filter, and the browser is told not to cache it. A node collects the errors that it sees in memory and hands them to the cluster every ten seconds (`artemis.error-analysis.flush-interval`), so an error that happened on another node can take that long to appear. The node that answers adds what it collected itself.

How long the counts survive depends on the distributed data provider. With **Hazelcast**, the default, they are lost when the whole cluster stops, and they survive the restart of a single node as long as another node keeps running. With **Redis** they survive a restart of the cluster. With the **Local** provider of a single node they are lost when the node restarts. In every case an entry expires 30 days after its error happened last, and the analysis keeps at most the 1000 groups that were seen most recently. Only core nodes hand over their errors, so the errors of a build agent are not counted. The page says all this, because a quiet page is not proof that nothing went wrong. For the full history, use the log of your deployment.
