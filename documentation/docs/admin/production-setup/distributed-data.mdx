This page explains how to upgrade an Artemis installation that uses Redis or Valkey for distributed data. It is
intended for system administrators. Developers changing data stored in the distributed provider should follow the
[developer guideline](/developer/guidelines/distributed-data#changing-a-stored-type).

## When this procedure applies

The procedure applies when `artemis.distributed-data.provider` is set to `Redis`. Valkey implements the Redis protocol
and follows the same procedure. Redis and Valkey persist queues, maps, sets, and other shared state across an Artemis
restart. Hazelcast does not retain this data after its cluster stops and therefore needs no persistent-data migration.

Artemis assigns a schema version to its Redis or Valkey data. Stored structures use versioned keys such as
`artemis:v2:{buildJobQueue}`. The metadata keys are deliberately readable without an Artemis-specific codec:

```text
artemis:distributed-data-schema
artemis:distributed-data-schema:release
```

The first Artemis release with this mechanism treats existing unversioned data as schema version `0` and migrates it
to schema version `1` during startup. A release declaring a later schema runs every step in between during the same
startup, so a store that has never been migrated goes from `0` through `1` to the version the release expects.

## Prepare an upgrade

<Callout variant={CalloutVariant.warning}>

  Do not perform a rolling upgrade across distributed-data schema versions. Stop every old Artemis core node and every
  old build-agent node that uses the same Redis or Valkey store before starting the new release. An old node does not
  know about the new namespace and can continue writing to legacy keys after the migration has finished.

</Callout>

1. Schedule a maintenance window in which no Artemis or build-agent node uses the distributed store.
2. Stop every Artemis core node and every build-agent node connected to that store.
3. Prevent process supervisors or orchestration platforms from restarting an old node automatically.
4. Create and retain a consistent Redis or Valkey backup according to the product's backup procedure.
5. Verify that no old Artemis process remains connected.
6. Start one core node with the new Artemis release and wait until it is ready.
7. Verify the migration as described below.
8. Start the remaining core and build-agent nodes with exactly the same Artemis release.

Starting several new nodes together is safe because they coordinate migration with a distributed lock. Starting one
node first makes failures and migration progress easier to diagnose.

## What the migration preserves

Every migration moves the data that cannot be reconstructed safely. The initial schema `0` to `1` migration carries
these structures:

| Structure | Why it is preserved |
|---|---|
| `buildJobQueue` | Contains queued student builds. |
| `processingJobs` | Tracks builds that are already assigned to an agent. |
| `buildResultQueue` | May contain results that have not yet reached the database. |
| `features` | Contains runtime feature-toggle changes made by an administrator. |
| `pyris-job-map` | Tracks in-flight Iris jobs and their remaining expiry time. |

`deferredBuildResultQueue` was introduced after schema `1`. It holds results awaiting exercise result-processing admission;
future schema migrations must preserve it alongside `buildResultQueue`. Deferred results remain visible in the admin
result-queue listing and are retried every five seconds without queue-listener events. The admin clear operation
clears both result queues. Before downgrading to a release without deferred-result support, let the current release
drain both queues; the older release cannot process the deferred queue.

Result writers share 256 named permits per exercise across the cluster. Deletion closes admission, cancels builds and
waits for every permit before removing exercise data; ordinary results can otherwise be graded concurrently. A deletion
that cannot drain writers within one 60-second acquisition deadline returns HTTP 503 before cleanup starts. Retry it
after active processing finishes. Deferred results and follow-ups resume after a failed deletion if the exercise remains.
The permits use the configured provider's ordinary AP locks and inherit their partition limitations.

Do not mix this permit protocol with an earlier release that used one result-processing mutex: stop all old core
processes before starting replacements, including any core that can process results or delete exercises. Keep admission
closed during the transition. Neither the retained result queues nor the distributed-data schema needs to be cleared.

### Schema `1` to `2`

Schema `2` stores the class of every test in the build result. Both result queues hold build results in the old layout, which
the new release cannot read, so the migration **discards** them: `buildResultQueue` and `deferredBuildResultQueue`.
A finished build whose result had not yet been written to the database at the moment of the upgrade loses its feedback,
and the student needs a new build (a new push, or a retrigger by the instructor). To avoid this, wait until both queues are empty before you stop
the old nodes; the build agent overview shows them. The structures whose types did not change move over unchanged:

| Structure | Why it is preserved |
|---|---|
| `buildJobQueue` | Contains queued student builds. |
| `processingJobs` | Tracks builds that are already assigned to an agent. |
| `features` | Contains runtime feature-toggle changes made by an administrator. |
| `pyris-job-map-v2` | Tracks in-flight Iris jobs and their remaining expiry time. |

Everything else starts empty, as in the first migration. A store that has never been migrated goes through `0` and `1` and
ends at `2` in the same startup.

Other distributed structures start empty in the initial schema `0` to `1` migration. They contain reconstructible or transient state such as
build-agent registrations, websocket presence, caches, and topic messages. A user whose short-lived operation was in
progress, for example an LTI launch, may need to retry it after the maintenance window.

Entries are moved incrementally, and the schema version is published only after migration finishes. If the migrating
node stops, start it again with the same new release. The migration resumes safely.

## Verify the migration

The first new node logs messages similar to:

```text
Distributed store predates schema versions, treating its contents as version 0
Migrating distributed data from schema version 0 to 1
Distributed data is now at schema version 1
```

A store that is already at a numbered version logs only the steps that are still missing.

Read the metadata with `redis-cli` or the equivalent `valkey-cli` commands:

```bash
redis-cli GET artemis:distributed-data-schema
redis-cli GET artemis:distributed-data-schema:release
redis-cli --scan --pattern 'artemis:v2:*'
```

The first command must report the schema expected by the release. The second reports the Artemis release that last
completed a migration. Use `SCAN`, not `KEYS`, when inspecting a production store.

Do not edit the schema metadata or move keys manually. A node refuses to start when it encounters malformed metadata,
a newer schema, or a schema for which the release has no adjacent migration. Resolve the version mismatch instead of
bypassing this protection.

## Rollback

<Callout variant={CalloutVariant.danger}>

  Rolling back the Artemis binaries does not roll back distributed data. A previous release cannot use the migrated
  namespace. Restore the Redis or Valkey backup taken before the upgrade before starting any previous-release node.

</Callout>

Stop all new nodes before restoring the backup. Never let old and new Artemis releases use the restored store at the
same time.

## Types that Artemis reads from the store

Both distributed data providers, Hazelcast and Redis or Valkey, only create objects of known types when they read a
stored value. A class name found in the store that is not on the list is refused before the class is loaded, and the
read fails with the message `Type <name> is not allowed in the distributed data store`. Hazelcast reports its own
message, `Resolving class <name> is not allowed`. Artemis logs the refused name on the Redis or Valkey provider.

The filter only restricts what is read. It does not change how values are written, the stored format or the schema
version, so the migration described on this page is not affected. A mixed-version rollout needs one precaution: the result
of a failed build job carries the exception of the failure with its causes, and an updated build agent replaces causes of
types outside the list (for example a Git client exception of a failed clone) by plain exceptions before it publishes them.
A build agent that is not updated yet still publishes the original types, and an updated core node refuses to read them.
Update the build agents before or together with the core nodes. If an old agent can still publish results, or such a result
is already queued, wait until the result queues are empty, or add the missing prefix, for example `org.eclipse.jgit.`, to
`artemis.distributed-data.additional-allowed-types` until all agents are updated.

The default list contains:

| Entries                                                                                  | Reason                                                       |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| `de.tum.cit.aet.artemis.` (everything below this prefix)                                 | Queue items, DTO records, enums and cache values of Artemis  |
| `java.util.`, `java.time.`, `java.math.`                                                 | Collections, dates and numbers inside those records          |
| A fixed set of `java.lang` classes, for example `String`, the number types and `Throwable` | Values and exceptions held by stored records                 |
| `org.springframework.security.web.webauthn.api.`                                         | Passkey registration options                                 |
| `org.springframework.security.oauth2.core.`                                              | Pending OpenID Connect sign-in requests                      |
| `com.nimbusds.jose.`                                                                     | Signing keys of the LTI key set                              |
| `com.github.dockerjava.api.exception.`                                                   | Exceptions of failed build jobs                              |
| Two Spring cache markers, `NullValue` and `SimpleKey`                                    | A cached `null` and a composite cache key                    |
| `com.hazelcast.`, `io.github.bucket4j.` (Hazelcast only)                                 | Classes that Hazelcast and the rate limiter store themselves |

Types outside the default list, such as those in `java.net` or most of `java.io`, are refused. Most
installations need no change. If a plugin or a locally patched Artemis stores additional types, add them with the
property `artemis.distributed-data.additional-allowed-types`. It takes a comma separated list. An entry that ends with
a dot allows every type below that prefix, any other entry allows exactly one class:

```yaml
artemis:
    distributed-data:
        additional-allowed-types: org.example.extension., org.example.other.StoredValue
```

Set the property identically on all core nodes and build agents, because every node reads values that another node
wrote. A change takes effect when the node restarts.

## Legacy keys after the first migration

The migration removes entries from the unversioned structures that it preserves. Other unversioned keys can remain
because the legacy namespace covered the entire Redis or Valkey keyspace and cannot be deleted safely with one pattern.
They are no longer read by the new release and do not prevent startup.

Do not run a broad wildcard deletion, especially when the store is shared with another application. After the upgrade
and its backup-retention period, an administrator may inventory and remove known obsolete Artemis keys according to the
installation's normal change procedure.

## Redis does not need a service registry

Artemis nodes using Redis discover shared state through Redis and do not use Eureka to form the distributed-data
cluster. A Redis deployment therefore does not need a JHipster Registry. This differs from Hazelcast, where Artemis
uses the registry to discover cluster members.
