AI Worker runs bounded, explicitly installed workloads outside the Artemis server.
The worker has no database connection, repository credentials, incoming HTTP server,
or Hazelcast/Redis membership. Artemis core coordinates execution through a separate
TLS Apache Artemis broker. Workload-specific authorization and persistence remain in
the owning feature; [Hyperion](/admin/hyperion#whole-exercise-generation-workers) owns
exercise generation and its teaching-quality review.

## Deployment topology

| Environment             | Recommended placement                                 | Required separation                                                                              |
| ----------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Staging                 | Dedicated worker VM with one execution slot initially | Separate broker accounts, image qualification, model credentials and budgets from production     |
| Production              | Dedicated worker VM or host                           | No core, database, LocalVC or exam-critical build services on the worker host                    |
| Small test installation | Separate VM on the same physical machine              | Independent Docker daemon and restricted network; never mount the core/build-agent Docker socket |

The supervisor's Docker socket grants control over its daemon and potentially its
host. Running the supervisor as an unprivileged container does not remove that
privilege. A separate rootful daemon on the core host is **not** equivalent to VM
isolation. An explicitly isolated daemon is an advanced test-only deployment option;
its host and network isolation must be established outside the application.

Generated-code containers use network `none`, a read-only root filesystem, dropped
capabilities, `no-new-privileges`, and bounded CPU, memory, processes and writable
scratch mounts. They never receive the Docker socket or provider/broker credentials.
Restrict supervisor egress to approved broker, model, registry and telemetry endpoints.
Block database, repository/NFS, management and cloud-metadata access.

## Broker provisioning

Use the matching application release's
[broker configuration](https://github.com/ls1intum/Artemis/blob/develop/docker/aiworker/broker.xml).
The sample provisions `worker-1`, a private TLS CORE listener on **61617**, persistent
queues and a bounded dead-letter policy. It is not the browser STOMP broker.

- Give core only the `aiworker-core` role. Give `worker-1` only the `aiworker-1` role.
- Pre-create `aiworker.<worker-id>.commands` and `aiworker.<worker-id>.events` with
  exact per-worker ACLs. Duplicate the sample's addresses and ACLs for additional IDs.
- Workers consume only their commands and send only their events. Core has the inverse
  permissions. Neither account creates queues or accesses broker management.
- Supply `aiworker.keyStorePath` and `aiworker.keyStorePassword` to the broker JVM.
  Trust the issuing CA in both application JVMs; require hostname verification.
- Monitor `aiworker.dead-letter`, persistent broker storage and address limits.
  Do not use wildcard worker credentials or place passwords in connection URLs.

## Core configuration

Enable coordination only on a `core` node. The worker pool is independent of whether
Hyperion is enabled:

```yaml
artemis:
    aiworker:
        enabled: true
        broker-url: tcp://worker-broker.example:61617?sslEnabled=true&verifyHost=true
        user: ${AI_WORKER_CORE_BROKER_USER}
        password: ${AI_WORKER_CORE_BROKER_PASSWORD}
        ids: [worker-1]
        presence-ttl: PT30S
        lease-ttl: PT45S
```

Use the same authoritative `DistributedDataProvider` and worker configuration on all
coordinators. Presence and slot reservations have explicit lifetimes on both Hazelcast
and Redis. A claim is bound to execution UUID, worker incarnation, slot, workload
schema/profile and immutable image. Stale events cannot release a replacement claim.
Workload resource identifiers are opaque to AI Worker.

For Hyperion, all exercise writers must additionally satisfy its
[coordination and recovery requirements](/admin/hyperion#whole-exercise-generation-workers).
Redis/Valkey is not a disposable cache: use synchronous AOF (`appendonly yes`,
`appendfsync always`, `no-appendfsync-on-rewrite no`) and `maxmemory-policy noeviction`.
Automatic asynchronous failover is not qualified for ownership-sensitive persistence.
Never flush or replace the store under running writers.

## Worker configuration

Choose the distribution for the installed workload:

| Distribution | Build | Image recipe |
| --- | --- | --- |
| Generic supervisor (no Hyperion adapter or model provider) | `:aiworker:bootJar` → `modules/aiworker/build/libs/aiworker.jar` | `docker/aiworker/worker.Dockerfile` |
| Hyperion authoring | `:hyperion:worker:bootJar` → `modules/hyperion/worker/build/libs/hyperion-worker.jar` | `docker/hyperion/worker.Dockerfile` |

For `hyperion-generation`, deploy the **Hyperion distribution**, not the bare supervisor.
Both images run the same AI Worker lifecycle as UID 1000 with the same transport contract. Preload a qualified, digest-pinned sandbox image on the isolated daemon.
Configuration files containing secrets must be readable only by the deployment account
and worker UID, and mounted read-only.

```yaml
spring:
    main:
        web-application-type: none
    artemis:
        mode: native
        broker-url: tcp://worker-broker.example:61617?sslEnabled=true&verifyHost=true
        user: ${AI_WORKER_BROKER_USER}
        password: ${AI_WORKER_BROKER_PASSWORD}
artemis:
    aiworker:
        id: worker-1
        image: registry.example/hyperion-java-gradle@sha256:<qualified-digest>
        workload: hyperion-generation
        workload-version: 1
        profile: java-gradle
        max-concurrent-executions: 1
        runtime: runc
        memory-bytes: 2147483648
        cpu-quota: 200000
        pids: 256
        heartbeat-interval: PT10S
        connection-grace: PT45S
        shutdown-timeout: PT2M
```

Replace the digest placeholder with the image's actual 64-digit SHA-256 digest.
The environment-based entry point also accepts `AI_WORKER_ID`, `AI_WORKER_SANDBOX_IMAGE`,
`AI_WORKER_WORKLOAD`, `AI_WORKER_PROFILE` and `AI_WORKER_BROKER_{URL,USER,PASSWORD}`.
A mounted Spring configuration can supply the corresponding properties directly.

Each process selects **one installed workload capability** and one image. Scale different
workloads/profiles with separate worker identities. An identifier does not install an
implementation: unsupported combinations advertise no usable capacity. This keeps image,
resource policy and credentials operator-controlled, not selectable by models or jobs.

The shipped workload is `hyperion-generation`, schema `1`, profile `java-gradle`.
Configure its worker-local Spring AI chat model with `spring.ai.model.chat=openai` and
`spring.ai.openai.*`, as described in [Hyperion setup](/admin/hyperion#configure-spring-ai).
Chat is disabled by default in the generic executable. Other workloads do not need model
credentials unless their implementation uses a model. Use `max-retries: 0` when exact
provider accounting is required. Content telemetry stays off unless explicitly approved.

## Capacity and administration

Open **Administration → AI Generation**. The page is available when either
`artemis.aiworker.enabled` or whole-exercise generation is enabled on core. AI
Worker coordination is a separate module feature: turning Hyperion off does not
turn worker monitoring off. The **Administration → Features** page reports the
AI Worker, Hyperion, and whole-exercise generation settings separately. These
are startup settings, not runtime switches.
If coordination is disabled, the status endpoint returns 404 and the view reports that
status is unavailable rather than claiming an empty healthy pool.

| Column             | Meaning                                                            |
| ------------------ | ------------------------------------------------------------------ |
| Worker             | Stable worker name                                                 |
| State              | Available, running, starting, not ready, or offline                |
| Free / total slots | Current capacity; unavailable workers do not contribute free slots |
| Last contact       | Time core received the latest accepted heartbeat                   |
| Running jobs       | Executions reported by the worker; unknown when offline            |

Like Build Agents, the page loads an initial REST snapshot and receives updates over
admin-only WebSocket topics. The scheduling node publishes watched snapshots every
five seconds; there is no browser polling loop. The last-updated time and manual
refresh remain available. Failed requests are marked rather than presenting stale
data as healthy. Monitoring requires the standard `scheduling` profile on a core node.

Active generations show the exercise, owner, worker, start time, and whether a run is
running, saving, or being canceled. Open a run in a dialog without leaving the admin
page. Cancellation applies to the exact run and requires an audit reason.

Worker monitoring remains available without Hyperion; a worker-status outage does
not disable generation cancellation. Transport identifiers, capability schema versions,
and image digests remain available through `GET /api/aiworker/admin/workers` for incident
investigation, rather than occupying the everyday overview.

Budget memory and CPU for the worker JVM **plus every concurrent sandbox**. The slot
range is 1–16, default 1. Increasing slots does not relax per-execution resource limits,
feature budgets or provider rate limits. Keep the worker grace interval above heartbeat
spacing and core's reservation lifetime longer than presence lifetime.

## Maintenance and failure handling

1. Stop new workload admission and wait for active executions and pending deliveries to finish.
2. Confirm the workload's persistence/restore operations have also finished; worker idleness
   alone does not prove core has stopped writing.
3. Stop the worker with a container stop timeout longer than its two-minute shutdown budget.
4. Deploy matching core, worker, broker ACL and image configuration; then verify readiness.
5. Run a workload canary before reopening admission.

Protocol **4** uses neutral envelopes and explicitly versioned workload capabilities.
It is incompatible with earlier Hyperion-only wire protocols. Drain and stop old workers,
reconcile their containers under the old ownership labels, and change broker destinations
and configuration together. Do not keep old and new workers sharing an identity.

Cancellation and lost coordinator renewals stop only the exact execution. Reliable
accounting/checkpoint events precede completion; failed delivery keeps the slot occupied
while that worker is alive. A worker process loss is not a durable local outbox or an
exactly-once execution guarantee. Core fences stale incarnations; each workload decides
whether a retained result is usable and whether persistence requires operator recovery.

## Ansible and staging qualification

The `ls1intum.artemis.ai_worker` role deploys the supervisor. Select workload/profile
explicitly; enable `artemis_aiworker_enabled` on core and provision `artemis_aiworker`
broker credentials and worker IDs. Hyperion's two feature flags remain separate.
The role validates inputs, protects rendered secrets, preloads the sandbox image and
requires an explicit maintenance confirmation before replacing a running worker.
It does not provision the broker, certificates, firewall or isolation boundary.

Before staging admission, verify actual broker ACLs/TLS, image digests, Docker runtime,
store durability, worker capability and capacity. Then exercise successful completion,
cancellation, worker restart/lost renewals, capacity exhaustion and workload-specific
persistence/undo. Test with the deployment's intended distributed provider. Promote the
same qualified artifacts and configuration shape to production with separate secrets.
