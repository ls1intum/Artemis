Jenkins is deprecated and will be removed in Artemis 11, planned for March 2027
(see [Planned removals in Artemis 11](/about/roadmap#planned-removals-in-artemis-11)).
This guide describes how to move an installation that runs **Jenkins with LocalVC** to
**LocalCI with LocalVC**, the [Integrated Code Lifecycle](/admin/production-setup/integrated-code-lifecycle-setup).
Do the migration on a 10.x release, and upgrade to Artemis 11 only afterwards, so that you never change the build
system and the major version in one step.

<Callout variant={CalloutVariant.warning}>
    This guide is derived from the Artemis source code and the existing documentation. It has not yet been validated by migrating a
    production installation. Rehearse every step on a copy of your database and a staging server first, and keep the backups
    described below.
</Callout>

## What changes and what stays

LocalVC is the version control system of both setups. Only the build system changes, so the migration is much smaller than
it looks.

| Stays as it is | Changes |
| --- | --- |
| Git repositories, their URLs and access rules (LocalVC) | Builds run on Artemis build agents in Docker containers, no longer on Jenkins |
| Users, courses, exercises, participations, results and feedback | How an exercise is built: from the exercise's build phases and Docker image, no longer from a stored Jenkinsfile |
| Authentication, including LDAP, SAML2 and OIDC | How build agents authenticate to the repositories: per-build clone tokens or SSH keys, no longer a shared username and password |
| Exam and course configuration | Where instructors edit the build: the structured build plan editor, no longer a pipeline script |

Jenkins also kept a copy of the users and a build plan per participation. LocalCI has neither, so there is nothing to synchronize
and no Jenkins user to maintain.

## Before you start

1. **Read the [Integrated Code Lifecycle setup](/admin/production-setup/integrated-code-lifecycle-setup)** and the
   [security guide](/admin/production-setup/security) on repository authentication. Plan the build agent capacity with the
   [scaling guide](/admin/scaling). Builds that took one Jenkins node can need several build agents with LocalCI, and the
   build queue is shared state, so a multi-node installation also needs a [distributed data provider](/admin/production-setup/multiple-artemis-instances).
2. **Check feature parity** for your languages in the
   [language table](/instructor/exercises/programming-exercise#supported-programming-languages) and the
   [feature support table](/instructor/exercises/programming-exercise#feature-support-by-language). LocalCI supports every
   language that Jenkins supports and more. Sequential test runs for Kotlin and static code analysis for Swift, which used to exist only with Jenkins,
   are available with LocalCI from the release that contains them. Check the feature table of your target version before you migrate.
3. **Find customizations.** These do not carry over automatically:
   - Instructors who edited the pipeline script of an exercise in the script-based build plan editor. LocalCI ignores a stored Jenkinsfile
     and runs the build phases of the exercise. Such an exercise needs its script rebuilt as build phases, see [Step 4](#4-check-every-exercise).
   - Overridden Jenkins templates under `src/main/resources/templates/jenkins`, and changes to the pipeline for network access.
     LocalCI uses the [build phases templates](/admin/production-setup/programming-exercise-adjustments) and the Docker flags of the exercise instead,
     see [LocalCI Build Environment](/admin/production-setup/localci-build-environment).
   - Custom Docker images used by Jenkins agents. LocalCI runs the Docker image configured for the exercise on the build agents. Such an image must be
     available to the build agents in a registry or loaded on each Docker build agent, built for the architecture of the build agents (`artemis.continuous-integration.image-architecture`,
     `amd64` by default), and contain all build dependencies. A Docker build agent that runs in a container needs registry credentials that the container can read, because a login on the host does not reach the container by default. The Kubernetes runner needs an
     entry in `image-pull-secrets` for a private registry, see [build runners](/admin/production-setup/build-runners).
4. **Choose the time.** Migrate between teaching periods, never during an exam or in the days before a deadline.
5. **Take backups** of the Artemis database, the Artemis configuration and the LocalVC repository directory. Keep the Jenkins server
   untouched until the end of the migration.

## Migration steps

### 1. Prepare the LocalCI infrastructure

- Provision the hosts for the build agents. A build agent needs Docker, access to your Artemis nodes through the distributed data provider,
  and network access to the registry that serves the images. Start Artemis nodes with the `buildagent` profile for dedicated build agents,
  or let the core nodes build too.
- Pull the Docker images for your languages on the build agents so that the first builds do not wait for downloads. Builds fail when a
  build agent cannot reach the registry.
- Choose the distributed data provider. A single node can use the local provider. Several nodes need
  [Hazelcast or Redis](/admin/production-setup/distributed-data).

### 2. Rehearse on staging

1. Restore a copy of your production database on a staging server and start it with the new configuration of Step 3.
2. Complete Steps 3 to 5 on staging. Keep notes of every exercise that needed manual work, since you repeat that in production.

### 3. Change the configuration

Change these on every Artemis node. The profile names are the Spring profiles in `spring.profiles.active`.

| Setting | Jenkins with LocalVC | LocalCI with LocalVC |
| --- | --- | --- |
| Profiles | `jenkins`, `localvc` | `localci`, `localvc`, and `buildagent` on nodes that build |
| `jenkins.*` | Jenkins URL, credentials and tokens | Remove the whole block |
| `artemis.version-control.build-agent-git-username` and `build-agent-git-password` | The shared credential pair for Jenkins | Remove both. A node that runs LocalCI **refuses to start** while either is set. |
| Jenkins-specific keys under `artemis.continuous-integration` | Used, for example the build timeout | Remove them. They are marked as Jenkins specific in `application-artemis.yml`. |
| Build agent authentication | The shared credential pair above | Per-build clone tokens or SSH keys, see [Build agent authentication](/admin/production-setup/security) |
| Distributed data | Not needed on a single node | Set `artemis.distributed-data.provider` to `Hazelcast`, `Redis` or `Local`, see [distributed data](/admin/production-setup/distributed-data) |

The remaining LocalCI options (concurrent builds, Docker flags, the maximum build duration and the bulk trigger limits) are described in
[Configure Build Management](/admin/production-setup/integrated-code-lifecycle-setup#configure-build-management).

Start one node and check the log. The startup fails early and with a clear message when a profile or a credential does not match.
Open the administration area and confirm that the build agents appear and that the build queue is empty.

### 4. Check every exercise

LocalCI reads the build phases and the Docker image from the build configuration of the exercise. When an exercise has none,
LocalCI uses the defaults of its programming language and project type, which is what a new exercise gets. Therefore most exercises that
used the default Jenkins template need no change, and exercises with a customized pipeline do.

For each course that you migrate:

1. Open the exercise's build plan editor and look at the phases and the Docker image. Compare them with what the old pipeline did.
2. Rebuild customized pipelines as build phases. A phase has a name, a script, an inclusion condition (`Always` or `After due date`), a toggle that says
   whether tests are expected, the paths of its result files, and a toggle to run it at the end even after a failure.
   See [Adapt Build Phases](/instructor/exercises/programming-exercise/configure-the-build#adapt-build-phases-optional).
3. Trigger the template and the solution build of the exercise. The template should fail its tests and the solution should pass them, exactly as before.
4. Push a change to a student repository of a test account and confirm that the result arrives, including the feedback and, where you use it,
   static code analysis.

Ask the instructors of the affected courses to do this for their exercises, since they know what the pipeline was meant to do.
There is currently no list of the exercises that had a customized Jenkins pipeline, see the open points below.

### 5. Verify under load

On staging, trigger the builds of one large exercise ([bulk builds](/admin/production-setup/integrated-code-lifecycle-setup#bulk-builds)) and
watch the build queue, the build agent utilization and the failure rate. Adjust the number of build agents and the concurrent builds
per agent until the queue drains at an acceptable speed.

The failure rate here is the share of builds that did not deliver a result because of the infrastructure: builds that end as **Timeout**, **Missing**,
**Cancelled** or **Error** in the finished builds list of the build queue administration. Builds whose tests fail are not part of it. Compare the rate of the loaded run with a run
of the same exercise at low load. If it rises with the load, reduce the concurrent builds per agent, because timeouts under load usually mean that the agent host runs out of CPU or memory.
Also push repeatedly from a few test accounts during the run, because that is what students do before a deadline, see
[When many students push at once](/admin/scaling#when-many-students-push-at-once).

### 6. Cut over production

1. Announce a maintenance window to instructors.
2. Stop the nodes, back up the database, and start them with the configuration of Step 3.
3. Run the checks of Steps 4 and 5 on a few exercises that instructors prepared.
4. Keep Jenkins running and **read-only** for as long as you need the old build logs and plans. Do not delete anything there yet.

Existing results, feedback and grades stay unchanged. New pushes are built by LocalCI.

### 7. Decommission Jenkins

Wait until a full term has run on LocalCI without a rollback, then:

1. Disable the Jenkins jobs and the Server Notification Plugin webhook.
2. Remove the Jenkins server, its reverse proxy entry, its credentials and its users.
3. Remove the leftover Jenkins configuration and the Jenkins nginx and firewall rules.

## Rolling back

Until you upgrade to Artemis 11 you can go back, because Artemis 10 still supports Jenkins:

1. Stop all nodes and restore the backups of the database, the configuration and the repositories.
2. Start the nodes with the old profiles and the old configuration.

<Callout variant={CalloutVariant.warning}>

  Restoring the backups discards everything that happened after they were taken: new exercises, results, feedback, student commits and
  every other change in the database and the repositories. Announce the data loss to instructors and students before you do it, and take
  a fresh backup of the current state first, so that nothing is lost for good.

</Callout>

## What instructors need to know

- The build of an exercise is a list of phases with a Docker image, edited with **Edit build plan** on the exercise detail page. There is no pipeline script.
- Builds run in Docker containers on build agents, so a test that needs a package or a tool needs a Docker image that contains it.
- Builds of exams run with the highest priority in the build queue.

## Frequently asked questions

Each answer links to the page that explains the topic in full.

LocalCI can be extended to support further use cases. Where an answer says that something is not available, it describes the current state and not a fixed limit.
To request a setting or a behavior that is missing, open an issue in the [Artemis repository](https://github.com/ls1intum/Artemis/issues) and describe the use case.

**Can a script detect that it runs in CI?** There is no `CI` variable. `INITIAL_WORKING_DIRECTORY` is set in every build, and instructors can add variables per exercise.
See [Detecting that a script runs in LocalCI](/admin/production-setup/localci-build-environment#detecting-that-a-script-runs-in-localci).

**Can builds use a custom Docker registry with credentials?** Yes. Log the Docker user of every build agent in to the registry, with the login stored in `config.json` rather than in a credential helper.
See [Images from a private registry](/admin/production-setup/localci-build-environment#images-from-a-private-registry).

**What is the pull policy for images?** A build agent pulls an image only when it does not have it. A changed tag is not noticed, so use versioned tags.
See [Pull policy](/admin/production-setup/localci-build-environment#pull-policy).

**How well can nodes be added, and does it scale automatically?** A build agent joins a running cluster within seconds. There is no built-in autoscaler, and the experimental
[Kubernetes runner](/admin/production-setup/build-runners) lets a cluster schedule the builds. See [Operating build agents](/admin/production-setup/multiple-artemis-instances#operating-build-agents).

**What happens to the queue when students spam pushes?** Every push is a build, and the queue is ordered by priority and arrival. Instructors can cap the submissions per student with a
Lock Repository [submission policy](/instructor/exercises/programming-exercise/grade-and-verify#submission-policy-configuration). See [When many students push at once](/admin/scaling#when-many-students-push-at-once).

**Is there a sleep period between a submission and the build, to buffer requests?** No. Without a submission policy, students can submit as often as they like, and every submission is built.
The same section describes what protects the installation instead.

**Do all steps run in the container, with and without network?** The build script runs in the container, the clone of the repositories does not. A container has one network
setting for all of its phases, and an exercise without a selection gets Docker's default network. See [Network access](/admin/production-setup/localci-build-environment#network-access).

**Can I inject a Maven configuration for credentials, or a global offline configuration?** There is no installation-wide Maven setting. Put it in the Docker image or in the default
phases. See [Dependencies and Maven configuration](/admin/production-setup/localci-build-environment#dependencies-and-maven-configuration).

**How far can the default pipeline be adapted?** Instructors change the phases of each exercise, and administrators change the templates for new exercises.
See [How far the default build can be adapted](/admin/production-setup/localci-build-environment#how-far-the-default-build-can-be-adapted).

**Which user runs the Docker container?** The default user of the image, and `root` for a few housekeeping steps.
See [Which user runs the build](/admin/production-setup/localci-build-environment#which-user-runs-the-build).

**Which template is used for a new exercise?** The one for its language and project type, with `_static` and `_sequential` for those options, and plain Maven for Java without a project type.
See [Which template a new exercise gets](/admin/production-setup/localci-build-environment#which-template-a-new-exercise-gets).

**How do updates work in a multi-node setup?** The whole cluster is stopped and started in a defined order, with the build agents last.
See [Operating build agents](/admin/production-setup/multiple-artemis-instances#operating-build-agents) and [Deploying a New Version](/admin/production-setup/multiple-artemis-instances#deploying-a-new-version).

**What goes into which configuration file, and how many databases are there?** See [Which setting goes on which node](/admin/production-setup/multiple-artemis-instances#which-setting-goes-on-which-node).
There is one database, shared by the core nodes, and the build agents do not use it.

**Is there a log size limit?** Yes, 10,000 lines per build and 1,024 characters per line by default. See [Build logs](/admin/production-setup/localci-build-environment#build-logs).

**What happens when a node fails during a build?** The build is put back into the queue and another agent runs it, up to five times.
See [Operating build agents](/admin/production-setup/multiple-artemis-instances#operating-build-agents).

**How much build configuration does an instructor need when creating an exercise?** None beyond the language and the project type. A new exercise starts with a working build, and the build plan editor is optional,
see [Configure the Build](/instructor/exercises/programming-exercise/configure-the-build).

## Open points for the maintainers

These need a decision or a check before this guide is final.

- Validate the whole procedure with a copy of a production database that has Jenkins exercises, including old student participations.
- Decide whether Artemis should migrate customized Jenkinsfiles to build phases automatically, or only report which exercises have one.
  The guide currently makes this manual.
- Decide what happens to old Jenkins build logs and build plan links on results created before the migration.
- Add an administration view or a query that lists the exercises with a stored Jenkinsfile, so that operators do not have to find them by hand.

Gaps in comparison with Jenkins. The documentation states each one as it is today. LocalCI can be extended to cover them, and a decision would change the answers above:

- **No debounce for builds, and no installation-wide limit.** Instructors can cap submissions per exercise with a Lock Repository policy, which takes effect when a result is processed.
  A waiting period that merges quick successive pushes, or a limit on the queued builds of one participation, would protect the queue at a deadline,
  see [When many students push at once](/admin/scaling#when-many-students-push-at-once).
- **No installation-wide build environment.** There is no setting for environment variables (such as `CI=true`), a default Docker network, or a Maven configuration that applies to the builds
  of all exercises. Administrators use the image or the default phases instead.
- **No configurable pull policy.** The Docker runner pulls an image only when it is missing, and reads registry credentials from the Docker configuration of the agent host without credential helpers.
  An explicit registry credential setting and a policy to always check for a newer image are not available.
- **No built-in autoscaling.** Artemis exposes the queue and the agents, but starting and stopping agents is left to the environment. The experimental
  [Kubernetes runner](/admin/production-setup/build-runners) lets a cluster schedule the builds, but its Helm chart has a fixed number of build agents and no scaling rule.
- **Choices at exercise creation.** The Java project type (Maven or Gradle) is chosen per exercise. An installation-wide default would shorten the creation form for institutions that use one build tool.
